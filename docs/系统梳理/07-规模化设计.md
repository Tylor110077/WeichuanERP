# 07 · 规模化设计（客户与厂家会变得很多）

> 触发点：客户与厂家（供应商）数量会持续增长到几百甚至上千，商品型号在电线电缆行业也会很多。
> 本文回答三个问题：**现在哪些地方会"放不下"？** **应该换成什么呈现方式？** **先后顺序怎么排？**

## 一、结论先说

| 风险等级 | 问题 | 现状证据 | 数据量到什么程度会疼 |
|---|---|---|---|
| **P0 会直接拖慢每天开单** | 开单页把**整个商品目录 + 整个客户目录 + 全部历史销售明细**一次性查出来塞进页面，再在浏览器里过滤 | `sale-orders/new/page.tsx:20`（全部商品，无 `take`）、`page.tsx:99-124`（全部历史销售明细，用于"最近成交价/上次给该客户的价格"） | 商品 ≥ 约 800 条或历史单据 ≥ 约 1 万行时，开单页首屏明显变慢（负载按数据量线性增长） |
| **P1 列表页放不下** | 客户列表、商品列表**全量查询 + 全量渲染，没有分页** | `customers/page.tsx:52`、`products/page.tsx:92`（均无 `take`、无 `page`） | 客户/商品过几百行后：首屏 DOM 大、手机卡、找东西只能靠搜索 |
| **P1 芯片墙** | 商品页的厂家筛选是把**每个厂家渲染成一个 chip** 平铺一行 | `products/page.tsx` 的 `MfrChip` 列表 | 厂家超过约 15 个就开始折行挤压，超过 30 个基本不可用 |
| **P2 主数据列表** | 厂家/分类/单位/组织/标签五个列表同样全量渲染、无分页 | `master-data-manager.tsx` 直接渲染传入的 `rows` | 厂家上千时同样放不下（分类/单位通常很少，可不动） |
| **P2 财务类表格截断** | 应收应付、对账单等用 `take: 200 / 500` 截断但没有分页，用户看不到全貌 | `receivables-payables/page.tsx`、`supplier-statement/page.tsx` | 单据上千后"只显示最近 N 张"会成为常态，需要翻页 |

**一句话**：列表本身没问题（表格能横向滚动、能搜索），问题在于**"全量"和"平铺"**——该分页的分页、该收进搜索框的收进搜索框。

## 二、设计原则

1. **搜索优先于浏览**：数量大了以后，用户不是"翻列表找"，而是"输入关键词直接命中"。列表仍需存在（用于浏览最近的、核对总量），但**默认只给第一页**。
2. **"最近/常用"优先于"全部"**：开单时最可能用到的是"最近卖过的商品"和"最近往来的客户"，而不是第 3000 条商品。
3. **一屏装不下就换控件**：同一组筛选项在少量时用 chip（一眼看全、一点即筛），大量时换成可搜索的选择器（输入即匹配）。判据是数量阈值，不是"感觉"。
4. **列表后端分页、URL 可分享**：沿用售卖单列表已有的 `?page=` 模式（服务端 `skip/take` + 计数），不引入虚拟滚动等新范式。
5. **不减少功能**：任何"收起来"的东西都要有可到达的路径（搜索、页签、分页）。

## 三、具体方案

### S1 开单页的选择器改为"服务端搜索 + 最近优先"（P0）

**现状**：`customers` 与 `products` 两个数组作为 props 传给客户端组件，在浏览器里 `includes()` 过滤；
"最近成交价"更是把**全部历史销售明细**查出来再取每个商品的第一条。

**目标**：
- 首屏只带**最近往来 + 少量样本**：客户取"最近有成交的 50 个"，商品取"最近卖过/最近进过的 50 个"，而不是全表；
- 用户输入 ≥ 1 个字符时，走**服务端搜索 action**（`searchProductsForOrder(keyword)` / `searchCustomersForOrder(keyword)`，各自 `take: 30`），返回结果替换下拉候选；
- "最近成交价/上次该客户的价格"改为**按需查询**：选中商品（或该客户+商品组合）时再查一条，而不是预先把全表拉进内存；
- 保留本地过滤作为"候选已加载时"的即时反馈，避免每次按键都等网络。

**验收**：商品 5000 条、历史单据 10 万行时，开单页首屏负载与现在（2 个商品）处于同一量级；输入关键词 1 次即列出匹配项。

### S2 客户列表与商品列表加服务端分页（P1）

- 两个页面加 `?page=`，`PAGE_SIZE = 50`（资料类列表比单据列表更适合大页），服务端 `skip/take` + `count`；
- 复用售卖单列表的分页条（上一页 / 第 N / M 页 / 下一页），并把当前搜索词、厂家或组织筛选一起带在链接上；
- 表格上方显示「共 N 条」，让用户知道还有多少（现只有当前页数量）。

### S3 厂家筛选自适应：少则 chip，多则搜索（P1）

- 厂家 ≤ 12 个：保持现在的 chip（一眼看全，信息气味最好）；
- 厂家 > 12 个：改为「全部 / 未填厂家」两个 chip + 一个**可搜索的厂家选择器**（复用已有的 `SearchSelect`），并在标题旁显示"共 N 个厂家"；
- 阈值写进代码常量，避免以后靠感觉调。

### S4 主数据列表（厂家/组织/标签/分类/单位）分页（P2）

在 `MasterDataManager` 上增加可选的 `pager` 渲染（由服务端算好 `page/totalPages/buildHref` 传入），
`rows` 只传当前页；分类、单位这类通常不足 20 条的列表不传 `pager` 即可，行为不变。

### S5 财务类表格补分页与"共 N 条"（P2）

应收应付、厂家对账的表格改为分页（当前 `take: 200/500` 保留为上限提示），合计仍用 SQL 聚合（已在 R0-1 落地），不受分页影响。

### S6 数据库与查询（P2，随 S1 一起做）

- 搜索走 `contains`（`LIKE '%x%'`）会全表扫描；客户/商品量上千后建议：
  - 常用检索字段加索引（`customers.name`、`customers.phone`、`products.code`、`products.name`）；
  - 开单页的"最近"查询改为按 `createdAt desc` 且**带 `take`**（现在是无上限），配合已有索引；
- 这些属于 schema/索引变更，需单独一次迁移，不与界面改动混在一起。

## 四、先后顺序

| 顺序 | 做什么 | 理由 |
|---|---|---|
| 1 | **S2 分页**（客户、商品） | 改动小、当天见效，立刻消除"全量渲染" |
| 2 | **S3 厂家筛选自适应** | 同样小改动，直接解决"芯片墙" |
| 3 | **S1 开单页服务端搜索** | 影响面较大（触及开单页与两个 action），但这是唯一会拖慢每天开单的问题，必须在数据变多之前做 |
| 4 | S4 主数据分页、S5 财务分页 | 数据量到几百时再做也不迟 |
| 5 | S6 索引与查询收敛 | 与 S1 同期评估，单独迁移 |

## 五、验收标准（可量化）

1. **负载不随总量线性增长**：商品/客户各 5000 条、历史单据 10 万行时，开单页首屏 HTML + 内联负载不超过约 300 KB（现在随总量增长，无上限）。
2. **列表页首屏行数恒定**：客户/商品列表任何数据量下首屏 ≤ 50 行；页码与总数可见。
3. **筛选区不折行爆炸**：厂家 ≥ 50 个时，筛选区仍是一行（1 个选择器 + 2 个 chip）。
4. **功能不减**：所有原本能在列表里看到/操作的对象，都能通过搜索 + 分页到达；搜索、筛选、页签、分页条件互通不丢。

## 七、执行记录：S1 已落地（本次提交）

开单页从"一次性下发全量目录"改为"最近往来 + 按需搜索"。

**改动**

- 新增 `src/app/(main)/sale-orders/new/search-actions.ts`（只读 server actions）：
  - `recentProductsForOrder()` / `recentCustomersForOrder()`：首屏候选＝最近卖过/进过/往来的 40 条（不足用最新建档补齐）；
