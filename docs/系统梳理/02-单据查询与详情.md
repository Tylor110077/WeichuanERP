# 02 · 单据查询与详情

范围：售卖单列表 / 进货单列表 / 两类退货单列表 / 售卖单详情 / 进货单详情 / 打印预览，以及它们共用的组件。
一句话结论：**四个列表 + 两个详情 + 两个收付款区块 + 两个单据操作条，本质上是同一套东西写了两遍（对称复制），重复度 65%~96%；而用户真正缺的是"从一张单能走到相关联的一切"。**

---

## 一、逐页逻辑地图

### 1. 售卖单列表 `src/app/(main)/sale-orders/page.tsx`（269 行）

- **唯一职责**：按条件列出售卖单，并让用户走到详情或直接登记收款。
- **入口**：侧边栏「售卖单」(`layout.tsx:29`)；工作台「今日销售额」卡片 (`dashboard/page.tsx`)；开单成功后的 `redirect("/sale-orders")`。
- **筛选**（`page.tsx:114-140`）：关键词 `q`（单号/客户）、客户 `customerId`（可搜索下拉）、起止日期 `from`/`to`、状态 `status`、款项 `settle`（未结清/已结清）。日期另有快捷条（`DateShortcuts`，会带上其余筛选，见 `page.tsx:102-110`）。
- **列表列**：单据号 / 客户 / 状态 / 金额 / 已收 / 款项（已结清胶囊 或 未结清 ¥x）/ 操作人 / 开单时间 / 操作（详情 + 未结清时多一个「登记」）。
- **写操作**：本页无写操作（纯查询）。
- **边界**：空列表 → `EmptyState` 带「+ 新建售卖单」；分页 links 保留全部筛选（`page.tsx:236-243`）；作废单的款项列显示 `—`。

### 2. 进货单列表 `src/app/(main)/purchase-orders/page.tsx`（296 行）

- 与售卖单列表**结构对称**，差别只有：客户 → 厂家（`supplierId`）、已收 → 已付、多一列「来源」（自动补货 / 手工），以及一条额外过滤：`q` 支持按单号搜。
- **唯一额外的业务分支**：`sourceSaleOrderId` 非空时状态列显示「自动补货」并链回售卖单。这一分支只在进货单侧存在，售卖单侧没有"本单的补货单"筛选。

### 3. 售卖单详情 `src/app/(main)/sale-orders/[id]/page.tsx`（310 行）

区块顺序（`page.tsx:77-260`）：

1. **标题行**：`售卖单 SO2026...` + 状态胶囊 + 右侧三个按钮：打印销售单（次按钮）、退货（警告色，`btnWarn`）、作废（危险色，`DetailActions` 内）、返回列表。
2. **基本信息卡片**：客户 / 开单操作人 / 开单时间 / 备注，以及金额组：`已收 / 应收`（斜杠形式）、`未收金额`、`本单毛利（按成本快照）`。成本与毛利对 `sales` 角色隐藏。
3. **收款区块** `ReceiptBlock`（`receipt-block.tsx`，188 行）：已收 / 未收 / 「收款」按钮 / 收款历史（每笔可「撤销收款」）/ 反馈提示。
4. **商品明细**：编码 / 商品名称 / 数量（含"用库存 X + 现场进 Y"小字）/ 单位 / 售价 / 金额 / 备注 / 成本（快照）；表尾合计。
5. **关联补货单**（有则显示）：自动补货进货单号 + 厂家 + 状态，可点进。
6. **本单退货记录**（有则显示）：退货单号/数量/金额，链到退货单列表。

- **写操作**：作废（`DetailActions` → `voidSaleOrderAction`，需填原因，会同时作废关联的自动补货单并冲回库存）；退货（链到 `/sale-returns/new?orderId=`）；收付款登记与撤销（`receivables-payables/actions.ts`）。

### 4. 进货单详情 `src/app/(main)/purchase-orders/[id]/page.tsx`（282 行）

与售卖单详情同构，差异清单：
- 客户 → 厂家；已收/应收 → 已付/应付。
- 多一个状态分支：`pending`（待入库）时出现绿色「确认入库」按钮（`detail-actions.tsx:38-50`）——这是进货单特有的"确认收货"动作。
- 明细列里「售价」变「进价」，多一列「规格」；数量小字由"用库存/现场进"变"客户 X + 备货 Y"（对应多补备货）。
- 没有"本单退货记录"以外的差异；退货按钮同样链到 `/purchase-returns/new`。

### 5. 退货单列表 `sale-returns/page.tsx`、`purchase-returns/page.tsx`（各 84 行）

- 只列退货单：退货单号 / 原单 / 客户（厂家）/ 状态 / 冲减应收（应付）/ 操作人 / 时间 / 操作。
- **无筛选、无分页、无快捷时间**——与售卖/进货列表的体验明显不一致（后两者有 5 个筛选项 + 分页 + 快捷日期）。
- 入口只在详情页的「退货」按钮、以及详情页的退货记录链接，导航里没有。

### 6. 打印预览 `src/app/sale-orders/[id]/print/print-editor.tsx`（373 行）

- 工具栏（打印时隐藏）：打印 / 返回 / 列显示开关（`Chip`）/ 行增删。
- 文档区：单头信息 + 可编辑表格 + 合计 + 金额大写（`rmbUpper`）。
- **打印内容在页面上实时可编辑，但不会回写数据库**——这是一处容易误解的地方：用户改了打印稿上的数量，以为订单也改了。

## 二、重复与不一致（附证据）

| 对比 | 规模 | 独有行 | 重复度 |
|---|---|---|---|
| `receipt-block.tsx` vs `payment-block.tsx` | 188 vs 188 | **7** | **≈96%** |
| `sale-returns/page.tsx` vs `purchase-returns/page.tsx` | 84 vs 84 | 11 | ≈87% |
| `detail-actions.tsx`（销售 vs 进货） | 60 vs 99 | 8 | ≈87% |
| `sale-orders/page.tsx` vs `purchase-orders/page.tsx` | 269 vs 296 | 49 | ≈82% |
| `sale-orders/[id]/page.tsx` vs `purchase-orders/[id]/page.tsx` | 310 vs 282 | 102 | ≈65% |

具体差异点（可据此设计统一的 props）：

| 维度 | 售卖单 | 进货单 |
|---|---|---|
| 交易对手 | `customer` | `supplier` |
| 款项字段 | `receivedAmount` / 已收 / 未收 | `paidAmount` / 已付 / 未付 |
| 金额标签 | 应收 | 应付 |
| 状态 | `confirmed` / `voided` | `pending`（待入库）/ `received` / `voided` |
| 特有动作 | 打印销售单 | 确认入库（`pending` 时） |
| 明细列 | 售价 / 成本（快照） | 进价 / 规格 / 客户 vs 备货拆分 |
| 关联单据 | 本单自动补货进货单 | 来源售卖单 |

`receipt-block.tsx` 与 `payment-block.tsx` 的 7 行差异只是文案与字段名——**这是全场最该先合并的一处**（一个 `direction: "receipt" | "payment"` 参数即可）。

## 三、摩擦点（按用户真会撞上的顺序）

1. **"这张单的货是哪来的、卖给谁了"要跨页找。** 售卖单详情只链到自动补货单；反过来进货单详情只链到来源售卖单。想知道"这个自动补货单的货最终卖给了哪个客户"需要点进点出。建议两个方向都补链接。
2. **退货入口在详情页里，列表没有。** 退货单列表没有筛选、没有分页，且导航里没有入口 → 想"查上个月的退货"只能先进某张售卖单详情，或手输 URL（`sale-returns` 全站仅 2 处提及，均在详情页）。
3. **打印页的编辑是个陷阱。** 打印预览里改数量/单价、加删行都是纯前端状态（`print-editor.tsx:61-84`），不会保存；但界面没有任何提示说明"这里的修改不会保存到订单"。用户很可能以为改了打印稿就等于改了订单。
4. **四个列表的筛选能力不对等。** 售卖/进货列表 5 个筛选项 + 分页；退货列表 0 个筛选、0 分页。同一个"查单据"的心智模型在这里断裂。
5. **详情页首屏要滚动才能看到款项动作。** 收款/付款区块位于基本信息之后、商品明细之前；对"我来登记一笔收款"的人来说，进入页面后还要向下滚动一屏（`receipt-block` 的锚点 `#receipt` 已支持直达，但只有列表的「登记」链接用它）。
6. **危险操作确认成本不对称。** 作废：按钮 + 必填原因（好）；退货：直接跳转新页面（可接受）；主数据里的停用/删除：直接提交、无确认（见 `00-总览` S5）。

## 四、合并 / 重组 / 升级建议

| # | 建议 | 依据 | 影响文件 | 量 | 风险 |
|---|---|---|---|---|---|
| D1 | 收付款区块合并为一个组件：`<PaymentBlock direction amount payments outstanding ... />`，文案与字段名由调用方传入 | 96% 重复，改一处等于改两处（避免"收款修了、付款没修"的经典 bug） | `receipt-block.tsx`、`payment-block.tsx`、两个详情页 | S | 低（纯重构，行为不变） |
| D2 | 退货单列表与售卖/进货列表统一：加同样的 5 个筛选 + 分页 + 快捷日期，并给出导航入口（或作为「单据」页的一个页签） | 一致性；"查退货"不该比"查售卖单"难 | `sale-returns/page.tsx`、`purchase-returns/page.tsx` | M | 低 |
| D3 | 详情页互链补全：售卖单 ↔ 自动补货单、进货单 → 来源售卖单（已有）→ 该售卖单的客户；退货单 → 原单（已有）→ 反向列出"本单的退货" | 信息气味：用户是从一张单出发去理解业务的 | 两个详情页、退货列表页 | S | 低 |
| D4 | 打印页顶部加一句明确提示「打印稿的修改不会保存到订单，如需改单请先作废后重开」，或把"编辑"改为默认只读、需要显式点「编辑」才可改 | 防错优于报错；消除"以为改了订单"的误解 | `print-editor.tsx` | S | 低 |
| D5 | 列表行内操作补「打印」（售卖单）与「确认入库」（进货单待入库行），减少进详情再操作的往返 | 就近原则 | 两个列表页 | S | 低 |
| D6 | 详情页把「款项」相关信息（已收/未收 + 登记按钮 + 历史）与「金额」合并在同一张卡片里，减小滚动距离 | 邻近性（Gestalt）：同一件事的信息不该被另一块隔开 | 两个详情页 + 收付款组件 | M | 低 |
| D7 | 售卖单/进货单列表、详情抽公共骨架（`OrderListShell` / `OrderDetailShell`），差异用配置表达 | 82% / 65% 重复；后续加字段不必改两处 | 8 个文件 | L | 中（需回归全部单据流程） |

## 五、这个模块最该先做的 3 件事

1. **D1 收付款区块合并**（半天，纯重构，收益是"改一次生效两处"，同时能顺手修掉两处不一致）。
2. **D3 + D5 链接与行内操作补全**（半天，直接减少每天的跳转次数，风险极低）。
3. **D2 退货列表对齐**（1 天，把"查单据"的心智模型补齐；顺带给退货一个导航入口，终结"靠手输 URL"）。
