# 08 · 大数据量下的性能与体验设计

> 触发点：单据、客户、厂家、商品都会长期增长（预期：单据数万到数十万、商品上千、客户上千）。
> 本文回答两件事：**① 视觉/渲染上的性能表现；② 在大量数据下如何既快又好用。**
> 所有数字都是在本地开发库**真实造数**后实测的（2 万售卖单 + 2 万明细 + 宽时间范围），不是估算。

---

## 一、实测基线：先找出真正的悬崖

造 2 万单 / 2 万明细后，逐页测「响应耗时 + 响应体大小」：

| 页面 | 改造前 | 改造后 | 问题性质 |
|---|---|---|---|
| `/reports?tab=receivables`（应收明细） | **18.3 s / 28.7 MB** | **0.47 s / 470 KB** | 全量渲染：把区间内每一张单都渲染成表格行 |
| `/price-analysis?productId=…`（价格分析） | 1.11 s / 3.0 MB | 0.59 s / 0.87 MB | 图表点数与明细行数无上限 |
| `/receivables-payables`（应收应付） | 0.79 s / 329 KB | 0.22 s / 143 KB | 表格一次渲染 200 行且无分页 |
| `/sales-analysis`（销售分析） | 0.23 s / 158 KB | 0.23 s / 158 KB（待改） | 在 JS 里遍历区间内全部单据与明细做聚合 |
| `/reports?tab=sales-rank`（单品排行） | 0.90 s | **0.09 s / 47 KB** | 把区间内全部明细取回内存再累加 |
| 单据列表 / 客户 / 商品 / 工作台 | 0.03~0.14 s | 同左 | 已有分页 + SQL 聚合，健康 |

**结论：会"炸"的不是列表页，而是三类页面**——
① 把区间内全部行渲染出来的报表；② 无上限的图表与明细；③ 在内存里做聚合的分析页。

> 28.7 MB 的单页响应意味着：手机打开会直接崩、桌面浏览器也要卡十几秒。
> 这类问题在数据量小的时候完全看不出来，属于"上线半年后才炸"的隐患。

---

## 二、把每个查询按"随数据量怎么长"分类

| 复杂度 | 含义 | 现状举例 | 处理原则 |
|---|---|---|---|
| **O(1)** | 与总量无关 | 单据详情、单号/主键查询、`groupBy` 聚合、`count()` 带索引 | 保持 |
| **O(页)** | 与每页条数有关（可控） | 各列表页（20~50 行/页）、订单开单页（最近 40 条候选） | 每页行数写死并保持小 |
| **O(区间)** | 与筛选区间内的行数有关 | 分析报表、价格分析、导出 | 下推到 SQL 聚合 / 限制渲染行数 / 明确提示 |
| **O(全表)** | 与总量成正比，必须消灭 | 「加载区间内全部单据+明细到 JS 再聚合」；应收应付全量聚合 | 改成 SQL 聚合或预聚合 |

## 三、三层措施（按性价比排序）

### 第 1 层：索引（已完成，零风险）

高频查询的共同形态是「**按状态/对象过滤 + 按时间倒序取一页**」。单列索引只能命中其中一个条件，
复合索引可同时服务过滤与排序，避免 `filesort`。

本次迁移 `20260912180000_perf_indexes` 新增：

| 索引 | 服务的查询 |
|---|---|
| `sale_orders(status, created_at)` | 售卖单列表、应收应付、报表（按状态 + 期间） |
| `purchase_orders(status, created_at)` | 进货单列表、应付 |
| `sale_orders(customer_id, created_at)` | 客户画像 / 客户详情（某客户的单据按时间） |
| `purchase_orders(supplier_id, created_at)` | 厂家对账 |
| `sale_returns(created_at)`、`purchase_returns(created_at)` | 退货单列表 |
| `products(manufacturer)` | 商品页按厂家分组/筛选、厂家商品数 |
| `customers(phone)` | 按电话搜客户 |
| `stock_movements(biz_type, created_at)` | 库存流水按类型 + 期间 |

`EXPLAIN FORMAT=TREE` 逐条核对，以上查询均已命中对应索引（例如售卖单列表从全表扫描变为
`Covering index range scan … (reverse)`，覆盖索引且直接反向扫描取 20 行）。

### 第 2 层：查询改写（本次已完成的部分）

1. **报表明细：行数上限 300 + 明确提示 + 导出保留全量**
   `MAX_REPORT_ROWS = 300`；被截断时页面上写明「仅展示前 300 行，完整数据请导出」。
   **导出走 `{ unlimited: true }` 绕过上限**（这里踩过一个坑：用 `undefined` 传参会触发默认参数，
   必须用 `0` 表示"不限"）。
2. **价格分析：图表 300 点 / 明细 200 行 / 每日统计 90 天**，各带说明文案。
   图表此前会给每一笔销售画一个点，几千个 `<circle>` 既拖慢渲染也撑大负载。
3. **应收应付：单据表分页（50 行/页）**；合计仍是 SQL 聚合，不受分页影响。
4. **（上一轮已完成）** 商品/客户列表分页、筛选下推到数据库、计数改 `groupBy`、
   开单页改为「最近往来 + 按需搜索」（首屏负载 322 KB → 38 KB）。

### 第 3 层：预聚合与键集分页（尚未做，给出触发条件）

| 措施 | 解决什么 | 触发条件（建议） | 做法 |
|---|---|---|---|
| **单据列表键集分页** | 深翻页 `OFFSET 100000` 仍要先扫 10 万行 | 单据 > 10 万或出现翻页变慢 | 用 `created_at < 上一页最后一行的值` 游标替代 `OFFSET`；UI 改为「上一页 / 下一页」，去掉页码跳转 |
| **客户/厂家往来余额** | 应收应付合计是 `O(全部单据)` 的聚合 | 单据 > 10 万（聚合 > 200 ms） | 在 `customers`/`suppliers` 上维护 `receivable` / `payable` 余额，开单、作废、退货、收付款时在同一事务里增减；页面只读余额行 |
| **按日汇总表** | 工作台/分析的「今日、本月、按日趋势」每次扫描区间明细 | 明细 > 50 万 | 建 `sales_daily(product_id?, customer_id?, date, qty, amount, cost)`，下单/作废时累加；分析页按日读几十行 |
| **搜索词前缀化** | `LIKE '%关键词%'` 无法用索引（全表扫描） | 单据 > 10 万且按客户名搜变慢 | 单号/编码类改前缀匹配（可走索引）；客户/商品名改用下拉选择（本来就是按 id 过滤） |
| **导出流式化** | 导出几十万行时一次性放进内存 | 导出 > 5 万行 | 用游标分批读 + 流式写 xlsx |

## 四、视觉与感知性能（渲染层）

1. **每页行数写死且保持小**：列表 20、资料列表 50、报表 300、图表 300 点、明细 200 行。
   DOM 行数与总量解耦——这是"视觉性能"的根。
2. **只渲染当前工作区**：页签/主从布局下，非当前页签的内容根本不进 DOM（不是隐藏，而是不渲染）。
3. **加载骨架**：新增 `src/app/(main)/loading.tsx`，路由切换时立即出骨架，避免"点了没反应"。
4. **不做无谓的客户端组件**：列表页保持服务端渲染，客户端 JS 只用在真正需要交互的地方
   （选择器、筛选表单、行内操作），减少 hydration 成本。
5. **表格横向滚动而非压缩**：列多时用 `overflow-x-auto`（已在用），避免挤成一列字。

## 五、好用：数据多了以后，交互也要跟着变

数据量大了，**"翻列表找"必然失败**，交互重心要从"浏览"转向"检索 + 最近优先"：

| 场景 | 小数据量时的做法 | 大数据量时的做法（已落地/计划） |
|---|---|---|
| 开单选商品/客户 | 下拉里滚动找 | **首屏只带最近往来 40 条 + 输入即服务端搜索**（已落地） |
| 找单据 | 列表翻页 | 单号/客户/期间/款项四类筛选 + 分页（已有），后续加键集分页 |
| 商品按厂家/分类看 | 一排 chip | **左栏可搜索的筛选轴**（已落地，厂家/分类各一条） |
| 资料维护（厂家/组织/标签） | 一条条翻 | 主数据列表分页 + 行内二次确认（分页待做） |
| 分析报表 | 拉全量看 | 行数上限 + 导出全量（已落地），后续预聚合 |

**判断标准**：任何"要靠肉眼扫完"的界面，在数据上千后都必须能通过**输入一个词**直接命中。

## 六、验收基线（可量化，改前改后都要测）

| 指标 | 目标 | 当前（2 万单实测） |
|---|---|---|
| 单页响应体 | **< 300 KB**（报表/分析类可放宽到 500 KB） | 最大 470 KB（应收明细） |
| 单页响应时间（本地 dev） | < 1 s | 最大 0.59 s |
| 首屏渲染行数 | ≤ 50 行（列表）/ ≤ 300 行（报表） | 达标 |
| 图表元素数 | ≤ 300 个点 | 达标 |
| 任一路由的 SQL 查询 | 无 `O(全表)` 的"取全部再算" | 仅剩分析页的聚合在 JS 里做（见第七节） |

**测试方式**：造 2 万单 + 2 万明细（脚本见本次提交说明），
用 `curl -w "%{time_total} %{size_download}"` 逐页测量，改动前后对比；测完删除造数。
