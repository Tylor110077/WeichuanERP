# 01 · 开单流程

范围：销售开单、进货开单、销售退货开单、进货退货开单（含它们的 server actions）。
一句话结论：**进货开单是 280 行的"正常表单"，销售开单是 1283 行、30 个 useState、8 套内联快捷新建的"全能页"——两者做的是同一件事（录入一张单），复杂度却差 4.6 倍。真正的设计问题不是"哪一行代码重复了"，而是"开单页让用户做太多系统能替他做的决定"。**

---

## 一、逐页逻辑地图

### 1. 销售开单 `/sale-orders/new`（`new-sale-form.tsx` 1283 行 + `page.tsx`）

**唯一职责**：录入一张售卖单。但因为"缺货要现场进货"这条业务规则，它实际同时承担了 6 件事：维护单据行、维护客户、维护商品、维护分类/单位/厂家、维护客户组织/标签、维护现场进货价与备货量。

**入口**：侧边栏「售卖单」→列表右上角「+ 新建售卖单」；工作台「销售开单」卡片；列表空状态引导按钮；客户画像/详情页等处的转介。全站 9 处提及。

**页面结构**（两个 `<details>` 折叠区，默认展开）：

| 区块 | 内容 |
|---|---|
| 客户信息（折叠） | 客户搜索选择器（输入即匹配候选）+「+ 新建客户」内联表单（名称/电话，含快捷新建组织、快捷新建标签）+ 选中后显示组织/标签/地址/电话 |
| 单据备注 | 限宽 `max-w-xl` 的单行输入（作用于整张单据） |
| 商品明细与备注（折叠） | 每行：商品搜索（浮层候选，含「＋新建商品：『关键词』」）、厂家标签、编码、数量、单位、库存（含均价）、售价（含参考价/上次该客户价）、补货区（用库存/需进货/进价/多补）、行备注、金额、删除 |
| 行操作 | 「+ 添加商品行」「+ 新建商品」（内联表单：名称/规格/厂家/分类/单位/参考进价/参考售价/预警线） |
| 提交区 | 「提交售卖单」+ 未选客户时的禁用提示；提交后反馈（成功/失败） |

**状态规模**：**30 个 `useState`**（`new-sale-form.tsx:104-170` 区间），包括 5 个"快捷新建"的开关与临时值、2 个 `useTransition`、商品浮层的定位坐标。对比进货开单只有 3 个。

**8 套内联快捷新建**（都在开单页里就地完成，不跳页）：
客户（`onCreateCustomer:171`）、分类（`quickCreateCategory:208`）、单位（`quickCreateUnit:226`）、客户组织（`quickCreateGroup:243`）、客户标签（`quickCreateTag:260`）、商品（`onCreateProduct:430`）、厂家（商品表单内联，`820` 行处「＋ 新建厂家」）。

**关键计算**（前端实时，`397-428`）：
- `usedStock(row)`：本次用掉的库存（留空＝尽量用库存；填 0＝全部现场进货），并受 `stockCap` 封顶；
- `needPurchase(row)`：需求 − 用库存，= 需要现场进货的数量；
- `extraRestock(row)` / `restockTotal(row)`：多补备货数量与补货总量；
- `lineAmount(row)`：数量 × 售价。

**提交后服务端做了什么**（`sale-orders/actions.ts` 的 `createSaleOrderAction`，三段式）：
1. 逐行做 `LinePlan` 计划：`stockUsed`（默认取 min(库存, 数量)）、`purchaseQty`、`extraQty`、`supplyPrice`；
2. **先**把"现场进货 + 多补"生成一张**自动补货进货单**（状态直接 `received`，即"生成即入库"，按当次进价移动加权入库），并写库存流水；
3. **再**扣减本单实际使用的库存（库存部分按当前移动加权成本、现场进货部分按填写的进价），写入成本快照 `costAmount` 与 `stockQtyUsed`；
4. 计算总金额、写审计、`revalidatePath`、`redirect("/sale-orders")`。

**校验与错误**（本轮刚统一为中文，见提交 `74e3168`）：逐个字段给出中文提示并带行号，例如「第 1 行「数量」：请填写数量」；客户未选时按钮禁用并说明原因。**提交失败不会丢失已填内容**（客户端状态保留，`useActionState` 不重挂页面）——这是现有实现的一个优点，改动时别破坏。

**边界**：未选商品的空行会被服务端跳过；库存为 0 时「用库存」自动为 0、占位显示 `0.000`（**注意：那是占位符，不是值**）；进货价为 0 视为合法；作废后库存与应收可正确冲回（`voidSaleOrderAction` 同时作废关联补货单）。

### 2. 进货开单 `/purchase-orders/new`（`new-order-form.tsx` 280 行）

**唯一职责**：录入手动进货单。结构：厂家（可搜索）+ 单据备注 + 明细行（商品/数量/进价/备注）+ 提交，全页 3 个 `useState`。
**服务端**（`purchase-orders/actions.ts`）：校验 → 生成单号 → 逐行入库（移动加权）→ 写流水与审计 → 重定向。
**边界**：状态为 `pending`（待入库）时可由详情页「确认入库」改为 `received`。

**与销售开单的对照**（同一件事，两套复杂度）：

| | 销售开单 | 进货开单 |
|---|---|---|
| 代码量 | 1283 行 | 280 行 |
| `useState` | 30 | 3 |
| 内联快捷新建 | 8 套 | 0 |
| 每行字段数 | 10（含补货 4 格） | 4 |
| 服务端事务 | 3 段（补货入库 → 扣库存 → 快照） | 1 段 |
| 前端计算函数 | 5 个 | 1 个 |

### 3. 销售退货 `/sale-returns/new`、进货退货 `/purchase-returns/new`（各 277 行，页面 + `return-form.tsx`）

- 页面只负责算"可退数量"：`可退 = 原单数量 − 已退数量`（`sale-returns/new/page.tsx:59-79`），退货价默认取原单售价（符合《细节评审》Q4 口径）。
- 表单：每行**先在下拉里选商品**（只列可退行，标注"可退 X"）、再填退货数量（`max=可退数量`）、退货单价、备注；可「+ 添加一行」。
- **入口摩擦**：从售卖单详情点「退货」进入本页时，表单是**空的一行**——明明是从那张单进来的，却要再选一次商品（`return-form.tsx:44`）。
- 两个退货页与对应的列表/actions 是 87% 重复的对称实现。

## 二、重复与不一致（附证据）

| 对比 | 规模 | 独有行 | 重复度 |
|---|---|---|---|
| 销售退货开单 vs 进货退货开单 | 95 vs 95 | 12 | ≈87% |
| 销售 actions vs 进货 actions | 608 vs 357 | 410 | 开单事务逻辑同构但销售多出"补货+分段成本" |
| 销售开单表单 vs 进货开单表单 | 1283 vs 280 | 1100 | ≈14%（几乎各写一套） |

**不一致点**：
1. 销售开单**不选商品也能加行**（行内是搜索框，空行被服务端跳过）；进货开单是**下拉选商品**（`new-order-form.tsx:140` 是 hidden input + 下拉）。同一个"选商品"动作，两页交互不同。
2. 销售开单有商品搜索浮层与"新建商品"内联表单；进货开单没有——进货时想建新品必须离开页面去商品页。
3. 退货开单不预填原单行，与"从原单进入"的语境不符。
4. 四个开单页的标题区与返回方式（P2-3 已统一过）目前一致，但**客户/厂家的选择器交互**在销售开单是"输入即匹配"，在进货开单也是搜索选择器，退货开单却是原生下拉——三种形态。

## 三、操作摩擦点（按用户真会撞上的顺序）

1. **「用库存 / 需进货 / 进价 / 多补」四个格子里，只有两个需要用户决定。** 「需进货」是系统算出来的（只读展示却占一格）、「用库存」默认就是"尽量用"（自动算）、真正要填的是「进价」（仅缺货时）和偶尔的「多补」。新手第一次开单会在这里犹豫：我该填哪个？填错会怎样？——实测这段是开单页里唯一需要思考的地方（见 T2，交互 13 次 vs T1 的 9 次）。
2. **"多补备货"是低频动作却常驻。** 多补在业务上确实存在（多进的货算库存、不算客户成本），但绝大多数单据不需要它，却与"进价"并排出现，容易被误填成"客户要多买"。
3. **退货开单不预填。** 从原单点「退货」，还得多一次"选哪个商品"（`return-form.tsx:44`），而原单明明已知。
4. **进货时建不了新品。** 进货开单没有内联新建商品，遇到没建档的货只能中断开单、去商品页、再回来（且回来后填好的行是否保留取决于是否离开页面——离开就丢）。
5. **销售开单里的 8 套快捷新建是双刃剑。** 好处是"不跳页就能建档"（这是它比进货开单顺手的地方）；代价是这页永远是最复杂、最不敢改的页面，且这 8 套逻辑与商品页/客户页的正式建档表单是**两套实现**（字段更少、校验更松），长期必然不一致。
6. **打印/改单衔接**：已开单要改，只能作废重开（业务上可接受，但详情页没有明确说这句话）。

## 四、合并 / 重组 / 升级建议

### O1（核心）把"货从哪来"从 4 个格子收敛成 1 个结论 + 1 个可选调整 ★

**现状**：用户面对 数量 / 库存 / 用库存 / 需进货 / 进价 / 多补 六个数字，其中三个是系统算的。

**建议**：一行只显示一个结论句，例如

> 数量 `666` 米 ｜ 货源：**库存 0 + 现场进货 666 @ ¥100**（点右箭头可展开调整）

- 默认方案由系统给出：有库存则优先用库存（`min(库存, 数量)`），不足部分标为现场进货并**预填最近进价**；库存为 0 则整行标为现场进货。
- 两个"改主意"的入口做成显式动作，而不是要用户理解字段含义：
  - 「改为全部现场进货」→ 把用库存置 0（对应现在的"用库存填 0"）；
  - 「只用库存（不足部分不进货）」在业务上不允许，故不提供（符合"禁止负库存"决议）。
- **多补备货**移到行尾的低频入口：「＋ 多补备货」展开后才出现数量框，并写明「多进的货计入库存，不计入本单成本」。

**收益**：T2 的交互从 ≈13 次降到 ≈10 次（与 T1 持平），并消除"我该填哪个"的犹豫。**依据**：渐进披露（默认不展示低频细节）+ 默认值即答案（系统能算的不要问用户）+ 减少选择（Hick 定律）。**影响**：`new-sale-form.tsx`。**量**：L。**风险**：中——必须保证分段成本与备货的落库逻辑完全不变（`actions.ts` 的 `LinePlan` 不动，只改表单呈现与传参方式），并回归"仅库存 / 仅现场进货 / 混合 / 带多补"四种组合。

### O2 四个开单页抽一套"单据编辑器"骨架

把"选交易对手 + 明细行（商品选择、数量、单价、备注）+ 合计 + 提交"抽成公共组件，四个页面各自只声明差异（列定义、是否允许现场进货、是否有退货上限）。**依据**：一致性 + 单一实现（现在改一个字段要改四处）。**量**：L。**风险**：中（先做 O1 再做，避免两件事同时改同一段代码）。

### O3 退货开单预填原单行

从 `/sale-orders/{id}` 点「退货」时，默认把该单**所有还有可退数量的行**带出来（数量留空或默认 0，单价按原售价），用户只需填数量。**依据**：识别优于回忆 + 语境继承（用户是从那张单来的）。**影响**：`sale-returns/new`、`purchase-returns/new` 的 2 个文件。**量**：S。**风险**：低（数量默认空，不会误提交）。

### O4 进货开单补上"新建商品"入口

把销售开单里的内联新建商品抽成公共组件，进货开单也接上；同时让"离开页面再回来"不丢已填内容（现在靠 React 状态，跳页必丢）。**量**：M。**风险**：低。

### O5 开单页的 8 套快捷新建逐步收敛

保留高频的「新建客户」「新建商品」（这两个是开单当下真的会遇到的）；分类/单位/组织/标签/厂家的新建移到各自的资料页（或保留但改为跳转 + 返回不丢单）。**依据**：一次只让用户做一个决定；开单页的职责是开单。**量**：M。**风险**：低—中（需要评估这几个快捷入口的实际使用频率，建议先在审计日志里看有没有写过这些实体）。

## 五、这个模块最该先做的 3 件事

1. **O3 退货预填**（半天，收益立即可感知，风险低）。
2. **O1 「货从哪来」收敛**（2~3 天，是开单体验的核心；先写一份"改前/改后操作步骤对照"再动手，且必须保住分段成本口径）。
3. **O4 进货开单补新建商品**（半天到 1 天，消除"进货时建不了新品"的断点）。
