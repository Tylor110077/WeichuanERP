## 0. 摘要

1. 主数据写路径**全部在 Server Actions 里**，共 8 个 action 模块（商品/客户/厂家/单位/分类/用户/个人资料/备份）+ 打印模板 + 工作台快捷入口，全部「薄壳」形态：`requireXxx()` → zod → 直写 `prisma`（无服务层、无事务封装的公共入口），因此计划里的「方案 C 抽服务层」需要逐 action 搬移（`src/app/(main)/products/actions.ts:103`、`customers/actions.ts:19` …）。
2. **路由重复是假象**：`/customer-groups`、`/customer-tags` 只是 `redirect("/customers")` 的死桩（`customer-groups/page.tsx:7`、`customer-tags/page.tsx:7`）；活的是 `/customers?tab=groups|tags` 与 `/customers/groups/new`、`/customers/tags/new`。**action 只有一份**，在 `customers/actions.ts`。CLI 命令面不必为「分组/标签」设计独立路由。
3. **软删 + 有条件硬删**：所有主数据都有 `status Int @default(1)`（1 启用 / 0 停用），每个实体另有真 `delete`，但都被「引用计数 = 0」拦住（商品/客户/厂家/单位/分类/组织/标签各有清单，见 §3.2）。**用户根本没有删除 action**，只有停用 + 重置密码。
4. **唯一性一半靠库、一半靠应用**：`users.username`、`units.name`、`customer_groups.name`、`customer_tags.name`、`products.code` 有 DB unique；`products.name`、`suppliers.name`、`customers.name`、`product_categories.name` **既不 unique 也无查重**（`saveSupplierAction` 连查重都没有，`suppliers/actions.ts:35`）。全库 `utf8mb4_unicode_ci` → 唯一索引与 `findFirst` 都大小写不敏感。
5. **拼音是 Prisma 客户端扩展自动写的**：`lib/prisma.ts:46-57` 的 `$allOperations` 钩子对 `customer/supplier/product/user` 的写入自动补 `search_pinyin`（`lib/prisma.ts:8-14`）。**CLI 若自建 `new PrismaClient()` 会静默写出 `NULL`，拼音搜索整片失效**——这是 CLI 必须遵守的硬约束。
6. **备份不是 mysqldump**：`src/lib/backup.ts` 应用自己 `SHOW TABLES` + `SELECT *` 导出带类型标记的 JSON → gzip（`backup.ts:86-92,178-211`），目录 `BACKUP_DIR ?? <cwd>/backups`（`backup.ts:95-99`），命名 `weichuan-backup-<ISO>.json.gz`，默认保留 14 份 / 每 24h（`backup.ts:109`）。另有一套**完全独立**的 shell 备份 `scripts/backup.sh`（mysqldump + GPG）→ 两套格式、两套保留策略，`/api/health` 只盯后者（`api/health/route.ts:14,27`）。
7. **恢复对 Agent 必须拒绝**：`restoreBackup` 逐表 `DELETE FROM` + 批量 INSERT、**无事务**、**不校验 schema 兼容**（`backup.ts:248-293`），只有前端一个勾选框把关（`backups/actions.ts:82`）。失败会留下半恢复的库。
8. **审计有一处静默失效**：`saveBackupConfigAction` 传 `entityId: "backup-config"`（`backups/actions.ts:64`），`writeAudit` 内部 `BigInt("backup-config")` 抛 `SyntaxError` 被 catch 吞掉（`audit.ts:40,46-49`）→ **备份配置变更从未入库**（已用 node 验证 BigInt 抛错）。
9. 只读侧没有任何主数据 JSON/导出出口（`reports/export` 只有 6 个报表 tab，`lib/reports.ts:323-330`），也**没有任何批量导入/排序能力**，CLI 的写与导出都得新建。
10. 现存一个真实数据损坏点：`/products/[id]` 编辑页不渲染「参考售价」（`products/[id]/page.tsx:51-76`），而 `parseProduct` 把它默认成 0（`products/actions.ts:18,36`）→ **从该页保存必把 `refSalePrice` 清零**；抽服务层时必须修掉。

## 1. action 全清单

约定：`guard` 列写真实判定（已回 `lib/auth/guards.ts` 核实）；`审计` 列是 `writeAudit(action / entityType)`。

`lib/auth/guards.ts` 只有三个 guard（计划 §4 提到的 `requireUser`/`requirePurchaseUser` **不存在**）：

| guard | 行 | 真实条件 |
|---|---|---|
| `requireAdmin` | `guards.ts:9-15` | `getCurrentUser()` 为 null **或** `role !== "admin"` → **抛** `Error("无权限执行此操作")` |
| `requireMasterDataWrite` | `guards.ts:18-25` | 未登录 → 抛 `"未登录"`；`role !== "admin"` → 抛 `"基础资料仅管理员可维护"`（**只有 admin**） |
| `requireLogin` | `guards.ts:28-32` | 仅要求已登录 |

> 注意两种风格并存：`requireAdmin()`/`requireMasterDataWrite()` 会**抛错**（调用方常写 `.catch(() => null)` 转成 `{ error }` 或再包一层中文提示），而快捷创建类 action 用 `.catch(() => null)` 后直接 `return { error }`。抽服务层时应统一为「返回 `{ok:false, code}`」，别继承抛错风格。

## 2. 路由重复问题（customer-groups vs customers/groups）

**结论：不是重复实现，是「旧 URL 死桩 + 新 URL 唯一实现」，action 只有一份。**

证据：

1. 旧路由是纯重定向，无 UI：
   - `src/app/(main)/customer-groups/page.tsx:7-8` → `redirect("/customers")`（注释 `3-6`：功能已并入客户管理页，保留旧路由避免书签失效）。
   - `src/app/(main)/customer-tags/page.tsx:7-8` → `redirect("/customers")`。
2. 活路由是**页签 + 独立新建页**：
   - 页签白名单 `TAB_KEYS = ["customers","groups","tags","profile"]`（`customers/page.tsx:29`）；组织管理渲染在 `tab === "groups"`（`customers/page.tsx:331-357`），标签在 `tab === "tags"`（`359-385`）。

## 3. 主数据规则：软删 / 唯一约束 / 拼音 / 校验

### 3.1 软删 vs 硬删

- 软删：每个主数据表都有 `status Int @default(1)`（`prisma/schema.prisma`：`Unit:170`、`ProductCategory:189`、`Product:215`、`Supplier:244`、`Customer:262`、`CustomerGroup:282`、`CustomerTag:294`、`User:91`）。翻转入口统一是 `toggle*StatusAction`（`products/actions.ts:179`、`customers/actions.ts:101,314,369`、`suppliers/actions.ts:70`、`units/actions.ts:59`、`categories/actions.ts:61`、`users/actions.ts:109`）。
- 硬删：**每个实体都有 `delete`，但被引用计数挡住**（这是「被单据引用过的能不能删」的答案——不能，返回中文错误让用户改用停用）：

| 实体 | 计数清单（表） | 代码行 |
|---|---|---|
| 商品 | `purchaseOrderItem`、`saleOrderItem`、`purchaseReturnItem`、`saleReturnItem`、`stockMovement` | `products/actions.ts:294-304` |
| 客户 | `saleOrder`、`saleReturn` | `customers/actions.ts:397-403` |
| 厂家 | `purchaseOrder`、`purchaseReturn` | `suppliers/actions.ts:99-105` |
| 单位 | `_count.products` | `units/actions.ts:87-92` |
| 分类 | `_count.products` | `categories/actions.ts:83-90` |
| 客户组织 | `_count.customers` | `customers/actions.ts:236-243` |
| 客户标签 | `_count.links`（= `customerTagLink`） | `customers/actions.ts:260-267` |
| 用户 | **无删除 action，也不存在删除入口** | `users/actions.ts` 全 140 行内只有 create/reset/toggle |

- 计数是**独立查询后再删**（无事务、无锁）→ 并发下理论上可在计数与删除之间插入引用（当前 UI 单管理员操作，风险低；CLI 高频写入时要注意）。
- `customer.delete` 会级联删 `customer_tag_links`（FK `ON DELETE CASCADE`，`prisma/migrations/20260902232721_customer_groups_tags/migration.sql:33`）；`customerGroup` 删除**不**级联（`ON DELETE SET NULL`，同文件 `:32`），所以组织删除前必须查 `_count.customers`，已实现。
- 商品删除**不检查库存**（`stockQty`/`stockAmount`），但库存只能由单据产生，单据被计数覆盖。
- 用户没有「改角色」和「删除」——见 §4。

### 3.3 拼音

**落库字段与自动维护：**

- 只有 4 张表有 `search_pinyin VARCHAR(255) NULL`：`customers`、`products`、`users`（迁移 `20260912210000_search_pinyin/migration.sql`）+ `suppliers`（`20260912220000_search_pinyin_supplier`）。**unit/category/group/tag 没有该列**，它们的拼音是渲染时用 `initials()` 现算（如 `customers/page.tsx:305-306`、`products/page.tsx:154-155` 附近的 rail 项）——CLI 想按拼音搜字典必须自己算。
- 自动生成器是 **Prisma Client 扩展**，不是 action：
  - `src/lib/prisma.ts:8-14` `SEARCH_PINYIN_FIELDS = { customer:["name"], supplier:["name","contact"], product:["name","code","manufacturer"], user:["displayName"] }`
  - `withSearchPinyin`（`:26-44`）：只有当本次 `data`（或 upsert 的 `create`/`update`）里含参与搜索的**字符串**字段时才重算，其余写入原样放行（`33-35`）。
  - `$allOperations` 钩子挂在扩展 client 上（`:48-57`），`prisma` 导出即扩展实例（`:73`）。
- **对 CLI 的直接结论**：只要 CLI 走 `import { prisma } from "@/lib/prisma"`（或它给的 `tx`，`prisma.ts:66-69` 的 `TxClient`），拼音就自动对；**若 CLI 自己 `new PrismaClient()`，`search_pinyin` 会静默为 NULL**，页面搜索与拼音匹配整片失效。反例见 `scripts/backfill-pinyin.ts:11-14`——它故意用裸 `PrismaClient` 并手工赋值 `searchPinyin`（`:21,30,39,47`）。
- 另一个已知不一致：更新商品时 `writeData` 只带 `name/manufacturer`（`products/actions.ts:113-121`，**不带 `code`**），扩展会以 `code=null` 重算 → 编辑过的商品 `search_pinyin` 失去编码段（创建时是含 `code` 的，`:273`、`prisma.ts:12`）。搜索仍能靠 `code contains` 命中（`products/page.tsx:101`），但拼音串本身变了。抽服务层时建议统一传入完整字段集。
- `py` 返回给前端的字段（`products/actions.ts:93,273`、`suppliers/actions.ts:139`）**不落库**，纯为客户端本地过滤（`search-select.tsx:12,126`、`entity-form.tsx:193`）。CLI 不需要它。

### 3.4 校验要点（跨模块共性）

- 全部用 zod v4 `safeParse` + 取 `issues[0].message`（如 `products/actions.ts:109`、`customers/actions.ts:32`）。
- **数字字段没有用 `src/lib/form-number.ts` 的三个函数**（AGENTS.md 要求用它）：商品用 `z.coerce.number()` + `z.preprocess`（`products/actions.ts:15-23`）——这是 `minStock` 留空→1 的既定行为，但也意味着 CLI 传 `""` 会变 0/NaN，服务层应显式区分。
- `id` 的判定统一是 `formData.get("id") ? Number(...) : null`（`products/actions.ts:105-106`、`customers/actions.ts:23-24`、`suppliers/actions.ts:39-40`、`units/actions.ts:21-22`、`categories/actions.ts:24-25`）→ **`id=0` 会被当成"新建"**（`0` falsy）。
- 归类字段的存在性：客户校验 `groupId`/`tagIds`（`customers/actions.ts:42-48`），商品**不校验** `unitId`/`categoryId` 是否存在（`saveProductAction`），只有 `createQuickProductAction` 校验单位启用（`237-238`）。CLI 写商品时应补上。
- `createQuickSupplierAction` 不校验其他字段（只有 name），`saveSupplierAction` 走 `supplierSchema`。

## 4. 用户与权限管理

### 4.1 角色枚举（实际取值）

- Schema：`enum UserRole { admin sales boss }`（`prisma/schema.prisma:22-26`），DB 列是 `ENUM('admin','sales','boss')`（`init/migration.sql` users 段）。
- zod 白名单：`z.enum(["admin","sales","boss"])`（`users/actions.ts:20`）。
- 中文标签：`ROLE_LABELS = { admin:"管理员", sales:"业务员", boss:"老板/财务" }`（`lib/auth/roles.ts:3-7`）。
- 新建页默认值 `sales`（`users/new/page.tsx:51`），文案解释能力（`52-56`）。
- 只有 `isAdmin(role)` 一个判定函数（`roles.ts:13-15`）。

### 4.2 密码策略

- `validatePasswordStrength`（`lib/auth/password.ts:37-41`）：`< 8` → `"密码至少 8 位"`；不含字母或数字 → `"密码需同时包含字母和数字"`。
- 三处入口都用它：建用户（`users/actions.ts:46-47`）、管理员重置（`:85-86`）、自己改密（`profile/actions.ts:15-18` 的 refine）。
- 哈希：`@node-rs/argon2` 默认 argon2id + 随机盐（`lib/auth/password.ts:1-14`）；`DUMMY_HASH` 用于防时序枚举（`:9-10,28-34`）。
- 重置密码会**删除该用户全部 session**（`users/actions.ts:96`）；自己改密只吊销其他会话（`profile/actions.ts:56` → `session.ts:95-104`）。

### 4.3 能做什么 / 不能做什么

| 能力 | 支持 | 证据 |
|---|---|---|
| 新建用户 | 是 | `users/actions.ts:30-74` |
| 重置密码 | 是 | `users/actions.ts:76-107` |
| 停用/启用（含踢下线） | 是，但不能停用自己 | `users/actions.ts:109-140`（`116`） |
| **修改角色** | **否，没有任何 action/UI/接口** | `users/actions.ts` 全体；`users/page.tsx` 只渲染账号/姓名/角色/状态/最近登录/创建时间列，操作为 `UserRowActions`（`user-row-actions.tsx:16-49` 只有「停用/启用」「重置密码」） |
| 删除用户 | **否** | 同上；库里只有 status 软删 |
| 改自己密码 | 是 | `profile/actions.ts:24-67` |
| 改自己的工作台快捷入口 | 是（服务端按角色过滤） | `dashboard/shortcut-actions.ts:18-62` |

> 结论：**角色变更目前只能在数据库里改**（或写迁移/seed）。CLI 若要支持 `master user role set`，属于新增能力，不是「复用现有逻辑」。

### 4.4 admin 之外谁能管用户

**没有人。** 所有 user action 都用 `requireAdmin()`（`users/actions.ts:34,80,113`），两个页面也硬判 `role !== "admin"` → `<NoPermission>`（`users/page.tsx:29-33`、`users/new/page.tsx:14-18`）。主数据同理：`requireMasterDataWrite()` 实际只放 admin（`guards.ts:18-25`），所以 `sales`/`boss` 对商品/客户/厂家/单位/分类/组织/标签**全部只读**（页面上的写按钮由 `isAdmin={user.role === "admin"}` 控制，如 `products/page.tsx:437,507,535,563`、`customers/page.tsx:307,351,379`）。

## 5. 备份与恢复的实现与风险

### 5.1 两套并存的备份系统（很容易混）

### 5.2 A 套（应用内）的实现细节

- **产物内容**：只含数据不含结构；明确排除 `_prisma_migrations`（`EXCLUDED_TABLES`，`backup.ts:24`；`listTables` 过滤 `:90`）。类型按原样保留（Decimal/BigInt/Date/Buffer/Json 带 `__t` 标记，`:39-83`）。
- **格式与包**：`{manifest:{format,createdAt,tables[],totalRows}, data:{表:行[]}}`（`BackupManifest` `:26-32`、`BackupPayload` `:34-37`）；`BACKUP_FORMAT = 1`，不匹配直接抛（`:21,219-221,229-231`；测试 `tests/backup.test.ts:25-34`）。
- **命名**：`backupFileName()` → `weichuan-backup-2026-09-12T10-00-00Z.json.gz`（`:143-147`，测试断言 `tests/backup.test.ts:36-41`）。同秒会重名覆盖（无后缀）。
- **保留策略**：`pruneBackups(keep)` 按**文件名倒序**（`listBackups` 排序 `:174`）保留前 `keep` 个（`:296-303`）；`keep` 从 `backup-config.json` 读，clamp 1..365；`intervalHours` clamp 1..720（`:120-121,130-131`）。
- **恢复算法**（`restoreBackup`，`:248-293`）：
  1. `listTables()` 取当前库表；只恢复「当前有 + 备份有」的交集（`:249-252`）。
  2. `SET FOREIGN_KEY_CHECKS = 0`（`:254`），收尾在 `finally` 里恢复为 1（`:273-275`）。
  3. 逐表 `DELETE FROM \`t\``（`:257`）→ 按 200 行一批 INSERT，**显式列出备份里的列**（`:258-272`）。
  4. 按 manifest 逐表 `COUNT(*)` 核对，任何一张不符就抛（`:277-291`）。
- **页面流**（`backups/actions.ts:80-116`）：`confirm==="yes"` → 上传 `.json.gz` → `parseBackupBuffer` → **先自动备份一份**（`:95`）→ 覆盖式恢复（`:96`）→ `createSession(admin.id)`（`:98`，因为 `sessions` 表已被清空）。

### 5.3 恢复的风险（为什么 RESTORE 对 Agent 必须设限）

1. **不可逆**：`restoreBackup` 对每张表先 `DELETE FROM`（`backup.ts:257`），当前数据全没。唯一退路是恢复前那一份自动备份（`backups/actions.ts:95`），而它**也受 `keep` 轮转**（`pruneBackups`，`backup.ts:296-303`）→ 连续恢复几次就可能把退路轮掉。
2. **没有事务**：`restoreBackup` 是裸 `$executeRawUnsafe` 循环，**没有 `$transaction`**（`:254-275`）；中途抛错（例如列不匹配的 SQL 错误）→ 部分表已清空、部分已写入，库处于半恢复状态，仅靠最后的行数核对报错，没有回滚。
3. **不校验 schema 兼容**：只校验 `format`（`:219-221`）与行数（`:277-291`）。`_prisma_migrations` 被排除在导出与恢复之外（`:24,249-252`）→ **恢复一个旧备份到新 schema 上没有任何保护**：期间新增的 NOT NULL 列会导致 INSERT 报错（列清单来自备份），被删掉的列会导致 unknown column。计划 §5.6 的「版本递增/审核」数据也会被直接抹掉。
4. **会话被清空**：`sessions` 表被 DELETE（`:257`）→ 全员下线；只有操作者一人被重建会话（`backups/actions.ts:98`）。对 CLI 而言，若 Agent 能触发恢复，它会把自己和其他所有人的 token/session 抹掉（若将来引入 `ApiToken` 表，该表同样会被覆盖）。
5. **门槛只有一个勾选框**：`confirm !== "yes"` 才拒绝（`backups/actions.ts:82-84`），没有 dry-run、没有「先展示将要覆盖的行数」、没有二次回执（对比计划 §6.3 要求的 `--confirm <单号>`）。
6. **上传即入口**：恢复唯一途径是把文件塞进 `formData`（`backups/actions.ts:86-93`），没有磁盘路径白名单；`parseBackupBuffer` 会 `gunzipSync` 整个 buffer（`backup.ts:227`）→ 恶意/超大包在内存里解（是否有体积上限取决于 Next Server Action body 限制，未核实，见 §8）。
7. **旁路**：`scripts/backup.ts --restore=<file>` 在**进程外**直接调 `restoreBackup`（`:37-51`），只要求 `--yes`（`:39-42`）——CLI 若 shell out 到它，就完全绕过了 action 的 `requireAdmin` 与审计（`:43-51` 无 `writeAudit`）。
8. **`deleteBackupAction` 的路径问题**：它把表单里的 `file` 原样交给 `deleteBackup`（`backups/actions.ts:40-42`），而 `deleteBackup` 接受**绝对路径**（`lib/backup.ts:315-318`：`path.isAbsolute(file) ? file : path.join(backupDir(), file)`）→ 理论上可删任意可写文件。同目录的下载路由做了正确示范：拒绝含 `/` 与 `..` 的参数（`backups/download/route.ts:12-14`）。CLI 的 `ops backup delete` 必须照抄这个白名单，或改为只接受 `basename` 且必须命中 `listBackups()`。
9. **`scripts/backup-roundtrip.ts` 是破坏性演练**：它 `dumpAll()` → `restoreBackup(before)`（`:24-29`）**直接覆盖当前库**（注释 `:5-6` 承认会覆盖，只是"恢复的是刚导出的同一份"）。**绝不能**做成常规 CLI 命令或定时任务。

### 5.4 `backups/download/route.ts` 的鉴权

- `GET`：`getCurrentUser()` + `user.role !== "admin"` → **403**（`route.ts:7-10`）；`file` 缺失或含 `/`、`..` → 400（`:12-14`）；读失败 → 404（`:23-25`）；`Content-Disposition: attachment`（`:20`）。
- **没有审计**：全文件无 `writeAudit` → 谁下载过整库无人知晓（对照 §6）。

### 5.5 `ops backup create|list|download|restore` 的暴露建议

| 子命令 | 建议 | 依据 |
|---|---|---|
| `ops backup list` | **可给 Agent** | 纯只读 `listBackups()`（`backup.ts:157-175`），可解析 manifest 行数 |
| `ops backup create` | **可给**（需 `--yes`），复用 `createBackup()+pruneBackups(cfg.keep)` 并写审计 | `backups/actions.ts:20-36` 已证实这条路径有审计；注意 `pruneBackups` 的删除**不审计**（§6.2） |
| `ops backup download` | **拒绝给 Agent token** | 产物是**全库明文 dump**（含 `users.password_hash`、`sessions.token_hash`、全部单据）且无审计（`route.ts` 无 `writeAudit`）。给 admin 人的 CLI 可以，Agent 不行 |
| `ops backup restore` | **必须拒绝（不可逆）** | §5.3 的 1/2/3/4/5：逐表 DELETE、无事务、无 schema 校验、清空会话、仅一个勾选框。应设计成「仅本地人工 + 离线路径 + 恢复前强制 `createBackup()` + 打印 dry-run 摘要 + 显式 `--confirm <文件名> --i-understand-irreversible`」，或干脆只允许运维在服务器上跑 `scripts/restore.sh`（演练库优先，`restore.sh:4,20-30`） |
| `ops backup verify` | 另设只读校验（解析 manifest + 行数），**不要**调 `backup-roundtrip.ts` | §5.3 第 9 点 |
| `ops backup delete` | 可给 admin 人，Agent 需 `--confirm <文件名>`；实现必须加 `basename`/白名单校验 | §5.3 第 8 点、`download/route.ts:12-14` |

### 6.3 推论

- 「哪些写操作没有审计」不只是「少写一行」，还有**静默丢弃**这一类（#1、#7）。抽服务层时应把 `AuditParams.entityId` 收窄为 `number | bigint | null`（或字符串走另一个字段），并让审计失败可观测。
- 计划 §9.5（`agent-cli-plan.md:225`）的答案：**主数据/用户/备份 action 基本都写了审计；缺口在备份配置、轮转删除、下载、脚本路径。**
