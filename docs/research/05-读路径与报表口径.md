# 05 · 读路径与报表口径（第 5 轨调查）

> 只读调查。基线：工作区当前 HEAD `33d0714`（`git log --oneline -1`）。
> 所有结论给 `文件:行号`，路径相对仓库根。凡未从代码确认的，一律进第 8 节，不猜。
> 本轨只覆盖**读路径**（列表 / 详情 / 报表 / 导出 / 草稿）；写路径（冲减、记账、主数据写入）

## 0. 摘要

1. **没有任何 JSON API**。全站机器可读出口只有两个：`/reports/export`（exceljs）与 `/api/health`
   （`find src/app -name route.ts` 仅得三处：`reports/export/route.ts`、`api/health/route.ts`、
   `(main)/backups/download/route.ts`）。CLI 的 `query *` 必须直连服务层或新加端点。
2. **时间范围默认值不统一**，这是对数最大的坑：单据类列表（售卖/进货/库存流水/财务流水/应收应付/
   审计/登录/供应商对账/报表中心）默认**本月 1 日 ~ 今天**；而 `/inventory`（只看进货时间）、
   `/price-analysis`、客户画像（`buildCustomerProfile`）默认**全部时间**；`/customers/[id]` 显示"全部时间"。
3. **状态过滤默认值不统一**：售卖单/进货单/退货单列表**默认包含作废单**（`status` 缺省即不过滤，
   `sale-orders/page.tsx:65`、`purchase-orders/page.tsx:65`）；应收应付、报表、销售分析、客户画像
   一律 `.status="confirmed"` 或 `not: "voided"`；财务流水默认 `status="confirmed"`，作废要显式选。
4. **库存三列是 Product 上的冗余列**（`prisma/schema.prisma:212-214`），由写入事务维护，
   读路径**不做现场聚合**；流水表只用来算"最近进价/最近进货时间/批次台账"。
5. **"展开全部"与状态过滤无关**：`git log` 里 `abb95d9` 那条说的是列表行展开商品明细改用
   `useTransition` 防卡顿（`sale-orders/order-table.tsx:62,75`），不是"展开全部状态"。
6. **"应收总额"存在两个不同口径**：工作台 `dashboard/page.tsx:41` 的 SQL 少了 `GREATEST(...,0)`，
   与 `/receivables-payables` `page.tsx:95` 的 `SUM(GREATEST(...,0))` 在有超付/多退单据时会不相等。
7. **`/inventory` 有两个"只筛当前页"的口径**：`warnOnly` 过滤与"预警商品 N 个"计数都只用当前页
   50 条（`inventory/page.tsx:171-184`），不是全量；CLI 想给全量数字必须自己算并说明差异。
8. **`price-analysis.ts` 的 `take: 3000` 取的是最旧的 3000 笔**（`orderBy asc` + `take`，
   `price-analysis.ts:102-103`），不是最近 3000 笔；"图表仅画最近 300 笔"的文案与实际数据不符。
9. **草稿只存浏览器 localStorage**（`lib/form-draft.ts:13,18,51,75,88`），`/drafts` 是
   client 组件读本地存储（`drafts/page.tsx:17`、`drafts/draft-box.tsx:34-38`）。
   **服务端/CLI 完全看不到草稿** → CLI 的 `query drafts` 不可实现，见第 5 节。
10. `/reports/export` 鉴权最弱：登录 + `role !== "sales"` 即可导出**全量**（`unlimited:true`），
    且**不写审计**（`reports/export/route.ts:9-11,23`，`grep writeAudit` 无命中）。

## 2. 逐页口径明细

### 2.1 `/sale-orders`（售卖单列表）

- **参数解析**：`page`（`Math.max(1, Number||1)`，`:28`）；`status`（原样透传，`:29`）；
  `customerId`（Number，`:30`）；`q`（trim，`:31`）；`settle` 只接受 `settled|unsettled`，其余当未填（`:32-33`）；
  `star === "1"`（`:36`）；`mode === "item"` 否则 `order`（`:38`）；`from/to` 走本地 `dateRange`（`:362-371`）。
- **数据来源**：`sale_orders` join `customers`/`users`，`include` 退货(`confirmed`)与全部商品行
  （`:83-104`）；`count` 与 `findMany` 共用同一 `where`（`:84-85`）。
- **状态过滤**：`...(status ? { status } : {})`（`:65`）→ **缺省不过滤，作废单照常出现在列表首屏**。
  下拉只有 `全部状态 / confirmed 已开单 / voided 已作废`（`:225-229`）。
- **款项结清筛选**（`:41-62`）是**原生 SQL**，两个方向各一条：
  `settled`：`so.status='confirmed' AND (total_amount - received_amount - COALESCE(SUM(confirmed 退货),0)) <= 0`；
  `unsettled`：同式 `> 0`。结果作为 `id IN (...)` 注入 `where`（`:77`）。
  注意：**退货只算 `status='confirmed'`**（`sale_returns` 子查询 `:47`）；`received_amount` 用冗余列。
- **列表行内数字**（`:131-158`）：`returned = Σ confirmed 退货 totalAmount`（`:132`）；
  `needsReceipt = status!=="voided" && total - received - returned > 0`（`:145`）。
  「款项」列在 client 组件里再用一次同式 `outstanding = total - received - returned`
  （`order-table.tsx:108,143-147`）——**前后端同一公式，目前一致**。
- **`mode=item`（只看商品）**：`saleOrderItem` 复用同一 `where` 包成 `{ saleOrder: where }`（`:109`），
  skip/take 同样 20（`:117-118`），另加 `aggregate` 汇总 `quantity/amount`（`:125`），
  文案"共 N 条商品行・总数量・合计 ¥"（`:188-193`）。**注意合计只覆盖全部筛选结果，而表格只显示当页**。
- 缓存：无 `unstable_cache` / `revalidate`；分页上限：无（`total` 全量 count）。

### 2.2 `/purchase-orders`（进货单列表）

与 2.1 同构。差异点：
- 状态取值 `pending|received|voided`（`:65,164-169`），缺省同样不过滤。
- `settle` 的 SQL 用 `po.status IN ('pending','received')`（`:49,59`），即**作废进货单不参与结清判定**。
- 行内 `outstanding = total - paid - returned`，`needsPayment = status!=="voided" && outstanding>0`（`:136,150`）。
- **item 模式有一处列重复**：表头出现两个「厂家」列（`:268` 与 `:271`），其中一个是厂家名、
  一个是商品 `manufacturer`；`colSpan={11}`（`:282`）与实际 11 列吻合，属展示层瑕疵，不影响数字。

### 2.3 `/sale-returns` 与 `/purchase-returns`（退货单列表）

- **只有 `page` 一个参数**（`sale-returns/page.tsx:19`、`purchase-returns/page.tsx:19`）：
  **没有时间范围、没有状态、没有关键词、没有分页夹紧之外的处理**。
- `total = prisma.saleReturn.count()`（`:25`）/ `purchaseReturn.count()`（`:26`）——**无 where，全表计数，
  含作废单**。这是全站唯一"无任何过滤"的计数。
- 每页 50（`:14`），`orderBy createdAt desc`，页码被夹进 `[1,totalPages]`（`:28`）。
- 行内金额 = `totalAmount`，表头文案「冲减应收」/「冲减应付」（`sale-returns/page.tsx:68`、
  `purchase-returns/page.tsx:68`）；状态标签 `confirmed 已开单 / voided 已作废`（`:11,103`）。
- 页面里那句注释"列表本身取最近 200 张"（`sale-returns/page.tsx:54`）**与实现不符**——实现是分页 50/页，
  取全量，注释是历史残留。

### 2.4 `/inventory`（库存查询）

- **数据来源**：全部来自 `products` 表自身列（`:98-110`），**没有任何现场聚合**。
  数量=`stock_qty`、金额=`stock_amount`、均价=`avg_cost`（`:316-317,495-501`）。
- **低库存 / 零库存判定**（`:175-177`）：
  `warning = p.status === 1 && minStock > 0 && qty < minStock`（**停用商品不计预警**）；
  `negative = qty < 0`。**没有"零库存"概念**，只有 `qty < minStock` 与 `qty < 0`。
- **`warnOnly` 是在分页之后过滤**（`:171-179` 先 `findMany` 取 50 条，再 `.filter(r => !warnOnly || r.warning)`）
  → 勾选"只看库存预警"时，**当前页没有预警商品就会显示空表**，即使后面页有。
- **"预警商品 N 个"也是当前页计数**：`warningCount = products.filter(...)`（`:181-184`），
  `products` 就是当页 50 条。**这是全站最容易和 CLI 对不上的数字之一**。
- 筛选（`:72-97`，全部下推 DB）：`q` 匹配 `name|code|search_pinyin contains lower(q)`；
  `category=<id>|none`；`manufacturer=<名>|none`（`none` → `manufacturer = ""`）；
  `from/to` → 存在至少一条 `bizType='purchase_in'` 且 `createdAt` 落在区间的流水（`:85-96`）。
- **"最近进价"与"最近进货"**（`:115-135`）：取所有**非作废进货单**的单号（`:115-118`），
  再取这些单号的 `purchase_in` 流水按 `createdAt desc` 全量拉回（无 take），
  每个商品取**第一条**（即最新）的 `unitCost` 与 `createdAt`。
- **批次台账**（`:147-169`）：`batch` 参数必须**命中当前页商品**才渲染（`:148-149` 从 `products` 里找）；
  数据是 `purchaseOrderItem where productId AND purchaseOrder.status != 'voided'`，`take:60`，
  `orderBy purchaseOrder.createdAt desc`；页脚累计进货量/加权均价/金额（`:167-169,477-487`）。
  **`take:60` + `quantity` 求和 → 批次台账的"累计进货/加权均价"是最近 60 条的，不是全量。**

### 2.5 `/stock-movements`（库存流水）

- **流水类型枚举的全部取值与中文标签**（`stock-movements/page.tsx:22-28`，枚举定义
  `prisma/schema.prisma:71-77`）：

  | bizType | 中文标签 | 徽标色 | 备注 |
  |---|---|---|---|
  | `purchase_in` | 进货入库 | green | 详情页可跳 `/purchase-orders`（`:18`） |
  | `sale_out` | 销售出库 | blue | 可跳 `/sale-orders`（`:19`） |
  | `purchase_return_out` | 进货退货 | orange | 不跳详情（`:17-20` 只定义两条） |
  | `sale_return_in` | 销售退货 | teal | 同上 |
  | `void_reverse` | 作废冲回 | gray | 同上 |

- **筛选维度**：`productId`、`bizType`、`from/to`（本月默认，`:275-284`）。**没有操作人/单据号筛选**。
- **每行数字**：`changeQty/beforeQty/afterQty/unitCost` 全部直接读流水列（`:212-218`），无重算。
- 关联信息（`:69-116`）是增量查询：按本页 `bizOrderNo` 反查四种单据，得到详情链接与往来对象
  （退货顺着原单找客户/厂家，`:100-107`），以及操作人显示名（`:109-116`）。
- 权限：拒 sales（`:37-41`）。

### 2.6 `/receivables-payables`（应收应付）

- **视图**：`view=payable` 否则 `receivable`（`:42`）；`counterId` 在应收侧是 `customerId`、
  应付侧是 `supplierId`（`:53,70`）。
- **两条口径并存，且必须用 SQL 的才是全量**：
  - **单据表**：`findMany ... take: 200`（`:67,84`），再在内存里过滤出 `total-paid-returned > 0`
    （`:127-132`），然后按 20/页切片（`:135`）。**表格最多覆盖最近 200 张单**，
    且超过时提示"下表仅显示最近 N 张（合计已含全部）"（`:386-390`）。
    注意 `pageCount = ceil(unpaidOrders.length/20)`（`:134`）→ **翻页只在 ≤200 张范围内有效**。
  - **合计卡（权威口径）**：`$queryRaw` 按对象分组（`:90-120`）：
    应收 `SUM(GREATEST(so.total_amount - so.received_amount - COALESCE(sr.total,0), 0)) AS total`，
    `unsettled = COUNT(差额 > 0)`；`WHERE so.status='confirmed' AND created_at BETWEEN`。
    应付同式，`WHERE po.status IN ('pending','received')`。
    **逐单 `GREATEST(...,0)`：超收/超退的单不会去抵减别的单**。
  - `totalOutstanding = Σ counterRows.total`（`:122`），`unsettledCount = Σ counterRows.unsettled`（`:123`）。
- 商品视角（`mode=item`）：把 `unpaidOrders`（≤200 单）的商品行平铺（`:174-189`），
  20/页，并给出 `flatItems.length`、总数量、合计金额（`:186-189,287-291`）——**同样受 200 单上限约束**。
- 默认区间判定：`isDefaultRange = !params.from && !params.to`（`:196`），文案"默认本月 1 号至今"（`:411`）。

### 2.7 `/payments`（财务流水）

- **数据就是 `payments` 表**，没有派生：`findMany` + `groupBy direction`（`:90-100`）。
- **状态默认**：`params.status === "all" ? undefined : params.status === "voided" ? "voided" : "confirmed"`
  （`:41`）→ **缺省只算已登记（`confirmed`）**，作废要选"全部（含作废）"或"只看已作废"。
- **合计**：`groupBy({ by: ["direction"], where: baseWhere, _sum: { amount } })`（`:99`），
  `baseWhere` = 状态 + 关键词 + `createdAt` 区间，**不含 `direction` 过滤**（`:83-88`）：
  **合计永远同时算收与付**，即使列表选了"只看收款"。`received/paid/net`（`:122-124`）。
- **关键词** `q`（`:46-80`）：先查最多 500 张售卖单/进货单（`:50-70`，`take:500`），
  再拼 `OR: orderNo contains | remark contains | (orderType='sale' && orderId in sales) |
  (orderType='purchase' && orderId in purchases)`。**命中集受 500 上限约束**：单号/客户名超过 500 张时
  会漏（超过 500 的匹配单里的收付款搜不到）。
- 区间用 `lib/reports.ts:28-39` 的 `dateRange`（本月默认，`:43`）。
- 关联单据/对方（`:103-120`）是按本页 `payments` 反查，`orderNo` 缺失显示 `—`（`:236`）。

### 2.8 `/sales-analysis`（销售分析）

## 3. 报表函数逐个口径

### 3.1 `src/lib/reports.ts`

**共用 `dateRange(from, to)`**（`:28-39`）：非 `yyyy-mm-dd` 或缺省 → `gte = 本月 1 日 00:00`、
`lte = 现在`（注意 `to` 缺省时 `lte` 是"当前时刻"，不是 23:59:59.999；`to` 给出时才是当日 23:59:59.999）。
**`lte` 语义随 `to` 是否给出而变**，CLI 复刻时必须照抄。

| 函数 | 输入 | 过滤条件 | 返回字段 | file:line |
|---|---|---|---|---|
| `inventoryReport()` | 无 | **无任何过滤**：全部 `products`（含停用） | `code,name,category,unit,qty=stock_qty,amount=stock_amount,avg=avg_cost,lastPrice,minStock,status` | `:41-89` |
| `summaryReport(from,to)` | `from,to` | 采购：`status='received'` 且 **`receivedAt ∈ [gte,lte]`**；销售：`status='confirmed'` 且 **`createdAt ∈ [gte,lte]`** | 4 行指标：采购额、销售额、成本、毛利润 | `:91-124` |
| `payablesReport(from,to,limit=300)` | +`limit`（0=不限） | `purchase_orders` `status != 'voided'` 且 `createdAt ∈ 区间`；`returns` 只取 `confirmed` | `supplier,orderNo,status,total,paid,returned,unpaid` | `:126-167` |
| `receivablesReport(from,to,limit=300)` | 同上 | `sale_orders` `status != 'voided'` 且 `createdAt ∈ 区间` | `customer,orderNo,status,total,received,returned,unreceived` | `:169-212` |
| `salesRankReport(from,to,limit=300)` | 同上 | `saleOrderItem` where `saleOrder.status='confirmed'` 且 `createdAt ∈ 区间`，`groupBy productId _sum(quantity,amount,costAmount)` | `code,name,unit,qty,amount,cost,profit` | `:214-269` |
| `operatorPerfReport(from,to)` | `from,to` | `sale_orders status='confirmed'` 且 `createdAt ∈ 区间`，**含 items** | `name,role,count,amount,cost,profit` | `:271-307` |
| `buildReport(tab,from,to,{unlimited})` | — | `limit = unlimited ? 0 : 300`；**只把 limit 传给 payables/receivables/sales-rank** | — | `:334-357` |

**毛利/利润的确切算法（本文件内一致）**：
- 销售额 = `sale_orders.total_amount` 之和（**不是** `sale_order_items.amount` 之和）；
- 成本 = `sale_order_items.cost_amount` 之和（**开单时的成本快照**，不是 `products.avg_cost`）；
- 毛利 = 销售额 − 成本；毛利率 = 毛利 / 销售额 × 100（分母 0 → 0）。
- 出现处：`summaryReport`（`:107-121`）、`salesRankReport`（`:264`）、`operatorPerfReport`（`:291,305`）。

**退货是否冲减（关键差异）**：
- `summaryReport` 的销售额/成本**完全不冲减退货**——只看 `sale_orders` 与 `sale_order_items`，
  退货表 `sale_returns`/`sale_return_items` 一次都没读（`:93-106`）。
  **所以报表中心的"销售额/毛利"是毛额，不扣退货。** 与单据详情的"本单毛利"（同样不扣退货）一致，
  但与应收口径（扣 `confirmed` 退货）不一致。
- `payablesReport`/`receivablesReport` 的应付/应收则**逐单冲减 `confirmed` 退货**，
  `unpaid = Math.max(0, total - paid - returned)`（`:163,208`）。

**`status` 列的标签映射**（`:159,204`）：应付 `received→已入库 / pending→待收货 / 其他→作废`；
应收 `confirmed→已开单 / 其他→作废`。因为 where 已排除 `voided`，"作废"这一支是死代码。

**截断**：`MAX_REPORT_ROWS = 300`（`:321`）；`capped` 只在 `limit > 0 && 行数 >= limit` 时置位
（`:143,188,245`）→ **`inventoryReport` / `summaryReport` / `operatorPerfReport` 永不 `capped`**，
`inventoryReport` 会把全部商品一次性返回。

`REPORT_TABS`（`:323-330`）：`inventory 库存查询 / summary 进销存汇总 / payables 应付明细 /
receivables 应收明细 / sales-rank 单品销售排行 / operator-perf 操作员业绩`。

### 3.2 `src/lib/price-analysis.ts`（`buildPriceAnalysis(productId, gte, lte)`，`:72-267`）

- **输入**：`productId`（商品存在性校验，不存在返回 `null`，`:77-86`）、`gte/lte`（由调用方给）。
- **数据**：`saleOrderItem where productId AND saleOrder.status='confirmed' AND saleOrder.createdAt ∈ [gte,lte]`，
  `orderBy saleOrder.createdAt asc`，**`take: 3000`**（`:88-104`）。
  ⚠️ `asc` + `take` = 取**最旧的 3000 笔**，不是最近 3000 笔（页面文案"仅画最近 300 笔"，`:136`）。
- **单行口径**（`:106-127`）：`unitPrice = Number(it.unitPrice)`（原样）；
  `unitCost = costAmount / qty`（qty>0，否则 0）；`profit = amount − costAmount`；
  `margin = (amount−costAmount)/amount*100`（amount>0，否则 0）。**单位成本用成本快照，不用 `avg_cost`。**
- **估价行的处理**：**没有任何 `estimated` 相关分支**——估价行的 `costAmount` 是 0
  （第 1 轨：`sale-orders/actions.ts` 对估价行不写成本快照），所以它会以
  `unitCost = 0`、`margin = 100%` 的形式进入所有汇总与图形（`:109-111,125`）。
  **`price-analysis.ts` 不会排除估价行**，`/price-analysis` 的毛利/毛利率会被估价行拉高。
  （`summaryReport`/`salesRankReport` 同理不排除，因为成本 0 已经进了 `cost_amount`。）
- **按天**（`byDay`，`:130-183`）：按 `dayTs`（当日零点的 epoch ms，**由 `created.getFullYear()/getMonth()/getDate()`
  计算，即进程本地时区**，`:115`）分组；累计 `saleCount`（按**商品行数**，不是单据数，`:150,160`）、
  `qty/amount/cost`；`minCost/maxCost` 取行成本单价的极值；`avgCost = Σcost / Σqty`（数量加权，`:179`）；
  `highest/lowest` 取当日 `unitPrice` 最高/最低的**那一行**（`:166-167`），按 `byDay.dayTs asc` 排序。
- **按客户**（`byCustomer`，`:186-237`）：`orderCount = Set(orderNo).size`（**按单号去重**，`:190,208,224`）；
  `avgPrice = Σamount / Σqty`、`avgCost = Σcost / Σqty`；
  `minPrice/maxPrice` 只在 `unitPrice > 0` 时参与（`:212-215`）；`lastDate` 取**字符串比较**最大的
  `toLocaleDateString("zh-CN")`（`:216`，即 `yyyy/M/d`，字符串序在该格式下与日期序一致）；
  排序 `b.amount - a.amount`（`:237`）。
- **totals**（`:239-253`）：`qty/amount/cost` 全量求和（受 3000 上限影响）；
  `avgPrice/avgCost/margin` 同上式；`minPrice/maxPrice` 取全部 `unitPrice>0` 的极值（`:242,251-252`）。

### 3.3 `src/lib/customer-profile.ts`

- **`orderFilter(from,to,productKeyword)`**（`:24-42`）：`status: "confirmed"` +
  `createdAt ∈ dateRange(from,to)` + 可选 `items.some.product OR(name|code contains kw)`。
- **`dateRange`（本文件私有，`:151-157`）与 `reports.ts` 的同名函数语义不同**：
  只填一头也算（`from` 缺省 = `2000-01-01`，`to` 缺省 = `2100-12-31 23:59:59.999`），
  **缺省 = 全部时间**。`reports.ts` 的同名函数缺省 = 本月。**这是同名不同义的第二个坑**。
- **`buildCustomerProfile(from,to,productKeyword)`**（`:44-116`）四条并行查询：
  1. `customer.findMany` 全量客户（含 `group` 与 `tagLinks`，`:48-54`）——**客户列表不受期间影响**；
  2. `saleOrder.groupBy(["customerId"]) _count._all, _sum.totalAmount where where`（`:56-61`）；
  3. `saleOrderItem.groupBy(["saleOrderId"]) _sum.costAmount where {saleOrder: where}`（`:64-68`）；
  4. `saleOrder.findMany where where select{id,customerId}` 作为"单→客"映射（`:70`）。
- 合并（`:79-95`）：先按 (2) 建 `agg`（cost 置 0），再把 (3) 的每单成本和经 (4) 归到客户头上累加。
  **`profit = sales − cost`；`margin = profit/sales*100`（sales>0）**（`:100-110`）。
  排序 `b.profit - a.profit`（`:113`）。**只返回有成交的客户**（`agg` 的 key 来自 groupBy）。
- **`getCustomerOrderPage(customerId,from,to,kw,page,pageSize)`**（`:122-145`）：
  `where = {...orderFilter(...), customerId}`；`count` → `totalPages` → 页码夹紧 → `skip/take`
  → `orderBy [{createdAt desc},{id desc}]`。返回 `{rows,total,page,totalPages}`，`rows` 含完整 `items`。

### 3.7 `src/lib/stock-cost.ts`（读路径只用于理解冗余列怎么来的）

- `applyStockChange`（`:21-53`）四分支：变动后为负 → 保持原金额与均价（`:30-34`）；
  恰好清零 → 金额与均价归 0（`:36-39`）；原为负 → 负数部分按原均价回补、剩余按新单价（`:41-48`）；

- 金额 `round2`、均价 `round4`、数量 `roundQty` 保留 3 位（`:27-28,56-58`）。
- **推论**：`products.avg_cost` 是"每次变动后 round4"的**连乘结果**，不是 `stock_amount/stock_qty` 的精确商。
  库存页的"均价"列直接显示 `avg_cost`（`inventory/page.tsx:317,501`），
  **CLI 若用 `stock_amount / stock_qty` 反算会得到第 4 位小数不一致的结果**。

## 5. 草稿与"只在客户端存在的数据"

**结论：开单草稿只存浏览器 localStorage，服务端与 CLI 完全不可见。**

- 存储键：`wc-order-drafts:<userId>`（`lib/form-draft.ts:13,51-53`）；旧键 `wc-order-draft:<scope>:<userId>`
  会一次性迁移（`:15,96-120`）。

  **`summary` 是为了让列表页不必懂单据结构**（`:32-41`）——也就是说 `amount` 这个数字是**开单页在保存时
  自己算好塞进去的**，不在服务端。
- `/drafts` 页面：服务端组件只做登录校验与文案（`drafts/page.tsx:5-19`，其中 `:14-15` 明确写
  "存在这台电脑的浏览器里，只有你自己看得到"），数据全在 client 组件 `DraftBox` 里用
  `useSyncExternalStore` + `getDraftsSnapshot` 读本地（`draft-box.tsx:34-38`），
  服务端快照固定为空数组（`form-draft.ts:206-209`）。**因此 `/drafts` 的 HTML 里没有任何草稿数据。**
- 每类 **8 份/页** 的前端分页（`draft-box.tsx:24,69-71`），删除要按两下（`:39-40,101-130`）。
- 同类"只在客户端"的数据（`grep -rln localStorage src/` 全部 4 个命中）：
  `lib/form-draft.ts`（草稿）、`components/sidebar-nav.tsx` + `lib/sidebar.ts`（侧边栏折叠状态）、
  `sale-orders/[id]/print/print-editor.tsx`（打印模板编辑器的本地状态）。

**对 CLI 的直接影响**：
- `wc-cli query drafts`（`docs/agent-cli-plan.md:159`）**在现有架构下不可实现**：
  草稿既不在数据库，也不在任何服务端可读位置，且带 `userId` 隔离、7 天过期、每类 20 份上限。

  原始取舍（`form-draft.ts:9-10` 明确写了这个取舍）。
- 「待办草稿」这一类因此应从 Phase 2 的"能查一切"里**显式剔除或改写为"不可查（仅浏览器）"**。
- 与之相对，`/pending-estimates`（估价待补）是**真正的服务端待办**，可作为 CLI 待办类命令的锚点，
  但注意它当前因 `estimated` 未落库而恒空（第 2.12 节、第 1 轨 P0）。

### 6.2 怎么取参考值（可操作的取数方式）

- 页面数字一律**从 HTML 里读**（都是服务端渲染的纯文本，无需执行 JS）：
  「共 N 张/条/个/笔」在筛选表单的 `<span>` 里；报表数字在 `<td>` 里带 `¥` 前缀；
  小数字用 `.toFixed(2)`/`.toFixed(3)`/`.toFixed(4)`（均价 4 位、数量 3 位、金额 2 位）。
- 需要精确参考值时，**不要用页面的格式化结果**，直接用 `buildReport` / `buildCustomerProfile` /
  `buildPriceAnalysis` / 页面文件里那段 `$queryRaw` 在 `prisma.$queryRaw` 里跑一遍——本报告已把每段 SQL 的
  位置列在第 2 节。
- 时间基准：**所有"本月/今日/本周"都是进程本地时区的自然日**。生产 `TZ=Asia/Shanghai`
  （`docker-compose.yml:41`），开发机跟随系统。**CLI 与页面必须在同一个 `TZ` 下跑**，否则
  `本月`/`今日` 边界会整体偏移 8 小时，这是最容易"差一点"的地方。
  只有 `/sales-analysis` 的按日分组显式写成 `+08:00`（`sales-analysis/page.tsx:55,64`），
  它的"日"永远按北京时间，但它的**区间**仍按进程本地时区——**两者不同源，跨月/跨日时可能不一致**。

### 6.3 高风险的"算不一致"点（对数时优先查这些）

1. **工作台 vs 应收应付**（`GREATEST` 缺失）：`dashboard/page.tsx:41` vs
   `receivables-payables/page.tsx:95`。有超收/超退单据时必然不等。
2. **`/inventory` 的 `warnOnly` 与预警计数**是页内口径（`inventory/page.tsx:171-184`）。

   `unsettledCount`（全量）与 `unpaidOrders.length`（≤200）的差值只体现在一句提示上（`:386-390`）。
4. **`/supplier-statement` 的合计受 `take:500` 限制**（`:76`）；且它的 `paid` 来自 `payments` 现场求和
   （`:96`），`reports.ts:161` 的 `paid` 来自冗余列 `paid_amount`。
5. **`price-analysis.ts` 的 `take:3000` 取最旧**（`:102-103`）+ 页面文案写"最近"（`price-analysis/page.tsx:136`）。
6. **估价行遍布所有口径**：成本 0 会同时抬高 `/price-analysis` 毛利率、`/sales-analysis` 利润、
   `/reports` 毛利、客户画像毛利。**没有任何报表排除 `estimated`**（`grep estimated` 在 `src/lib/` 下只命中
   `customer-profile.ts` 以外的 0 处——实际上 `src/lib/` 里没有任何 `estimated` 引用）。
   唯一提示在单据详情（`sale-orders/[id]/page.tsx:149-154`）。
7. **`dateRange` 三份同名不同义**：`lib/reports.ts:28-39`（缺省本月）、`lib/customer-profile.ts:151-157`
   （缺省全部时间）、各页面自带的 7 个副本（`sale-orders/page.tsx:362`、`purchase-orders/page.tsx:385`、
   `inventory` 用 inline 解析、`stock-movements/page.tsx:275`、`receivables-payables/page.tsx:449`、
   `supplier-statement/page.tsx:244`、`audit-logs/page.tsx:185`、`login-logs/page.tsx:137`）。
   8 份实现里，只有 `reports.ts` 的 `lte` 在 `to` 缺省时是"当前时刻"而非 23:59:59.999。
8. **`/payments` 关键词的 `take:500`**（`:58,69`）：超过 500 张匹配单时会漏收付款。
9. **`/customers/[id]` 的高亮用 JS `includes`**（`:77-78`），SQL 过滤用 MySQL `contains`（大小写不敏感）。
10. **`/sales-analysis` 单边日期被忽略**（`resolveRange` 要求 `from && to`，`:287`）。
11. **页面层格式化**：报表页的 `isMoney` 白名单 + `toFixed(3).replace(/\.?0+$/,"")`
    （`reports/page.tsx:120-129`）；入库/出库数量 `toFixed(3)`；均价 `toFixed(4)`。
    CLI 输出原始值，但**对数时要按页面的精度截断后比较**，否则会被"第 4 位小数"卡住。
12. **`avg_cost` 不是 `stock_amount/stock_qty`**（`lib/stock-cost.ts:52` 每次 round4）——不要反算。
