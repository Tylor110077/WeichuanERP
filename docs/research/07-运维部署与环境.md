## 0. 摘要

1. 生产是 **单机 Docker Compose + Nginx**：`app` 用 Next standalone 产物（`next.config.ts:22` → `Dockerfile:22,31` `CMD ["node","server.js"]`），只监听 `127.0.0.1:3000`（`docker-compose.yml:38`），HTTPS 由宿主机 Nginx 终止（`scripts/enable-https.sh:110-181`），证书在 `/etc/letsencrypt/live/<域名>/`（`:37,132-133`）。
2. **MySQL 端口完全没有对外发布**：`docker-compose.yml` 的 `mysql` 服务只有 `volumes` 与 `healthcheck`（`:13-21`），**没有 `ports:`**；全仓只有 `app` 一处 `ports`（`:37-38`）。→ 宿主机上跑的 CLI **既连不上 3306 也连不上 3307**，只有容器网络内的 `mysql:3306`（`:30`）可用。
3. **CLI 不能直接 `import` 现有鉴权/审计模块**：`src/lib/audit.ts:1`、`src/lib/auth/session.ts:1`、`src/lib/auth/guards.ts:1(→session)`、`src/lib/request-ip.ts:1` 都 `import "server-only"`，在 tsx/Node 下**直接抛异常**（已实测）。它们还 `import { headers } from "next/headers"`，进程外没有请求上下文。
4. **生产镜像里没有 `src/`**：`Dockerfile:22-28` 只拷 `.next/standalone`、`.next/static`、`public`、`prisma`、`node_modules`。→ 想在容器里 `npx tsx cli/index.ts` 直跑源码，**镜像必须改**（多拷 `cli/` 与它 import 的 `src/lib/**`，或改为构建期打包成一个 js）。
5. **双轨备份在生产其实是同一个目录**：`docker-compose.yml:16,36` 两处都把宿主机 `./backups` 挂到容器 `/backups`，而 shell 脚本写的是 `/opt/weichuan/backups`（`scripts/backup.sh:7-8`）——compose 文件就在 `/opt/weichuan`（`docs/部署指南.md:86`、`scripts/enable-https.sh:36`、`scripts/restore.sh:25`）→ 两者是**同一个宿主机目录**。所以 `/api/health` 数 `.gpg` 是能数到的（这解掉了 04 报告 §8 的疑点）。
6. **审计在 CLI 场景下会静默失效**：`writeAudit` 在 `ip === null` 时去调 `headers()`（`src/lib/audit.ts:28-33`），进程外必抛，而异常被 `:46-49` 的 `catch` 吞掉 → **Agent 的写操作一条审计都不落库**。CLI 侧必须显式传非 null 的 `ip`，并先把 `server-only` 拆掉。
7. 环境变量一共 **10 个名字**（§1），其中 CLI 真正需要的是 `DATABASE_URL`（仅当同容器内直连库时）与 `BACKUP_DIR`（`ops backup` 必须指它，不能默认 `./backups`）。
8. 迁移：18 个 migration（`prisma/migrations/`），生产靠人工执行 `docker compose exec app npx prisma migrate deploy`（`docs/部署指南.md:30,117`；`Dockerfile:27` 注释），**镜像启动时不自动迁移**（`Dockerfile:31` 只有 `node server.js`）。
9. 结论（详见 §6）：**推荐 CLI 走 HTTP 打到应用**（新增 `/api/cli/*` + `ApiToken`），而不是进程外直连服务层/数据库；若必须进程内复用，则 CLI 只能跑在 app 容器里，且要同步改 Dockerfile 与把 `server-only`/`next/headers` 从服务层与审计核心里剥离。

### 2.2 数据库可达性（CLI 的关键前提）

```
宿主机 /opt/weichuan
 ├─ nginx :443/:80  ──► 127.0.0.1:3000 ──► app 容器(standalone node server.js)
 │                                            └─ DATABASE_URL = mysql://…@mysql:3306/weichuan_erp
 ├─ ./backups ⇄ /backups（app 与 mysql 容器都挂载同一宿主目录）
 └─ mysql 容器 :3306  ← 仅 Docker 网络内可访问；宿主机无端口映射 ❌
```

- **`mysql` 服务没有 `ports:`**（`docker-compose.yml:4-21` 全段只有 `environment`/`volumes`/`healthcheck`），因此宿主机 `127.0.0.1:3306` 不通、`3307` 更不通（3307 是**开发机**专用：`scripts/db-start.sh:19` `--port=3307`，`:23` `--bind-address=127.0.0.1`）。
- 宿主机与容器共享 `/opt/weichuan/backups`（`docker-compose.yml:16,36`）→ **文件系统可达，数据库不可达**。
- 宿主机能通过 HTTP 打到应用：`127.0.0.1:3000`（同机）或 `http://47.108.181.80`（公网 80，尚无 HTTPS，见 `docs/生产环境安全与运维强化计划.md:33` R1 + `:210` A1 未完成）。

### 2.3 HTTP 机器可读出口现状

全仓只有 3 个 `route.ts`：`src/app/api/health/route.ts`、`src/app/(main)/backups/download/route.ts`、`src/app/reports/export/route.ts`。其中：

- `api/health`：**无需鉴权**（全文 43 行，无 `getCurrentUser`/`cookies` 引用）。
- `backups/download`：需 admin（`route.ts:7-10`）。
- `reports/export`：需登录且拒 sales（`src/app/reports/export/route.ts:9-11`）。

→ 若走 HTTP 路线，`ops health` 可以零改造直接复用 `/api/health`；其它命令必须新增端点。

- 迁移数量：**18 个**（`prisma/migrations/`，另有 `migration_lock.toml`，`provider = "mysql"`）。

### 3.3 CLI 新增 `ApiToken` 模型时的具体建议与注意事项

1. 本地：先 `npm run db:start`（`scripts/db-start.sh`）→ 改 `prisma/schema.prisma` → `npx prisma migrate dev --name api_token`（等价 `npm run db:migrate` 后按提示命名）→ 提交生成的 `prisma/migrations/<时间戳>_api_token/`。
2. **AGENTS.md 的坑**：改完 schema 必须重启 dev（`AGENTS.md`「改了 Prisma schema 必须重启 dev」；原因是运行中的 dev 进程持有旧 Prisma Client，会报 `Unknown argument`）。CLI 骨架若也在常驻进程里跑，同样要重启。
3. 生产：`docker compose exec app npx prisma migrate deploy`（`docs/部署指南.md:117`）。
4. **恢复备份会抹掉 `ApiToken` 表**：`restoreBackup()` 只恢复「当前有 + 备份有」的交集表（`src/lib/backup.ts:249-252`），`_prisma_migrations` 被排除（`:24`）——即「旧包恢复到新 schema」会少表/多列不匹配；若某 token 是恢复前刚建的，恢复后会消失（04 报告 §5.3 已详述，此处只作 CLI 影响提示）。
5. 新增模型的 `search_pinyin` 钩子不必登记，除非该模型有中文名称字段要搜索（`src/lib/prisma.ts:8-14` 是显式白名单）。

脚本 vs CLI 的边界结论：

- `db-*.sh`、`enable-https.sh`、`backup.sh`、`restore.sh` 都是**宿主机/容器运维脚本**（写死 `/opt/weichuan`、`/root/.weichuan/backup.key`、`/etc/nginx`），**不适合包进 `wc-cli`**——它们需要宿主机 root/cron，CLI 进程没有这些前提。
- 真正可被 CLI 复用的只有 **`scripts/backfill-pinyin.ts` 的写法作为模板**（见下），以及 `scripts/backup.ts` 的逻辑（但它自己就是「一层薄 CLI」）。
- `backfill-pinyin.ts` 作为 CLI 命令模板的**可取与不可取**：
  - 可取：单文件入口、无框架、`await` 直跑、异常统一 catch 后 `process.exit(1)`（`:62-68`）、输出人类可读的计数行（`:24,33,42,51,59`）——完全符合计划「不引入重型框架」。
  - 不可取：① 用裸 `new PrismaClient()`（`:14`）→ 绕过拼音扩展，CLI 写主数据不能这样；② 没有 argv 解析（`scripts/backup.ts:22` 的 `process.argv.slice(2)` + `includes("--x")` 也只是最土的写法，做不了 `--page/--from` 这类带值参数）；③ 无 `--json`、无退出码规范（只有 0/1，计划要求的 2/3/4/5 要自建）。
- `tsx` 可用性（CLI 若在容器内跑的前提）：`Dockerfile:2-6` 的 deps 阶段 `npm ci` **未加 `--omit=dev`**，且 `NODE_ENV=production` 到 `:12` 才设 → devDependencies（含 `tsx` `prisma`）**在最终镜像里存在**，`:26-28` 又把整份 `node_modules` 拷进 runtime —— 所以 `docker compose exec app npx tsx …` 是可用的（`docs/部署指南.md:31,87,94,96` 也正是这么用的）。

## 5. 健康检查与备份双轨的现状

### 5.1 `/api/health` 到底检查什么

- `src/app/api/health/route.ts:12` `dynamic = "force-dynamic"`；**无鉴权**。
- `db`：`prisma.$queryRaw\`SELECT 1\`` 成功与否（`:18-23`）。
- `backupFresh`：读 `BACKUP_DIR ?? "/backups"`（`:14`），**只数 `.gpg` 结尾的文件**（`:27`），取最新 mtime，判断是否在 **26 小时**内（`:15,28-33`）；目录不存在（ENOENT）→ `null`（跳过，`:25,35`）；其它错误 → `false`（`:35`）。
- 返回形状：`{ ok, db, backupFresh }`，`ok = db && backupFresh !== false`，200 / 503（`:38-42`）。
- → **它盯的是 shell 轨道（`backup.sh` 的 `.gpg`），完全不看应用内备份**。这在生产是成立的：`.gpg` 与 `.json.gz` 写在同一个宿主机目录（见 §0.5 与下节）。
- dev 下 `BACKUP_DIR` 未设置 → 常量取 `/backups` → macOS 上通常 ENOENT → `backupFresh: null`（本机 `backups/` 里只有 `.json.gz`，实测目录内容：`weichuan-backup-*.json.gz` × 7，大小约 7.3~8.1 KB）。

### 5.2 两套备份的关系（只补 04 报告没查实的部分）

| 事实 | 证据 |
|---|---|
| 生产是**同一个目录**（不是两处） | `docker-compose.yml:16`（mysql 挂 `./backups:/backups`）与 `:36`（app 同样挂载）；`scripts/backup.sh:7-8` 写 `/opt/weichuan/backups`；compose 文件位置 = `/opt/weichuan`（`docs/部署指南.md:86`） |
| 应用内轨道由**应用自己**调度，不需 cron | `src/instrumentation.ts:9-35`：服务启动 1 分钟后先跑一次（`:17,34`），此后每小时检查（`:16,33`），到点 `createBackup()` + `pruneBackups(cfg.keep)`（`:21-26`）；`register()` 里按 `globalThis` 标记防 HMR 重复（`:13-14`） |
| `backup:if-due` 用在哪 | 只在文档里作为**cron 二选一**备选（`docs/部署指南.md:82-88`；`src/instrumentation.ts:7` 注释同样说明）；仓库内没有任何 cron 文件调用它（`grep` 只有 `package.json:17` 与两处文档） |
| shell 轨道的调度 | 宿主机 cron `/etc/cron.d/weichuan-backup` 每日 02:00（`scripts/backup.sh:3`）——该文件**不在仓库里**（本机无法核实是否真装了） |

| 备份配置的存储 | `backup-config.json` 写在 `backupDir()`（`src/lib/backup.ts:128-137`，configPath 在 `:111-113`），默认 24h / keep=14（`:109`） |

## 6. CLI 部署形态推荐

### 6.1 三条路线的成本对比（全部有证据）

| 路线 | 可行性 | 证据 |
|---|---|---|
| **A. 宿主机 CLI 直连 MySQL** | ❌ **不可能**（不开放端口） | `docker-compose.yml:4-21` 无 `ports:`；只有 `app` 发布 `127.0.0.1:3000`（`:37-38`） |
| **B. CLI 直连服务层（进程内 `import`）** | ⚠️ 只能在 app 容器内；且当前不可行，需三处改造 | ① `server-only` 抛错（实测，见 §0.3）；② `next/headers` 无请求上下文（`src/lib/audit.ts:2,29`、`session.ts:2`）；③ 镜像内**没有 `src/`**（`Dockerfile:22-28`） |
| **C. CLI 走 HTTP 打到应用（新增 `/api/cli/*`）** | ✅ 最省事、约束最少 | 宿主机可达 `127.0.0.1:3000`（`docker-compose.yml:38`）；已有 `/api/health` 作为零改造先例（`src/app/api/health/route.ts`，无鉴权）；`/reports/export` 证明 route handler 内可正常用 `getCurrentUser`（`src/app/reports/export/route.ts:9`） |

### 6.2 推荐方案（分两步，风险递增）

**推荐：C 为主 + A/B 只用于本机运维命令。**

- CLI 形态：仓库内 `cli/`（Node + tsx + 自写 argv 解析，**不引入框架**，与计划 §8 Phase 1 一致）。
- 传输：`fetch(`${WC_BASE_URL ?? "http://127.0.0.1:3000"}/api/cli/...`）`，其中 `WC_BASE_URL` 由 CLI 自己引入（新变量，非服务端变量）。
- 鉴权：`ApiToken`（计划 §6.2）→ 请求头 `Authorization: Bearer <token>`；服务端 `requireUserFromToken()` 在 route handler 里解析（那里有请求上下文，`headers()` 可用）。
- **`ops health` 直接 GET `/api/health`，零改造、零鉴权**（`src/app/api/health/route.ts:17-42`）。
- **`ops version` 必须自建**（04 报告 §7 已指出：`package.json:3` 有 `version: 0.1.0`，无运行时出口）。若走 HTTP，可让 `/api/cli/version` 返回 `package.json` 的版本 + Git SHA（**注意**：`package.json` 不在 runtime 镜像里，`Dockerfile:22-28` 没拷它 → 要么 `import` 打进构建产物，要么用 `process.env` 注入，**不要再加一次 COPY 就指望 `fs.readFile("package.json")` 能读到**，除非同步改 Dockerfile）。
- 为什么不是 B：`server-only` + `next/headers` 意味着**即使把 CLI 塞进容器**，它也只能 `import` 纯净模块（`src/lib/prisma.ts`、`src/lib/backup.ts`、`src/lib/stock-cost.ts` 等），而**拿不到身份**（`getCurrentUser` 依赖 cookie）。计划 §6.1 已把方案 A 判为 ✗，本轨的补充是：**B 也需要身份注入点**，所以「服务层 + token guard」这件事在 A/B/C 三路下都躲不掉。

### 6.3 若坚持进程内直连（方案 B 的落地清单，含风险）

1. Dockerfile 增加：`COPY --from=build /app/cli ./cli` 与它 import 的源码（`COPY --from=build /app/src ./src`，或构建期用 esbuild/tsup 打成单个 js）。**当前镜像读不到 `cli/` 与 `src/`**（`Dockerfile:22-28`）。
2. 剥离 `server-only`：把审计核心从 `src/lib/audit.ts`（`:1` 有 `server-only`，`:29` 调 `headers()`）拆成「无请求依赖的 `writeAuditCore(params & { ip: string | null })`」+ 一个 web 壳负责填 `ip`。**否则 CLI 一 import 就抛，且审计会被 `:46-49` 静默吞掉。**
3. 身份：`requireUserFromToken(token)` 只依赖 `src/lib/prisma.ts`（可 import，已实测 OK），不要碰 `session.ts`/`guards.ts`。
4. 服务层函数签名必须 `(actor, input)`，**不能**内部调 `requireAdmin()`（那些函数在 `src/lib/auth/guards.ts:9-32`，进程外不可用）。
5. 环境变量：`DATABASE_URL`（容器内自动有）、`BACKUP_DIR=/backups`（`docker-compose.yml:34`）、`TZ`（`:33`）。
6. 风险：CLI 与 Next 进程**共用同一个 MySQL 连接**但**不共享事务**；`src/lib/prisma.ts:71-77` 的单例缓存只对 Next 进程有效，CLI 进程是另一个连接池（连接数上限未知，未核实）。
7. 风险：`writeAudit` 的 `entityId` 是 `BigInt(params.entityId)`（`src/lib/audit.ts:40`）——**任何非数字字符串都会被吞**（04 报告 §6.2 #1 实测 `BigInt("backup-config")` 抛错）。CLI 若用 `agentRunId`（字符串，计划 §5.5）当 `entityId`，会**静默丢失审计**；要么新增列，要么 `entityId: null`。

### 6.4 CLI 需要的环境变量（推荐方案下）

| 变量 | 谁用 | 说明 |
|---|---|---|
| `WC_TOKEN` | CLI 侧 | 计划 §6.2 已定；**当前 0 命中**，纯新增 |
| `WC_BASE_URL` | CLI 侧 | 默认 `http://127.0.0.1:3000`（与 `docker-compose.yml:38` 一致）；**新变量，需在计划里补** |
| `BACKUP_DIR` | 仅当 CLI 要**直接读备份目录**（`ops backup list/download` 走文件而非 HTTP）时 | 生产为 `/backups`（容器内）或 `/opt/weichuan/backups`（宿主机）。建议：`ops backup list/download` 走 HTTP（复用 `backups/download/route.ts:12-14` 的路径白名单），**不要**让 CLI 直接读文件 |
| `DATABASE_URL` | 仅方案 B 需要 | 方案 C 下 CLI **不需要**，服务端已有 |

### 6.5 明确不建议的做法

- **不要**让 CLI 直连数据库或加 `ports: 3306:3306`（`docker-compose.yml:4-21` 现状是不发布；发布等于把 DB 暴露到宿主机，与 `docs/生产环境安全与运维强化计划.md:25,79` 的「MySQL 3306 未对外」相悖）。
- **不要**把 `scripts/backup-roundtrip.ts` 做成 CLI 命令（`package.json:19` 的 `backup:verify` 名字有误导性；脚本本体 `:24-29` 会覆盖当前库）。
- **不要**让 CLI shell out 到 `scripts/backup.ts --restore=`——那会绕过 `requireAdmin` 与审计（04 报告 §5.3 #7 已述）。
