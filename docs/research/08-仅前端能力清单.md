## 0. 摘要

1. **本轨最重要的结论（好消息）**：「用库存 / 需进货 / 多补」以及金额/成本/毛利的**落库口径全在服务端**
   （`sale-orders/actions.ts:260-472`），客户端 `new-sale-form.tsx:1559-1590` 那一套只是**显示用镜像**。
   CLI 落库**不需要自己算**影响库内数字的部分。
2. **开单草稿是纯 localStorage，无服务端表**（`src/lib/form-draft.ts:13-22,73-93`；`prisma/schema.prisma` 无 Draft 模型）。
   `/drafts` 页面读的就是这份 localStorage（`drafts/draft-box.tsx:34-38`，SSR 快照恒空数组）。
   → **CLI 侧不可实现**，必须 ③ 明确不支持，或 ① 另建服务端草稿表（语义会变）。
3. **改单（作废+重开）没有服务端入口**：它由前端两次请求 + `router.push('/sale-orders/new?fromOrder=N')`
   串起来（`sale-orders/[id]/detail-actions.tsx:46-50`）。预填本身是**服务端**做的（`new/page.tsx:33-53`），
   但「作废」与「按原单重建」之间没有任何服务端耦合，原单与新单之间也没有 `revisionOf` 关联。
4. **打印**：页面是服务端渲染 + 客户端可编辑预览（`print/page.tsx`、`print-editor.tsx`）；
   模板**存数据库**（`model PrintTemplate`，`schema.prisma:566-582`）且有 3 个服务端 action，
   但**抬头/地址/电话另存 localStorage**（`print-editor.tsx:37,51-90`）——同一份数据两处存。
   CLI 能拿到数据与模板，但**渲染逻辑在 React 组件里，必须自己重写**；`window.print()` 本身 ③ 不支持。
5. **没有全局键盘快捷键系统**。`src/lib/shortcuts.ts` 名字误导，它是「工作台快捷入口目录」。
   全仓 `onKeyDown` 只有候选面板导航、开单页拦截回车、筛选回车即筛三类局部行为，
   **没有任何"只能靠快捷键触发、页面上没有按钮"的功能**。
6. **没有任何批量写操作**：列表页没有行选择框，不存在"全选 + 批量作废/打标签/改价"。
   最接近的只有退货的「全部退」（一次提交、服务端一次处理多行）与列表的「展开全部」（纯 UI）。
7. **列表的分页与筛选全部下推 SQL**，不是纯前端过滤；纯前端过滤只发生在左栏/下拉候选这类小控件上。
   唯一的例外是库存 `warnOnly`：它是**SQL 分页之后**在服务端 JS 里再过滤（`inventory/page.tsx:169-179`），
   CLI 要决定照抄还是下推（见 7.3）。
8. grep 结果：`/suppliers`、`/units`、`/categories`、`/suppliers/[id]`、`/customer-groups`、`/customer-tags`
   **全部是 9 行的 redirect**（分别跳 `/products` 或 `/customers`），计划文档第 2 节的路由清单需要标注。
9. 客户端搜索没有独立于服务端的一套数据源：首屏只下发「最近往来 N 条」（`RECENT_LIMIT=40`、
   `SEARCH_LIMIT=30`，`search-actions.ts:24-27`），其余靠 server action 搜——CLI 可以复用这些 action。
10. 关键风险点收敛为 3 个必须补的服务端入口：**改单（reopen）**、**服务端草稿（可选）**、
    **打印渲染（CLI 侧重写）**。

## 2. 开单草稿机制（确定结论）

**确定结论：草稿完全存在浏览器 `localStorage`，服务端与数据库里没有任何副本。CLI 侧不可实现。**

### 2.1 存储介质与 key
- 介质：`localStorage`。文件首行 `"use client"`（`lib/form-draft.ts:1`），只有 `localStorage.getItem/setItem/removeItem`（75, 88, 100, 102, 194）。
- 列表 key：`` `${LIST_PREFIX}:${userId}` `` = `wc-order-drafts:{userId}`（`form-draft.ts:13,51-53`）。
- 旧版单人单份 key：`` `${LEGACY_PREFIX}:${scope}:${userId}` `` = `wc-order-draft:sale:{userId}` / `wc-order-draft:purchase:{userId}`（`form-draft.ts:15,55-57`），
  读到会迁移进草稿箱并删除旧 key（`form-draft.ts:96-120`）。
- key 里带 `userId`（`form-draft.ts:10-11` 注释、51），所以"同一台电脑换人登录不串"。
- 数据库侧：`prisma/schema.prisma` 的 `model` 列表（83-588）中**没有 Draft 模型**。

### 2.2 数据结构
```ts
{ v: 1, drafts: DraftRecord[] }                       // VERSION = 1（form-draft.ts:16,86-88）
DraftRecord = { id, scope: "sale"|"purchase", savedAt: number, summary, data }
DraftSummary = { partner, lines, amount, preview }     // form-draft.ts:32-49
```
- 校验：`isDraftRecord`（67-70）；版本不符或 `drafts` 不是数组 → 整个草稿箱丢弃（77-78）。
- 摘要由表单侧算好一起存：`new-sale-form.tsx:773-785`（`amount` = `Σ lineAmount`）、`new-order-form.tsx:322-330`。

### 2.3 保存时机
- 输入停顿 **700ms** 防抖落盘：`SAVE_DELAY_MS = 700`（`form-draft.ts:22`），`useEffect` + `setTimeout`（311-334）。
- **恢复完成前禁止保存**（否则首屏空表单会盖掉好草稿）：`hydrated = useRef(false)`（274），effect 里先 `hydrated.current = false`（287）再 `= true`（308），保存 effect 首行 `if (!hydrated.current) return`（312）。
- 全清空（`hasContent === false`）→ 删除该草稿、`currentId` 置 null（315-319）。
- 提交时删草稿但不动表单：`clearStored()`（336-339），由表单 `onSubmit={clearStored}` 调用
  （`new-sale-form.tsx:843`、`new-order-form.tsx:392`）。
- "有内容"的判定：`new-sale-form.tsx:795-796`（选了客户 / 有备注 / 任一行有商品或搜索词）；`new-order-form.tsx:340`。
- 跨标签页同步：`subscribeDrafts` 监听 `storage` 事件（177-188）。

### 2.4 过期与容量策略
- 过期：`MAX_AGE_MS = 7 * 24 * 60 * 60 * 1000`（7 天，`form-draft.ts:18`），读盘时过滤（80）。
- 每类上限：`MAX_PER_SCOPE = 20`（`form-draft.ts:20`），保存时按 `savedAt` 倒序保留最近的 20 份（145-151）。
- 无痕模式写不进：`writeAll` 里 catch 吞掉（86-92）；读失败返回 `[]`（81-83）。
- 保存时间人话化：`formatSavedAt`（212-223）。

### 2.5 `/drafts` 页面数据源
- 页头与登录检查在服务端（`drafts/page.tsx:5-8`），只向下传 `user.id`（`drafts/page.tsx:17`）。
- 列表渲染**全部**在客户端读 localStorage：
  ```ts
  useSyncExternalStore(subscribeDrafts, () => getDraftsSnapshot(userId), emptyDraftsSnapshot)
  ```
  `drafts/draft-box.tsx:34-38`；SSR 快照是模块常量空数组 `EMPTY_DRAFTS`（`form-draft.ts:206-209`）。
- 分页是**纯前端 slice**：`DRAFT_PAGE_SIZE = 8`、`group.slice(...)`（`draft-box.tsx:24,69-71,134-138`）。
- 「继续开单」链接带 `?draft=<id>`（`draft-box.tsx:98`）；开单页用 `useSearchParams().get("draft")` 取（`new-sale-form.tsx:767`）。
- 列表页头部「继续未完成的单」同样是客户端读 localStorage 才渲染（`components/draft-resume-link.tsx:30-49`）。
- 注意：**直接点「新建」开单页一定是空白的**，不会自动带出上次草稿（`form-draft.ts:229-231` 注释；`draft-resume-link.tsx` 也是显式带 `?draft`）。

### 2.6 对 CLI 的处置建议
- 建议 **③ 明确不支持**：`query drafts` / `draft list` 这类命令删掉。理由：草稿的语义是"这台机器上没填完的单子"（`form-draft.ts:9-10` 注释），服务端本来也看不到；
  强行同步到服务端会改变语义（多设备共享），且要处理 id/冲突/清理，收益低。
- 如果业务上确实要"Agent 先草稿、人再确认"，正确做法不是草稿，而是计划文档 5.6 的 **`pending_review` 待审核单据**——那才是有服务端入口的等价能力。

## 3. 改单（作废+重开）预填的实现与 CLI 补口方案

### 3.1 前端链路（两页拼接，无服务端入口）
1. 详情页点「改单」→ 展开表单（`sale-orders/[id]/detail-actions.tsx:83-106`），
   `onSubmit={() => setReopenIntent(true)}`（86），reason 默认填「改单」（91）。
2. 提交调 `voidSaleOrderAction`（`detail-actions.tsx:41-44`，实现在 `sale-orders/actions.ts:514-625`）。
3. 作废成功后前端跳转：
   ```ts
   useEffect(() => {
     if (reopenIntent && voidState?.ok) router.push(`/sale-orders/new?fromOrder=${orderId}`);
   }, [reopenIntent, voidState, router, orderId]);
   ```
   `detail-actions.tsx:46-50`；进货单版 `purchase-orders/[id]/detail-actions.tsx:48-52`（`/purchase-orders/new?fromOrder=`）。
4. **这一步是纯前端**：作废与"按原单重开"之间没有任何服务端耦合，是两次独立请求。

### 3.2 预填实现（服务端读原单，不是客户端 fetch）
- `sale-orders/new/page.tsx:22-24` 接收 `searchParams.fromOrder`；`:33-53` 直接 prisma 读原单：
  ```ts
  prisma.saleOrder.findUnique({ where: { id: fromOrderId }, include: {
    customer, items: { include: { product, unit } }, autoRestockOrders: { include: { items: true } } } })
  ```
- `:90-124` 映射成 `prefill`，其中**现场进货部分要从自动补货单取回来**：
  `supplyPrice` / `supplierId` / `extraQty` 来自 `autoRestockOrders.flatMap(...).find(pi => pi.productId === it.productId)`（`:100-119`）；
  `stockUsed` 来自 `it.stockQtyUsed`（`:115`）；`estimated` 原样带过（`:109`）——估价行改单后仍必须是估价行（注释 `:170-171`）。
- `purchase-orders/new/page.tsx:28-40` 同构（只读原单 items，无自动补货单）；`:120-139` 映射 prefill。
- 表单侧：`prefill` 直接做 `useState` 初值（`new-sale-form.tsx:184-209`、`new-order-form.tsx:106-108`），
  并 `skipRestore: !!prefill` 让草稿不参与（`new-sale-form.tsx:791`、`new-order-form.tsx:336`），
  因为"草稿会盖掉原单内容"（`form-draft.ts:254-255` 注释）。
- 页面提示原单是否已作废：`new-sale-form.tsx:845-858`（`prefill.voided`）。
- 提交 `createSaleOrderAction` 会**重新计算库存与成本**（提示文案 `new-sale-form.tsx:851-853`）。

### 3.3 CLI 要在哪一层补入口
- **必须在服务层补一个 `reopen`**，建议签名：
  `reopenSaleOrder(actor, { orderId, reason, overrides })` →
  内部顺序：`voidSaleOrder`（复用现有）→ 读原单构造 create 输入（复用 3.2 的映射逻辑，把它从 page.tsx 抽到 `src/lib/services`）→ `createSaleOrder`（复用）
  → 返回 `{ voidedOrderId, newOrderId }`。
- 需要顺带决策的两点：
  1. **是否新增 `revisionOf` 关联**：`prisma/schema.prisma:378-408` 的 `SaleOrder` / `:316-349` 的 `PurchaseOrder` 里**没有**指向被改原单的列，新单与旧单目前只有文案上的关系。计划文档 5.6 的 `revise` 需要这一列。

### 5.1 「用库存 / 需进货 / 多补」——客户端镜像（**必须抄**，用于 dry-run 预测）

```ts
function usedStock(row: Row): number {
  if (row.estimated) return 0;                       // 估价行不占库存
  const qty = Number(row.quantity);
  if (!Number.isFinite(qty) || qty <= 0) return 0;
  const cap = Math.max(Math.min(row.stockQty, qty), 0);
  if (row.stockUsed.trim() === "") return cap;       // 留空 = 尽量用库存
  const v = Number(row.stockUsed);
  return Number.isFinite(v) ? Math.max(0, Math.min(v, cap)) : cap;
}

function needPurchase(row: Row): number {
  if (row.estimated) return 0;                       // 估价行先不进货
  const qty = Number(row.quantity);
  if (!Number.isFinite(qty) || qty <= 0) return 0;
  return Math.max(qty - usedStock(row), 0);
}

function extraRestock(row: Row): number {
  const v = Number(row.extraQty);
  return Number.isFinite(v) && v > 0 ? v : 0;        // 负数/空视为 0
}

function restockTotal(row: Row): number { return needPurchase(row) + extraRestock(row); }

function lineAmount(row: Row): number {
  const q = Number(row.quantity);
  const price = Number(row.unitPrice);
  return Number.isFinite(q) && Number.isFinite(price) ? q * price : 0;
}
```


**客户端与服务端的两处差异（CLI 必须知道）**：
1. 客户端**不做 round2/round3**（显示值可能是 1.2345），服务端四舍五入到 3 位数量 / 2 位金额。
2. 客户端的 `row.stockQty` 是**页面加载时的快照**；服务端在事务内逐行重读并校验 `cur.qty < stockUsed` 抛「库存不足」（`:331`、`:433`）。

**成本快照（服务端，`:456-470`）**：

- **对 CLI 的意义**：不需要为批量操作设计循环调用；反过来，如果 CLI 想提供 `--ids` 批量作废，
  那是 CLI 自己的便利功能，服务端没有对应语义，应明确"逐个调用 + 聚合结果"，并在部分失败时说清哪个成功。

### 7.3 一个口径陷阱：库存 `warnOnly`
`inventory/page.tsx:169-179`：
```ts
const rows = products
  .map((p) => { ... return { p, qty, minStock, warning, negative }; })
  .filter((r) => !warnOnly || r.warning);      // ← 在 skip/take 之后才过滤
```
`products` 已经是本页（`take: PAGE_SIZE`）的结果，所以「预警商品 N 个」这个列表是"**当前页里**的预警商品"，

- CLI 必须显式决策：
  - 方案 A（口径正确）：把 `minStock > 0 AND status = 1 AND stockQty < minStock` 下推到 SQL；
  - 方案 B（与页面数字一致）：照抄"页内过滤"。
- 建议 A，并把页面这个不一致作为独立 bug 记录（不属本轨）。

## 8. 对 `docs/agent-cli-plan.md` 第 7 节命令面的具体修订建议

### 8.1 建议删除
- `wc-cli query drafts`（以及通用参数里任何 draft 相关筛选项）—— 数据源是浏览器 localStorage，服务端没有（第 2 节结论）。
  若要保留该命令名，应当**重新定义**为「待审核单据」（5.6 的 `pending_review`），而不是开单草稿。

### 8.2 建议改名/补语义（原草案里语义不成立）
- `wc-cli order sale reopen` / `order purchase reopen`：
  草案把它列在 `order sale create|void|star|reopen` 里，看起来是"一个动作"。实际现状是**两个独立请求 + 一次前端跳转**（3.1），
  且原单与新单之间**没有关联列**（`schema.prisma:378-408` 无 `revisionOf`）。
  → 建议单列为一级语义并写明三步：
  ```
  wc-cli order reopen --type sale|purchase --from <orderId> --reason <text> [--set ...] [--dry-run|--yes]
    # 语义：作废原单 + 按原单内容 + 覆盖项生成新单，输出 { voidedOrderId, newOrderId }
  ```
  并在服务层实现（`src/lib/services/order-reopen.ts`），**同时补 `revisionOf`/`version` 列**
  （这也是计划 5.6 `review revise` 的落点；否则 `revise` 无法指向"被驳回那版"）。
- `wc-cli order estimate fill`：服务端已有 `fillEstimatedAction`（`pending-estimates/actions.ts:42`）+
  `FillForm`（`pending-estimates/fill-form.tsx`）。命令 OK，但要在帮助里写清"会同时生成一张待收货/已收货进货单并把成本回写原行"。
- `wc-cli master ... update` 里的"就地新建"类入口（新建厂家/单位/分类/组织/标签/占位商品）
  **不需要单独命令**，它们是"创建主数据"的不同入口，`master create` 已覆盖。

### 8.3 建议新增
```
# 打印（第 4 节）
wc-cli print template list|show|create|update|set-default|delete
    # 复用 print/template-actions.ts 的 3 个 action（抽服务层）；仅 admin
```

### 8.4 建议在通用参数里补充的说明
- 分页参数要与页面一致（`--page`、`--page-size`），并**明确每个 query 命令的默认排序**（第 7.4 节：都是 `createdAt desc` 或 `code/name asc`）。

- **不要**暴露 `--from-order`：它只是页面预填的内部参数，CLI 侧应走 `order reopen` 的语义（3.3）。
