## 1. guards.ts 逐个实现（原文条件 + file:line）

文件全文 32 行（`src/lib/auth/guards.ts`），顶部注释自称"文档 5 章权限矩阵"，并声明
"前端只做展示控制，所有写操作后端鉴权"（`guards.ts:3-6`）。

### 1.1 `requireAdmin`（guards.ts:9-15）

```ts
export async function requireAdmin() {          // :9
  const user = await getCurrentUser();          // :10
  if (!user || user.role !== "admin") {         // :11
    throw new Error("无权限执行此操作");          // :12
  }
  return user;                                  // :14
}
```

- 判定：`!user || role !== "admin"`。**未登录与越权共用同一句错误**，调用方无法区分。
- 失败形态：`throw`。返回：`User`。
- 实际等价于"仅 admin"。

### 1.2 `requireMasterDataWrite`（guards.ts:18-25）

```ts
export async function requireMasterDataWrite() {   // :18
  const user = await getCurrentUser();             // :19
  if (!user) throw new Error("未登录");             // :20
  if (user.role !== "admin") {                     // :21
    throw new Error("基础资料仅管理员可维护");        // :22
  }
  return user;                                     // :24
}
```

- 判定：逻辑上**与 `requireAdmin` 完全等价**（都只放行 `admin`），差别仅在错误文案与"未登录"分支分开。
- 注释称"业务员/老板只读"（`guards.ts:17`），但代码并未表达"只读"——只读是靠不调用这个 guard 实现的。
- 失败形态：`throw`。

### 1.3 `requireLogin`（guards.ts:28-32）

```ts
export async function requireLogin() {        // :28
  const user = await getCurrentUser();        // :29
  if (!user) throw new Error("未登录");        // :30
  return user;                                // :31
}
```

- 判定：仅要求有会话。
- 注释说"manager 列表页只需登录，写按钮按角色显示"（`guards.ts:27`）——即**它本身不做任何角色判断**，
  角色过滤全部由调用方在之后手写 `if (user.role === ...)`。
- 失败形态：`throw`。实际使用点只有两处：`receivables-payables/actions.ts:30,136`、`dashboard/shortcut-actions.ts:21,44`。

## 2. 会话机制与"CLI 能否复用 cookie"的结论

### 2.1 机制事实（逐条给证据）

| 项 | 事实 | 证据 |
|---|---|---|
| cookie 名 | `weichuan_session` | `session.ts:14`（并导出 `SESSION_CONSTANTS = { COOKIE_NAME }`，`session.ts:125`） |
| cookie 值 | `randomBytes(32).toString("hex")`，即 64 字符明文随机串 | `session.ts:43` |
| 服务端存什么 | `tokenHash = sha256(token)`，`Char(64)` 唯一列 `sessions.token_hash` | `session.ts:20-22,48`；`schema.prisma:116` |
| 过期 | 8 小时；读时若 `expiresAt < now` 则删行并返回 null | `session.ts:15,80-83`；`schema.prisma:119` |
| cookie 属性 | `httpOnly: true`、`sameSite: "lax"`、`path: "/"`；`secure` **仅当** `x-forwarded-proto` 为 https | `session.ts:25-40` |
| 解析成身份 | `getCurrentUser()`：按 `tokenHash` 查 `session` 并 `include: { user: true }` → 直接返回 `User`（含 `id`,`role`） | `session.ts:67-92` |
| 停用即吊销 | `session.user.status !== 1` → 删除该用户全部会话 → null | `session.ts:85-89` |
| 登出 | 删除该 token 的 session 行 + 删 cookie | `session.ts:57-64` |
| 改密/重置 | `revokeOtherSessions` / `deleteMany({userId})` | `session.ts:95-104`；`profile/actions.ts:56`；`users/actions.ts:96,127` |
| CSRF | **无 CSRF token、无 Origin 校验代码**；仅靠 `SameSite=Lax` | 全仓 `csrf` grep 仅命中 `next.config.ts:6` 的 Referrer-Policy；`SameSite` 见 `session.ts:33` |
| 路由级拦截 | **无 `middleware.ts`**（仓库根与 `src/` 都无此文件） | `find . -name middleware.ts` 0 命中 |
| 登录校验所在层 | `src/app/(main)/layout.tsx:77-80`：`getCurrentUser()` 为 null → `redirect("/login")` | 同左；`/login`、`/api/*`、`/reports/export` 不在 `(main)` 下，各自单独校验 |

### 2.2 结论：**不建议 CLI 复用 cookie**，理由如下

1. **登录动作本身只能靠 Server Action POST**。`loginAction` 是 `"use server"` 里的 action（`login/actions.ts:26`），
   CLI 要拿 cookie 必须模拟一次表单 POST 到 `/login`，并带上 Next.js 内部的 `Next-Action` id 头；
   该 id 是构建产物，**版本一变就失效**（计划 6.1 表里对这个不稳定的判断是对的）。仓库里没有任何
   面向程序的登录端点（`/api/*` 只有 `health`）。
2. **cookie 是 HttpOnly**（`session.ts:32`），浏览器脚本读不到；CLI 必须以 HTTP 客户端参与握手，
   拿不到"先登录再复用 token"的稳定路径。
3. **即使拿到 cookie，也无法表达 Agent 身份**。`getCurrentUser()` 只返回 `User`，`role` 就是人的角色
   （`session.ts:91`）。计划 5.5/5.6 需要的"这是 Agent 发的 / 不能自审自批"在 cookie 会话里**没有承载点**，
   只能靠"给 Agent 单独开一个 role 为 sales 的账号"，而这既拿不到作用域收敛、也无法区分"哪个 token"。
4. **绕道方案（技术可行，但不推荐）**：会话行的校验就是 `sha256(cookie值) == sessions.token_hash`
   （`session.ts:72-76`），所以**有数据库写权限的进程可以自己插一行 `sessions` 并直接用明文 token 当 cookie**，
   从而以任意用户的身份访问网页与 Server Action。代价：需要 DB 凭据、TTL 仍是 8 小时、
   无 scopes、吊销粒度只有"删这一行"、且**完全绕过应用层审计**（审计里只会看到"某人登录了"）。
   计划 6.3 的"权限不足要可收敛"与第 10 节的"token 泄露对策（只存哈希/可吊销/有 scopes）"都做不到。
5. 因此维持计划 6.2 的方向（新增 `ApiToken` + `requireUserFromToken`），但**必须同时解决
   "Agent 身份如何落库"**（见 §8.3）。

## 5. 审计：`writeAudit` 实现 + 覆盖度清单 + 缺失清单

### 5.1 确切签名与实现（`src/lib/audit.ts`，全文 50 行）

```ts
export interface AuditParams {                    // audit.ts:12
  userId?: number | null;                         // :14  “登录失败等场景可为空”
  action: "login" | "logout" | "create" | "update" | "delete" | "receive" | "void" | "reset_password"; // :15
  entityType: string;                             // :16
  entityId?: number | string | bigint | null;     // :17  ← 注意类型：**允许 string**
  before?: unknown;                               // :19
  after?: unknown;                                // :21
  ip?: string | null;                             // :22
}
export async function writeAudit(params: AuditParams): Promise<void>  // :25 → 返回 void
```

写入内容与逻辑（`audit.ts:25-49`）：

- IP 兜底：`params.ip == null` 时从 `headers()` 取 `x-forwarded-for` 第一段 → `x-real-ip` → `null`（`:27-34`）。
- 落库字段：`userId / action / entityType / entityId / beforeJson / afterJson / ip`（`:36-44`）。
- `entityId`：`params.entityId != null ? BigInt(params.entityId) : null`（`:40`）。
- `beforeJson/afterJson`：**非空才写**（`!= null ? ... : undefined`，`:41-42`），所以 `before: null` 与"没传 before"**不可区分**——审计里看不出"原值为 null"。

**`BigInt` 会不会抛错（兄弟轨的发现，本项目核实：成立）**：

- `sessions`/`audit_logs` 的 `entity_id` 是 MySQL `BIGINT`（`schema.prisma:150`），Prisma 对应 `BigInt`。
- `BigInt("backup-config")` 抛 `SyntaxError: Cannot convert backup-config to a BigInt`
  （`audit.ts:40`）。因为 `AuditParams.entityId` 的类型标注把 `string` 也接受了（`audit.ts:17`），
  **类型层面不拦，运行期抛**。
- 但是——**抛错被吞掉**：整个写入在 `try` 里（`audit.ts:26`），`catch` 只做
  `console.error("[audit] 审计日志写入失败:", err)`（`audit.ts:46-49`），**函数不抛、不返回失败**。
  且注释明说"审计写入失败不该让业务事务失败"（`audit.ts:47`）。
- 结论：**`entityId` 传非数字字符串 = 该条审计 100% 静默丢失**，只在服务端日志留一行，页面上查不到任何痕迹。

**实际命中这个 bug 的地方（唯一一处）**：

- `backups/actions.ts:60-66` `saveBackupConfigAction`：`entityType: "backup_config"`、
  **`entityId: "backup-config"`**（`:64`）→ 抛错 → 被 `audit.ts:46` 吞掉。
  后果：**改备份间隔/保留份数这个操作在审计页上完全不可见**。
- 反证开发者知道这个坑：同一文件 `createBackupNowAction` 在 `:25-26` 写着
  "…传字符串会被 writeAudit 内部 BigInt() 抛错而静默丢弃"，并于 `:32` 用 `entityId: null` 规避。
  `deleteBackupAction:46`、`restoreBackupAction:104` 也都用了 `null`。**只有 `saveBackupConfigAction` 漏改。**

**失败是否被吞掉**：是。除上面的 `BigInt` 抛错外，任何 DB 故障（连接断、约束冲突）也只 `console.error`。
所以"审计表只增不改不删"（`audit.ts:8`）这句话还有半句需要打问号：
注释称"数据库层面由迁移权限约束"，但 `prisma/migrations/` 下 **grep `GRANT|REVOKE|trigger` 0 命中**
（已核 `docs/research` 之外的 11 个迁移目录），即**这条约束在代码库里没有落地**。

### 5.2 审计写入的事务性：**不在同一事务内**

- `writeAudit` 用的是**全局单例** `import { prisma } from "@/lib/prisma"`（`audit.ts:3`），
  调的是 `prisma.auditLog.create`（`audit.ts:35`），**不接受 `tx` 参数**。
- 有 **3 处**把 `writeAudit` 写在了 `prisma.$transaction(async (tx) => { ... })` 回调**内部**，
  但它们实际走的是另一条连接、立即提交，**不参与该事务**：

| 位置 | 所在事务范围 | 后果 |
|---|---|---|
| `sale-orders/actions.ts:405-421`（自动补货进货单审计） | 事务 `:218-490` | 事务若在之后回滚（如 `:433` 库存不足 throw、或 P2002 重试），**审计行残留** |
| `sale-orders/actions.ts:595-602`（级联作废补货单审计） | 事务 `:534-608` | 同上（后续 `:604` 更新失败会残留"已作废"的审计） |
| `purchase-orders/actions.ts:150-156`（进货单创建审计） | 事务 `:129-158` | 同上（P2002 重试时**同一次创建会写多条审计**） |

- 其余 71 处都在事务**之后**调用（例如 `sale-orders/actions.ts:492-498` 在主事务成功后写），
  方向相反的风险是"**业务已提交、进程在写审计前挂掉 → 审计缺失**"。两者都是"审计与业务不同源"。
- **`sale-orders/actions.ts:200-212`** 是另一个特例：自动按厂家名创建 `supplier` 用的是**全局 prisma**
  （不在事务里），所以"补货单最终回滚"时，**厂家档案已经建了、审计也写了**（`sale-orders/actions.ts:205`）。

## 7. 登录节流与密码策略

### 7.1 节流（两层，都靠 `login_logs` 表，**不是内存**）

| 层 | 阈值 | 窗口 | 数据来源 | 判定函数 | 证据 |
|---|---|---|---|---|---|
| 账号级锁定 | 失败 **≥5** 次 | **15 分钟** | `login_logs`（`userId + success:false + createdAt`）计数 | `getLockRemainingSeconds(userId): number` | 常量 `session.ts:17-18`；实现 `session.ts:107-123` |
| IP 级限流 | 失败 **≥20** 次 | **5 分钟** | `login_logs`（`ip + success:false + createdAt`）计数 | `isLoginIpThrottled(ip): boolean` | 常量 `login-throttle.ts:10-11`；实现 `:13-23` |

细节：

- 账号锁定的解锁时刻 = **窗口内第一次失败的时间 + 15 分钟**（`session.ts:121-122`），不是"最后一次失败后 15 分钟"。
- IP 限流在**账号查询之前**执行，所以未知账号同样受限（`login/actions.ts:45-57`，注释 `:45`）；
  被限流时 `userId: null` 写登录日志（`:53-55`）。
- 两种节流都**不区分成功/失败以外的维度**：只数 `success:false`，没有按"密码错误 vs 账号不存在"分桶。
- `getLockRemainingSeconds` 内部可能被调用两次（先 `count` 再 `findFirst`），逻辑上只要 `count >= 5` 就必有 `findFirst` 结果（`session.ts:112-119`）。
- **CLI 用 token 鉴权的限流建议**：现有 `login_logs` 表**无法承载**（它没有 `api_token_id` 列，
  `schema.prisma:127-142`）。三个可选做法，按推荐度：
  1. 在 `ApiToken` 上加 `lastUsedAt` + 计数列（或新表 `api_token_usage`），按 token 计失败/速率；
  2. 复用 `audit_logs`（action 加 `api_call`）按 `entityId=tokenId` 计数——缺点是审计表会承担限流职责，且 `BigInt` 坑要绕；
  3. 进程内内存计数——**不可取**，standalone 多进程/重启即失效（`next.config.ts:23` `output: "standalone"`）。
- 另外提醒：**token 鉴权路径不应走 `getLockRemainingSeconds`**（它按 `userId` 数"登录失败"，
  而 token 调用没有密码校验环节），否则会把"人登录失败"与"Agent 调用失败"混在一起。

### 8.2 第 6.2 节：改成什么

原文"现状是 cookie 会话 + 无 token 机制（⚠️待核实是否有 API key）"可以**去掉待核实标记**，并按下面改写：

> ### 6.2 CLI 怎么鉴权（✅已核实现状）
>
> **现状（已核实）**：只有 cookie 会话（`weichuan_session`，值 32 字节随机 hex，库中仅存 `sha256`，
> TTL 8h，HttpOnly+SameSite=Lax，`session.ts:14-40`），**全仓无任何 token / API key / Authorization 头 /
> 签名 URL 机制**（grep 0 命中），只有 3 个 `route.ts`（`/api/health` 无鉴权、`/reports/export` 与
> `/backups/download` 走 cookie）。也没有 `middleware.ts`，登录校验在 `(main)/layout.tsx:77-80`。
>
> **结论：CLI 不能复用 cookie。** 理由（三条）：① 拿 cookie 只能模拟 Server Action POST
> （需 Next 内部 `Next-Action` id，构建相关、不稳定）；② cookie 是 HttpOnly；③ **cookie 身份里没有
> "Agent"这一维**（`getCurrentUser` 只返回 `User`，`session.ts:91`），5.5/5.6 需要的溯源与
> "Agent 不能自审自批"无从表达。（技术上"有 DB 权限就自插 `sessions` 行"可行，但会绕过审计、
> 无 scopes、无独立吊销，见研究报告 §2.2。）
>
> **新增（方向不变，按下面几条收紧）**：
> - 新模型 `ApiToken { id, userId, tokenHash(sha256, unique), name, scopes(Json), expiresAt, lastUsedAt, revokedAt, createdAt }`；
>   `tokenHash` 与 `Session.tokenHash` 同样只存哈希（`schema.prisma:116` 已是同一做法，直接照抄）。
> - `requireUserFromToken(token)`：解析 → 查 `tokenHash` → 校验 `revokedAt/expiresAt` → 校验 `user.status === 1`
>   → **同时把 `apiTokenId` 与 `actorKind: "agent"` 一并返回**（否则 5.5 无法落库）。
> - **token 的失败形态必须统一**：现有 guard 是 `throw new Error(...)`（`guards.ts:12,20,30`），
>   cookie 型 action 是 `return {error}`（§1.5）。CLI 的服务层请统一成"抛带退出码的领域错误"，
>   映射到计划 6.3 的退出码 `3`（权限不足）/`4`（业务规则拒绝）。
> - 限流：**不要复用 `login_logs`**（它没有 token 维度）；在 `ApiToken` 上加 `lastUsedAt` + 失败计数，
>   或新增 `api_token_usage` 表。阈值建议与账号级对齐（5 次/15 分钟）但按 `apiTokenId` 计数。
> - CLI 侧读取方式沿用原文（`WC_TOKEN` 或 `~/.config/weichuan/token`，不进命令行参数）。

### 8.3 第 5.6 节"审核只能由人做、Agent 不能自审自批"要补什么

**问题**：现在**没有任何字段能承载"这是 Agent 发的 token"**。已核实：

- `User`（`schema.prisma:83-110`）全部字段：`id / username / passwordHash / displayName / searchPinyin /
  role / status / shortcuts(Json?) / lastLoginAt / createdAt / updatedAt` + 9 个关系。
  **没有 `isAgent`**；全 schema grep `isAgent|actorKind|reviewStatus|agentRunId|revisionOf|reviewedBy` **0 命中**。
- `role` 只有 3 个值（`schema.prisma:19-23`），**无法**用"新增一个 role=agent"承载：
  一旦第 4 个角色值出现，`roles.ts:3-7` 的 `Record<UserRole, string>` 会编译报错，
  且 `layout.tsx:9,18,23-68` 的菜单过滤、所有 `role === "..."` 判断都要重审。
- `User.shortcuts`（`Json?`，`schema.prisma:93`）理论上能塞元数据，但它是工作台快捷入口，
  `lib/shortcuts.ts` 会解析它——**不要**借道，会互相踩。

**建议（按优先级）**：

1. **身份维度放在 `ApiToken` 上，不要放在 `User` 上**。`ApiToken.actorKind`（或 `tokenKind`：`human|agent`）
   + `scopes`。这样"同一个人的会话"与"同一个人的 Agent token"天然分离，
   且吊销 token 不影响人登录。
2. **`User` 上仍建议加一个只用于兜底的标记**（若确实存在"纯 Agent 账号"）：
   新增 `isAgent Boolean @default(false)`（**必须配迁移 + 重启 dev**，见 AGENTS.md）。
   但不建议把它作为主判据——主判据应是 token 的 `actorKind`。
3. **审核权限不能只靠 `role`**。现在"审核"这个能力在代码里**根本不存在**
   （全仓无 `reviewStatus`/`ReviewNote`/审核 action）。落地时请显式写成 `ApiToken.scopes` 里
   不含 `review:approve` / `review:reject`，并在服务层硬编码：
   **`actorKind === "agent"` 的请求，无论 role 是什么，一律拒绝 `review:*`**，
   拒绝时写审计（`action:"void"` 不够用，建议扩展 `AuditParams.action` 联合类型，
   `audit.ts:15` 目前是 8 个字面量的联合，加值要同步改 `audit-logs/page.tsx:14-23` 的中文映射表）。
4. **注意 `AuditLog` 无法承载 Agent 维度**：`AuditLog` 只有
   `userId / action / entityType / entityId / before / after / ip / createdAt`（`schema.prisma:144-161`），
   没有 `actorKind` / `agentRunId` / `apiTokenId`。计划 5.5 说"`writeAudit` 带上 `actorKind` 与 `agentRunId`"，
   意味着**必须加列 + 改 `AuditParams`（`audit.ts:12-23`）+ 改审计页展示与筛选**（现在是按实体/时间筛，
   见 §6.1）。且 `AuditLog.userId` 是 `Int?` 且外键指向 `users`（`schema.prisma:146-147`），
   Agent 的"授权人"放 `userId`、`apiTokenId` 另开一列是最小改动。
5. **`ReviewNote` 的 `reviewerUserId` 必须是真人**（`schema.prisma` 无此表，需新建），
   并建议加 `reviewedByTokenId Int?` 只为留证（正常情况恒为 null）。
