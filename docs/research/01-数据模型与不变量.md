## 0. 摘要

- 数据模型：23 个 model、10 个枚举、无任何 `Float`；金额一律 `Decimal(14,2)`，数量 `Decimal(12,3)`，
  单价 `Decimal(12,2)`，移动加权均价 `Decimal(12,4)`（`prisma/schema.prisma:209-214,421,592-595`）。
- 库存在 `products.stock_qty / stock_amount / avg_cost` 三列上**事务内维护**，不靠流水聚合；
  `stock_movements` 是"只增"的流水账本，读路径只拿它做"最近进价/最近进货时间/筛选"，不作余额来源
  （`src/app/(main)/inventory/page.tsx:98-110,119-135`、`src/lib/reports.ts:41-84`）。
- 成本快照存在 `sale_order_items.cost_amount`（= 库存部分成本 + 现场进货部分成本），
  开单事务内一次写定（`src/app/(main)/sale-orders/actions.ts:456-470`）；`sale_return_items.cost_amount`
  存的是回补成本。唯一允许改写历史快照的地方是估价补单（`src/app/(main)/pending-estimates/actions.ts:114-117`）。
- 计划第 3 节 6 条不变量的判定：**①③⑤⑥ 成立**（⑤原文标"待核实"，本轮已核实并给出完整冲减口径）、
  **④ 部分成立**（自动补货进货单创建即入库，是"确认入库"之外的例外）、
  **② 服务端行为成立但整条链路当前不可达**（见下一条 P0 缺陷）。
- **P0 缺陷（新发现，计划里没写）**：`estimated` 标志从未写进数据库——`sale-orders/actions.ts:474-488`
  的 `saleOrderItem.create` 缺少 `estimated` 字段（`rowsItem.estimated` 在 468 行被算出来却没用）。
  后果：估价行服务端行为正确（不占库存/不补货/成本 0），但落库后 `estimated=false`，
  于是单据详情不显示估价标签、`/pending-estimates` 永远查不到（`pending-estimates/page.tsx:36`）、
  `fillEstimatedAction` 直接被 `pending-estimates/actions.ts:63` 拒绝。整条估价闭环目前不可达。
- **P0 缺陷（新发现）**：进货退货单号序号从**错误的表**取——`purchase-returns/actions.ts:107`
  用 `tx.purchaseOrder.findMany` 查 `PRF` 前缀，恒为空 → 当日第 2 张进货退货单必然 P2002 重试 3 次后失败。
- 编号规则：前缀 + `yyyyMMdd` + 4 位序号，唯一索引兜底 + 事务内"取当日最大序号+1" + P2002 重试 3 次
  （`src/lib/order-no.ts:25-33`，`sale-orders/actions.ts:116-137,502-504`）。日单量 > 9999 时序号解析失效。
- 售卖单创建**即**出库并写成本快照（无"确认发货"步骤）；进货单创建 ≠ 入库，需 `receivePurchaseOrderAction`
  （`purchase-orders/actions.ts:175-249`）；例外：售卖单触发的自动补货进货单创建时即 `status=received`
  并直接入库（`sale-orders/actions.ts:360,376`）。

关于金额/数量类型的逐字段核实结论：**全表无 `Float`、无 `Int` 计金额**
（`grep -n "Float\|BigInt" prisma/schema.prisma` 只命中 `audit_logs.entity_id` 的 `BigInt?`，schema:150）。
单价/参考价/退货价一律 `Decimal(12,2)`；单据总额/行金额/成本金额一律 `Decimal(14,2)`；
数量与库存数量一律 `Decimal(12,3)`；库存均价 `Decimal(12,4)`；流水单位成本 `Decimal(12,4)`。
`stock_amount` 是唯一的 `(14,2)` 金额列与 `(12,3)` 数量的组合，因此"金额 = 数量 × 均价"必然有舍入差，
由 `applyStockChange` 的 `round2/round4` 收口（`src/lib/stock-cost.ts:27-28,47,52`）。

外键行为（`prisma/migrations/20260902135505_init/migration.sql:344-`）：单据行 → 单据头 `onDelete: Cascade`；
`purchase_orders.source_sale_order_id` → `SetNull`；`orders.operator_id`、`supplier_id`、`product_id`、
`unit_id` 一律 `RESTRICT`；`audit_logs/login_logs.user_id` 为 `SetNull`。
**`stock_movements` 没有外键**（init 迁移里没有为它 AddForeignKey，只建了索引，migration.sql:320-340），
`payments.order_id`、`sale_order_items.estimated_purchase_order_id` 同样无 FK（schema:544,435）。

## 3. 业务不变量逐条判定

### ① 移动加权成本按单据快照，不能回溯改历史单据 —— ✅成立（措辞需收紧）

- 快照字段：`sale_order_items.cost_amount`（`prisma/schema.prisma:421`），
  计算公式 `costAmount = round2(stockCost + purchaseCost)`（`sale-orders/actions.ts:456-470`）：
  - `stockCost = 使用库存数量 × 扣减前的 avg_cost`（`sale-orders/actions.ts:330-332`，
    均价在**扣减同事务内、扣减前**读取，第 325-330 行）；
  - `purchaseCost = 现场进货数量 × 开单时填写的进价`（`sale-orders/actions.ts:436`，注释 434-435）。
- 唯一的两个写点：创建时一次写定（`sale-orders/actions.ts:483`）、估价补单写回（见 ②）。
  **没有**任何"改单=原地更新历史行"的代码（全仓只有两处 `saleOrderItem` 写操作：
  `sale-orders/actions.ts:475` create、`pending-estimates/actions.ts:114` update）。
- 改单的既有实现确实是"作废 + 重开"：详情页「改单」= 先 `voidSaleOrderAction` 作废，
  成功后 `router.push('/sale-orders/new?fromOrder=<id>')` 用原单内容预填再走一次创建
  （`src/app/(main)/sale-orders/[id]/detail-actions.tsx:46-50,83-106`；重开由
  `createSaleOrderAction` 生成**新订单号**，新单与旧单之间**没有** `revisionOf` 之类字段，
  旧单状态终态为 `voided`，`sale-orders/actions.ts:604-607`）。
- 需要收紧的措辞：**作废冲回不用快照价，用冲回当时的 `avg_cost`**
  （`sale-orders/actions.ts:543`、`purchase-orders/actions.ts:322`），所以"作废+重开"的净效果
  不等于把库存恢复原样——这一点计划里没写，CLI 的 dry-run 摘要必须体现。

### ② 估价行不占库存、不参与成本、不自动进货 —— ⚠️服务端行为成立，但标志未落库（当前整条链路不可达）

服务端三条都成立，逐条证据（`src/app/(main)/sale-orders/actions.ts`）：

| 断言 | 实现 | 证据 |
|---|---|---|
| 不占库存 | `stockUsed = estimated ? 0 : …`，且 `requested` 之和不进库存流水 | 269；sale_out 流水只在 `stockUsed>0 / purchaseQty>0` 时写（323-350、425-454） |
| 不参与成本 | `purchaseCost=0`、`stockCost=0` → `costAmount=0` | 305-306、459 |
| 不自动进货 | `purchaseQty/extraQty = 0` → `restockTotal=0` → 不 push 到 `autoGroups` | 270-274 |

补单实现（与计划描述一致，`src/app/(main)/pending-estimates/actions.ts`）：
`requireAdmin`(43-44) → 校验是估价行/未补过/原单未作废(63-65) → 事务内建 **`status:"pending"`** 的进货单
（87-111，`sourceType:"auto"`、`sourceSaleOrderId` 指向原售卖单 92-93）→ 成本写回原行并打
`estimatedResolvedAt` + `estimatedPurchaseOrderId`(114-117) → 顺手改商品名/厂家(119-125) → 审计(130-143)。
**库存要等这张进货单"确认入库"**，符合第 ④ 条，路径正确。

❌ **缺口**：`estimated` 从未落库。
`rowsItem.push({ …, estimated: p.estimated })`（468）之后，创建行时没有传该字段
（`sale-orders/actions.ts:474-488` 的 data 只有 saleOrderId/productId/quantity/unitId/unitPrice/amount/
costAmount/stockQtyUsed/remark）。`git blame` 显示 239fdf22（2026-09-14）加了 468 行但没改 create。
后果链（每条可复现）：
- `/pending-estimates` 过滤 `estimated: true, estimatedResolvedAt: null`（`pending-estimates/page.tsx:36`）→ **永远为空**；
- `fillEstimatedAction` 第一步就 `if (!item.estimated) return { error: "这一行不是估价行" }`（`pending-estimates/actions.ts:63`）；
- 售卖单详情的「N 行估价待补」提示与行内标签（`sale-orders/[id]/page.tsx:149-151,204-209`）不显示。
- 另有一处相邻缺陷：行单位。表单支持估价行选单位/当场新建（`item_${i}_unitId`，解析进 `it.unitId`，
  `sale-orders/actions.ts:105`），并放进 `plans[].unitId`（303），但落库时用的是商品单位
  （`unitId: productMap.get(r.productId)!.unitId`，480），`plans[].unitId` 全文件再无读取点（`grep unitId` 仅 290/303/399/480）。

### ③ 估价行没有"改成普通行"的操作 —— ✅成立

- 开单表单：普通行只能「标为估价」（单向 `setRows(… estimated: true)`），
  已是估价行时只渲染一个静态徽标，注释明确"不给取消"（`src/app/(main)/sale-orders/new/new-sale-form.tsx:1812-1839`）。
- 服务端同样没有反向接口：没有任何 action 把 `estimated` 从 true 改回 false（全仓 `estimated:` 写点见
  `grep -rn "estimated:" src/`，只有 468 行的内存对象与 `pending-estimates/actions.ts:114` 的"标记已补"）。
- 编辑既有单据本身不存在（无 edit/update 单据入口），所以"估价行改普通行"没有入口。

### ④ 库存只能通过"确认入库"进来 —— ⚠️部分成立（有一个明确例外）

- 进货单创建 ≠ 入库：`createPurchaseOrderAction` 写 `status:"pending"`，**不碰库存**
  （`purchase-orders/actions.ts:136-147`；库存写入只在 `receivePurchaseOrderAction:207-227`，且 189 行强制
  `status !== "pending"` 直接拒绝）。
- 售卖单侧：`stockUsed / purchaseQty / extraQty` 三分拆分（`sale-orders/actions.ts:266-272`，表单侧
  `new-sale-form.tsx:1561,1571`），**售卖单创建即出库**（sale_out 流水 338-349、442-453 与成本快照 456-470），
  不存在"售卖单确认出库"的第二步。
- 完整库存写点清单（`bizType` × 位置，全部落在 4 个 action 文件里：
  sale-orders / purchase-orders / sale-returns / purchase-returns；`product.update` 的其它写点
  只改商品档案字段，见 `products/actions.ts:126,185`、`pending-estimates/actions.ts:124`）：
  - `purchase_in`：进货确认入库 `purchase-orders/actions.ts:216-227`；**售卖单自动补货单创建时**
    `sale-orders/actions.ts:376-392`；
  - `sale_out`：售卖单创建 `sale-orders/actions.ts:338-349`（用库存）、`442-453`（现场进货）；
  - `sale_return_in`：售卖退货创建 `sale-returns/actions.ts:142-158`；
  - `purchase_return_out`：进货退货创建 `purchase-returns/actions.ts:136-152`；
  - `void_reverse`：售卖单作废 `sale-orders/actions.ts:548-559`、级联作废自动补货单 `578-589`、
    进货单作废 `purchase-orders/actions.ts:327-338`、售卖退货作废 `sale-returns/actions.ts:231-242`、

### ⑤ 退货如何冲减（计划标"待核实"） —— ✅已核实；冲减是"读取时动态扣减"，不写回原单

**售卖退货**（`src/app/(main)/sale-returns/actions.ts`）：

| 维度 | 实际做法 | 证据 |
|---|---|---|
| 前置 | 原单必须 `confirmed`；业务员只能退自己开的单 | 69-72 |
| 数量上限 | 可退 = 原行数量 − 已确认退货单累计（按 `saleOrderItemId` 汇总） | 74-82、96-98 |
| 库存 | `+quantity`，成本单价 = **原售卖行快照均价** `costAmount/quantity` | 105、140-146 |
| 流水 | `bizType: sale_return_in`，`bizOrderNo` = 退货单号（PRS…） | 147-158 |
| 行成本 | `sale_return_items.cost_amount = qty × 快照均价` | 170 |
| 应收 | **不写回原售卖单**；`应收 = totalAmount − receivedAmount − Σ已确认退货单 totalAmount`，读取时算 | `receivables-payables/page.tsx:128-130`、`src/lib/reports.ts:155,200`、付款校验 `receivables-payables/actions.ts:54-55` |
| 是否影响成本快照 | **不影响**：原售卖行 `cost_amount` 不动；但会用快照价回补库存，从而改变**当前** avg_cost（移动加权的固有性质，`sale-returns/actions.ts:142`） |

**进货退货**（`src/app/(main)/purchase-returns/actions.ts`）：

| 维度 | 实际做法 | 证据 |
|---|---|---|
| 前置 | 原单必须 `received`；业务员只能退自己开的单；**当前库存必须 ≥ 退货量** | 66-69、90-94 |

| 库存 | `−quantity`，成本单价 = **当前 avg_cost**（不是原进货价） | 136 |
| 流水 | `bizType: purchase_return_out` | 148 |
| 应付 | 同售卖，读取时动态扣减（`receivables-payables/page.tsx:115,152-156`） | 同左 |
| 是否影响成本快照 | 无进货成本快照表可影响；`−qty @ 当前均价` 使均价**保持不变**、金额按均价减少 | 136 |

**两条与"冲减"相关的实现缺口（计划里没写，CLI 必须按真实行为实现或先修）**：

1. 退货单作废是"按当时的 `avg_cost`"反向操作（`sale-returns/actions.ts:226`、`purchase-returns/actions.ts:216`），
   而回补时用的是快照价（142）。两者不等时，作废退货会让 avg_cost 永久偏移（不可逆）。
2. 售卖单作废不检查两点，会造出坏数据：
   - **不检查是否存在已确认退货**（`voidSaleOrderAction` 只判 `status`，`sale-orders/actions.ts:526-531`），
     作废时按 `item.quantity` **全额**回补库存（536-560）→ 已退数量被回补两次；
     且退货单仍是 `confirmed`，应收仍在被冲减。
   - **不区分估价行**：估价行从未出库，作废同样给它 `+quantity`（536-560 无 `estimated` 判断）→ 库存凭空增加。
   - 级联作废自动补货单时**不甄别 `po.status`**（562-590 只按 `sourceSaleOrderId` 关系取单），
     而 `fillEstimatedAction` 生成的进货单也是这个关系且 `status:"pending"`（`pending-estimates/actions.ts:92-93`）——
     作废含未补估价行的售卖单时，会对一张从未入库的 pending 进货单做**负库存流水**（578-589），
     或在库存不足时抛出"库存不足，无法级联冲回补货单"导致整单作废失败。

## 4. 单据编号 / 库存 / 成本快照 的实现细节

### 4.1 单据编号（`src/lib/order-no.ts`）

- 格式：`前缀 + yyyyMMdd + "-" + 4 位序号`，本地时区（`order-no.ts:25-27`；`todayCompact()` 17-23）。
- 前缀：PO 进货、SO 售卖、PRF 进货退货、PRS 销售退货、PAY 收款、POF 付款（`order-no.ts:6-13`）。
- 唯一性保证：`order_no` 列上的唯一索引（`prisma/schema.prisma:318,380,450,493,541`；
  初始化迁移里每张单据表都建了 `UNIQUE INDEX xx_order_no_key`，如
  `prisma/migrations/20260902135505_init/migration.sql:162` 的 `purchase_orders_order_no_key`、
  `prisma/migrations/20260902225143_payment_order_no/migration.sql:3` 的 `payments_order_no_key`）
  + 事务内"取当日同前缀最大序号 +1" + 捕获 P2002 重试最多 3 次：
  - 售卖单 `sale-orders/actions.ts:116-137`（`nextSeqOf`）、`216-222`、`502-504`（重试）；
  - 进货单 `purchase-orders/actions.ts:76-87`、`127-131`、`162-164`；
  - 售卖退货 `sale-returns/actions.ts:112-121,188`；进货退货 `purchase-returns/actions.ts:107-116,181`；
  - 补单 `pending-estimates/actions.ts:77-89,149`；收付款 `receivables-payables/actions.ts:76-87,126`。
- 并发行为：两个并发事务可能算出同一序号，落库时后者踩唯一索引 → `continue` 重开事务重算
  （重试上限 3 次，超限返回"单据号生成失败，请重试"）；**序号是"读最大值"而非锁行/自增序列**，
  所以不存在"拿到号就一定不撞"的保证，只靠唯一索引兜底。CLI 若直接建事务也必须照抄这套重试。
- ❌ **缺陷**：进货退货单号从错的表取序号——`purchase-returns/actions.ts:107` 是
  `tx.purchaseOrder.findMany({ where: { orderNo: { startsWith: PRF+日期 } } })`，
  `purchase_orders` 里不存在 PRF 号 → `maxSeq` 恒为 0 → 当日第 2 张进货退货单必然得到
  `PRF<日期>-0001` 与第一张相同 → P2002 → 重试 3 次仍相同 → 返回"单据号生成失败，请重试"。
  （对比：售卖退货用的是正确的 `tx.saleReturn.findMany`，`sale-returns/actions.ts:112`。）
- 序号解析 `/-(\d{4})$/`（`order-no.ts:30-33`）：日单量超过 9999 后序号变 5 位（`padStart(4)` 不截断），
  解析失败返回 0 → 又会拿到冲突序号 → 当日该类单据全部开不出来。上限是每天每类 9999 张。

### 4.2 库存字段与流水

- **余额的唯一真相是 `products.stock_qty / stock_amount / avg_cost`**（`prisma/schema.prisma:212-214`），
  每个写路径都在事务里"读三列 → `applyStockChange` → 写回"，不重新聚合流水。
  读路径同样用这三列：`inventory/page.tsx:100-110`（列表按 Product 分页）与
  `src/lib/reports.ts:76-83`（导出报表直接取 `p.stockQty/p.stockAmount/p.avgCost`）。
- `stock_movements` 的定位是**追加式流水**（schema:585 注释"唯一库存账本"），写入时机与库存变更同一事务、
  同一 `applyStockChange` 调用旁（见 §3 ④ 的清单）。它被读的地方只有：
  `stock-movements/page.tsx:56-57`（流水列表）、`inventory/page.tsx:87-95`（按进货时间筛选商品）、
  `inventory/page.tsx:119-135` 与 `src/lib/reports.ts:52-60`（"最近进价/最近进货时间"）。
  **没有任何地方用流水 SUM 来校验/重建余额**——即"账本"目前只是事实记录，不是对账依据。
- 流水字段：`changeQty` 正入负出、`beforeQty/afterQty`（改前改后，便于人工核对）、`unitCost`、
  `bizType`、`bizOrderNo`（单号，不是 FK）、`operatorId`、`createdAt`（schema:588-608）。
- 成本算法：`src/lib/stock-cost.ts:21-53`。正常分支 `新金额 = 原金额 + 变动量 × 单价`、`新均价 = 新金额 ÷ 新数量`(50-52)；
  清零归零(36-39)；负库存入库的"冲负优先"防御(41-48)；变动后为负则金额保持、均价不动(30-34)。
  舍入：金额 2 位、均价 4 位（27-28）。批量退化测试在 `tests/stock-cost.test.ts`（7 个用例）。
- 库存数量上界：写入前不做上限校验，但 `applyStockChange` 在 `newQty === 0` 时强制 `amount=0, avgCost=0`（36-39），
  这是"卖完/整单作废冲回"不留残余成本的实现。

### 4.3 成本快照

- 存放：`sale_order_items.cost_amount`（`Decimal(14,2)`，schema:421），行级单值，不存 unitCost；
  行均价按 `costAmount / quantity` 反算（读取方如退货 `sale-returns/actions.ts:105`）。
- 写入时机：仅两处——售卖单创建（`sale-orders/actions.ts:459,468,483`）、估价补单写回
  （`pending-estimates/actions.ts:71,114-116`）。
- 售卖退货另存一份回补成本 `sale_return_items.cost_amount`（schema:529，写入 `sale-returns/actions.ts:170`）。
- 进货侧没有任何成本快照：进货退货只动数量与应付，`purchase_return_items` 无 `costAmount`（schema:473-489）。
- 毛利口径依赖 `cost_amount`（读路径属第 3 轨，此处不展开）。

   与 `bizType: void_reverse` 组合（不是"冲回单"的号）是有意设计还是历史遗留，代码里没有说明。

   但库中是否有历史数据无法确认。
