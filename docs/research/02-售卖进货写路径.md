# 第 2 轨：售卖 / 进货 写路径调查

> 只读调查，证据均为 `file:line`（本文件写作时的 HEAD = `33d0714`）。
> 本轨覆盖：售卖单开单/作废/星标、进货单开单/确认入库/作废/星标、估价补单、开单页只读搜索。
> 不覆盖：退货、收付款（第 3 轨）；主数据与系统写路径（第 4 轨）；读路径与报表口径（第 5 轨）。

---

## 0. 摘要

1. 这条写路径只有 **11 个导出的写/读 action**，全部集中在 4 个 `"use server"` 文件里：`sale-orders/actions.ts`（3 个）、`purchase-orders/actions.ts`（4 个）、`pending-estimates/actions.ts`（1 个）、两个 `new/search-actions.ts`（6 个只读）。**没有独立的服务层**，也没有 `reopen`/编辑单的 action。
2. **权限没有集中 guard**：`src/lib/auth/guards.ts` 只有 `requireAdmin` / `requireMasterDataWrite` / `requireLogin`（guards.ts:9-32）。售卖/进货写路径各自手写 `requireSaleWrite`（actions.ts:78-83）、`requirePurchaseWrite`（purchase actions.ts:44-49），以及"用 `getCurrentUser()` + `role` 判定 + 返回 `{error}`"的三四种写法。计划文档里提到的 `requireUser` / `requirePurchaseUser` **在 guards.ts 里不存在**（`requirePurchaseUser` 只是 `purchase-orders/new/search-actions.ts:36` 的局部函数）。
3. 权限实际口径（逐个核实）：开售卖单 = 已登录且 role ≠ boss（actions.ts:81）；开进货单 = 已登录且 role ≠ boss（purchase actions.ts:47）；确认入库 = 已登录且 role ≠ boss，且 sales 只能操作自己开的单（purchase actions.ts:181,190）；作废单据 = 已登录且 role ≠ sales（即 admin/boss）（sale actions.ts:520、purchase actions.ts:258）；星标 = 已登录（sales 限自己的单）（sale actions.ts:643）；**补单 = 仅 admin**（pending-estimates/actions.ts:43-44）。
4. **库存只有一个入口函数** `applyStockChange`（`src/lib/stock-cost.ts:21-53`），移动加权公式在 stock-cost.ts:50-52。售卖单开单会同时产生 3 类库存流水：`sale_out`（用库存）、`purchase_in`（自动补货单，**生成即入库**）、`sale_out`（现场进货部分）；作废全部走 `void_reverse`（sale actions.ts:338,381,442,548,578）。
5. **作废会回滚库存，但不回改成本快照**：`SaleOrderItem.costAmount` 永不被作废流程触碰（全库唯一写入点是 sale actions.ts:483）；冲回按**当前**均价计价（sale actions.ts:543,573；purchase actions.ts:322），因此"原扣出成本"与"冲回成本"在均价漂移后**不相等**，是现存口径缺口。
6. **改单 = 作废原单 + 用原单内容预填新单**（计划文档的说法**成立**）：详情页"改单"按钮提交的就是 `voidSaleOrderAction`/`voidPurchaseOrderAction`，成功后 `router.push("/sale-orders/new?fromOrder=<id>")`（sale `[id]/detail-actions.tsx:46-50,83-106`；purchase `[id]/detail-actions.tsx:48-52,91-114`），预填在页面里用只读查询拼（`sale-orders/new/page.tsx:36-124`）。**没有任何原地 update 的编辑 action。**
7. **`estimated` 估价行存在端到端断点**：schema 与补单侧齐备（`sale_order_items.estimated/estimated_resolved_at/estimated_purchase_order_id`，schema.prisma:431-435；`fillEstimatedAction` 要求 `item.estimated === true`，pending-estimates/actions.ts:63），但**开单侧从不把 `estimated` 写进 `saleOrderItem.create`**（sale actions.ts:475-487 的 data 里没有该字段；全仓库 `saleOrderItem.create` 只此一处）。后果：估价行落库后 `estimated=false`，既不会出现在 `/pending-estimates`（page.tsx:36 按 `estimated: true` 过滤），也无法用 `fillEstimatedAction` 补（直接返回"这一行不是估价行"）。
8. 并发的唯一兜底是 `orderNo` 的 `@unique`（schema.prisma:318,380）+ 3 次重试（sale actions.ts:216,502；purchase actions.ts:127,162；pending-estimates/actions.ts:73,149）。**状态类前置校验都在事务外**（sale actions.ts:531、purchase actions.ts:189/269、pending-estimates/actions.ts:64），重复/并发提交可能"双次冲回库存"或"双开补单"。
9. 审计：写路径基本都调了 `writeAudit`，但**在 `$transaction` 回调里调用它并不会跟着回滚**（audit.ts:35 用全局 `prisma`，不是 `tx`）。缺失项：`fillEstimatedAction` 顺带改商品名/厂家（pending-estimates/actions.ts:124）没有写 `entityType: "product"` 的审计；`createSaleOrderAction` 里自动建档的厂家（sale actions.ts:200-211）审计写在事务外，事务失败会留下幽灵审计。
10. CLI 侧的缺口不在"少了 action"，而在：无可注入的 actor（全靠 `cookies()`）、无 dry-run、无 `--json` 结构化返回（action 返回 `{error|ok: string}` 或 `redirect()`）、开单草稿只在 localStorage（`src/lib/form-draft.ts:75-88`）、改单预填只在页面里拼。

## 2. 售卖单写路径细节（`createSaleOrderAction`，actions.ts:139-511）

### 2.1 输入形状（表单 → schema）
- FormData 约定：顶层 `customerId`、`remark`、`starred`("1"/"")；行字段 `item_${i}_productId|quantity|unitPrice|supplyPrice|supplierId|extraQty|remark|stockUsed|estimated|unitId`（`parseCreatePayload` actions.ts:85-114，与 `new-sale-form.tsx:1782-2036` 一一对应）。
- 空行（`item_i_productId` 为空）会被跳过（actions.ts:90-93），所以"加了行没填"不阻塞提交。
- **表单实际不下发 `item_i_supplierId`**：`new-sale-form.tsx` 里没有任何该 name 的输入（全文件 grep `item_${i}_` 只有 productQuery/productId/estimated/unitPrice/quantity/unitId×2/stockUsed/supplyPrice/extraQty/remark，见 :1726-2036）。也就是说 UI 无法指定补货厂家，服务端只能靠 `product.manufacturer`。但 schema 接受 `supplierId`（actions.ts:41,99）→ **CLI 可以传行级厂家，网页不能**。
- **行级 `unitId` 收了但没用**：`saleOrderItem.create` 写的是 `unitId: productMap.get(r.productId)!.unitId`（actions.ts:480），而计划里的行单位 `p.unitId`（= `it.unitId ?? product.unitId`，:303）只存在于内存。所以"估价行可就地新建单位"（new-sale-form.tsx:380-395）落库后无效。

### 2.2 各项校验（顺序即代码顺序）
1. 权限（78-83）→ 2. zod（144-147）→ 3. 客户存在且 `status === 1`（152-153）→ 4. 商品全部存在且 `status === 1`（156-163，任一停用即整单拒绝）→ 5. 缺货行必须有厂家的兜底：优先行级 `supplierId`、否则 `product.manufacturer`（trim 后非空），都没有则报「商品 #x 缺货且无厂家，请选择补货厂家」（167-182）→ 6. 行级厂家的 `supplier.status === 1` 校验（183-189）→ 7. **按厂家名自动建档**：`supplier.findMany({name in mfrNames})` → 缺失的 `supplier.create({name})`（191-214，**事务外**）。
- 事务内还有两道库存硬校验：`cur.qty < p.stockUsed`（331）、`cur.qty < p.purchaseQty`（433）——因为自动补货已先入库，所以第二道通常能过（等于"先买后卖"）。

### 2.3 逐行拆分（`plans`，actions.ts:260-308）
| 概念 | 代码 | 计算 |
|---|---|---|
| 用库存 | `stockUsed`（267-269） | `estimated ? 0 : min( it.stockUsed == null ? min(stock, qty) : max(it.stockUsed, 0), stock, qty )`；**留空 = 尽量用库存，填 0 = 全部现场进货** |
| 需进货 | `purchaseQty`（270） | `estimated ? 0 : max(qty - stockUsed, 0)`（不落库，只决定补货单数量） |
| 多补 | `extraQty`（271） | `estimated ? 0 : max(it.extraQty ?? 0, 0)`；只进备货，不计入客户 |
| 补货总量 | `restockTotal`（272） | `purchaseQty + extraQty` → 汇总进 `autoGroups`（按 supplierId 分组，274-293） |
| 估价 | `estimated`（265） | 三者全 0、成本 0、不生成补货单 |

### 2.4 库存与成本处理（事务内，严格 4 步）
1. `saleOrder.create` status=`confirmed`、`totalAmount=0` 占位（309-320）。
2. **①-a 扣「用库存」**（322-350）：成本取**扣减前** `avgCost`；`p.stockCost = stockUsed × cur.avgCost`；`applyStockChange(cur, -stockUsed, cur.avgCost)`；写 `stockMovement` `bizType="sale_out"`、`unitCost=cur.avgCost`。
3. **①-b 自动补货进货单**（352-422，按厂家循环）：`purchaseOrder.create({status:"received", sourceType:"auto", sourceSaleOrderId, receivedAt: now})` ——**生成即入库**；每行 `applyStockChange(before, +quantity, supplyPrice)`（376，`quantity = restockTotal`，含多补）＋`stockMovement` `purchase_in`；`purchaseOrderItem.create` 里 `restockQty = stockExtra`（398）；审计（405-421）。
4. **② 扣「现场进货」部分**（424-454）：此时均价已含本次进货，但客户成本按**开单时填的进价**：`p.purchaseCost = purchaseQty × p.supplyPrice`（436）；库存扣减仍走 `applyStockChange(cur, -purchaseQty, cur.avgCost)`（437）+ `sale_out` 流水。
5. **成本快照**（456-470）：`costAmount = stockCost + purchaseCost`，`avgCost = costAmount / qty`（**注意这里的 avgCost 只是本次计算用的中间值，不落库**）。
6. `saleOrder.update {totalAmount}`（473）+ 逐行 `saleOrderItem.create`（475-487：`quantity/unitPrice/amount/costAmount/stockQtyUsed/remark`）。
7. 事务外：审计 `sale_order/create`（492-498，after 只有 `{orderNo, customerId, totalAmount}`——**不含行明细与库存影响**）→ `revalidatePath("/sale-orders")`（499）→ `redirect("/sale-orders")`（500）。
- **revalidate 缺口**：本 action 还会创建进货单、改库存，但只 revalidate 了 `/sale-orders`（499），没有 `/purchase-orders`、`/inventory`、`/stock-movements`。

## 3. 进货单写路径细节

### 3.1 创建（`createPurchaseOrderAction`，purchase actions.ts:89-173）
- 校验：权限（93）→ zod（95-97）→ 厂家存在且 `status === 1`（102-103）→ 商品存在且 `status === 1`（106-113）；`unitId` 强制取商品默认单位（120，注释"不做换算，单单位制"）。
- 副作用：**只写单据，不动库存**。`purchaseOrder.create` 内嵌 `items.create`（136-149），`status="pending"`、`sourceType="manual"`、`totalAmount = Σ round2(qty × unitPrice)`；审计写在同一事务里（150-156）→ 但见 §7 的注记（`writeAudit` 用全局 client，不参与回滚）。
- 成功 `redirect("/purchase-orders")`（160）；`P2002` 重试（162-164）；`NEXT_REDIRECT` 必须 rethrow（165-167），否则会被当成"开单失败"。

### 3.2 确认入库 / 成本重算（`receivePurchaseOrderAction`，purchase actions.ts:175-249）
- 前置：登录且非 boss（181）；单据存在（188）；**`status !== "pending"` 即拒**（189）；sales 只能入库自己开的单（190-192）。
- 成本重算就是 `applyStockChange(before, +quantity, unitPrice)`（207）→ 公式在 `src/lib/stock-cost.ts:50-52`：
  - 正常分支：`amount = max(state.amount + change × costPrice, 0)`（50）；`avgCost = amount / newQty`（51）；金额 round2、均价 round4（52）。
  - 防御分支：新库存 <0 → 保持原金额与原均价（30-33）；恰好清零 → 金额与均价归零（36-39）；原库存为负 → 负数部分按原均价回补、剩余按新价（41-48）。
- 写：`product.update {stockQty, stockAmount, avgCost}`（208-215）、`stockMovement` `bizType="purchase_in"`、`unitCost=item.unitPrice`（216-227）、`purchaseOrder.update {status:"received", receivedAt}`（229-232）；审计 `purchase_order/receive`（234-241）；`revalidatePath` 单据与列表（242-243）。
- `PurchaseOrderItem` 上**没有成本快照字段**：单行进价只有 `unitPrice`（schema.prisma:364），入库后成本只体现为 `Product.avgCost` 与 `StockMovement.unitCost`。

### 3.3 作废（`voidPurchaseOrderAction`，purchase actions.ts:251-360）
- 两条分支：
  - `status === "pending"`（270-291）：仅改状态 + 审计 + revalidate，`{ok:"已作废（未入库，无库存影响）"}`。
  - 已入库（293-355）：先在事务外逐行校验 `product.stockQty >= item.quantity`，不足则**拒绝并引导走进货退货**（294-306，文案含具体数字）；事务内按**当前均价**冲回：`applyStockChange(before, -quantity, before.avgCost)`（322）+ `void_reverse` 流水（327）+ 状态置 `voided`（340）。
- 与售卖单作废的差别：进货单作废**有**库存充足性校验，售卖单作废**没有**（sale actions.ts:534-608 全程只做加法）。

## 4. 作废 / 改单 的确切实现（回答点名问题 1 与 3）

### 4.1 作废是否回滚库存？成本快照会回改吗？
- **回滚库存：是。** 售卖单按整行 `item.quantity` 加回（sale actions.ts:543，`applyStockChange(before, +quantity, before.avgCost)`），流水 `bizType="void_reverse"`（548）；其随单自动补货单级联作废并按 `item.quantity` 冲减（562-590，**该分支有库存不足校验**，570-572），补货单状态 `voided` + `voidReason="随售卖单作废：SOxxx"`（591-594）。进货单已入库分支同样冲回（purchase actions.ts:322-338）。
- **成本快照：不会回改。** `SaleOrderItem.costAmount` 全仓库只有一处写入（sale actions.ts:483，开单时），作废流程只改 `SaleOrder.status/voidedBy/voidedAt/voidReason`（sale actions.ts:604-607）；`PurchaseOrderItem` 无成本快照。
- **但冲回价不是原扣出价**：扣出时用 `cur.avgCost`（332/436/448），冲回时用 `before.avgCost`（543/573）——即"当前均价"。均价在中间被其它单据改变后，库存数量账平但**库存金额账不平**，同时作废单的 `costAmount` 仍按原快照参与毛利，形成"作废单毛利不变而库存金额变了"的口径缺口。（本轨只报事实，是否可接受需第 5 轨报表口径一起判断。）
- 作废**没有**任何"单据已有退货/收款就不能作废"的校验：`voidSaleOrderAction` 只 include `items` 与 `autoRestockOrders`（526-529），`voidPurchaseOrderAction` 只 include `items`（264-267）；详情页按钮条件 `canVoid = admin || boss` 与退货无关（sale `[id]/page.tsx:71,283`；purchase `[id]/page.tsx:66`）。

### 4.2 作废的单还能不能改？
- **不能原地改，也没有任何编辑 action。** 全仓库 grep `reopen|改单|revisionOf` 的结论：只有页面/组件级别的"改单"按钮与预填逻辑，服务端只有 `void*Action` 与 `create*Action`。
- 证据链（售卖单）：`[id]/detail-actions.tsx:38-50`（`form === "reopen"` 提交的是 `voidSaleOrderAction`，成功后 `router.push('/sale-orders/new?fromOrder=' + orderId)`）→ `:83-106`（表单字段 `id` + `reason`，默认值"改单"）→ `sale-orders/new/page.tsx:36-53`（读原单 `include items/autoRestockOrders`）→ `:90-124`（拼 `prefill`，含 `stockUsed` 由 `it.stockQtyUsed` 回填、`supplyPrice/supplierId/extraQty` 从 `autoRestockOrders` 的 `PurchaseOrderItem` 回填）→ `new-sale-form.tsx:848`（"正在改单：原单 SOxxx"横幅）→ 提交走正常 `createSaleOrderAction`。
- 进货单同构：`purchase-orders/[id]/detail-actions.tsx:36-52,91-114` → `purchase-orders/new/page.tsx:26-40,120-139` → `new-order-form.tsx:397`。
- **计划文档第 3 节第 1 条"改单 = 作废原单 + 重开新单"✅ 成立**；新单与原单**没有任何关联字段**（`SaleOrder` 无 `revisionOf`，schema.prisma:378-408），改单前后只能靠 `remark`（默认写"改单"）+ 审计时间人工对。
- 未作废的单也可以点"改单"（按钮只在 `voided` 时隐藏，`detail-actions.tsx:62`），服务端 `voidSaleOrderAction` 也不检查"是不是改单"——改单语义完全由前端意图（`reopenIntent`）承载，**CLI 若只调 action 无法表达"这是改单"**。
- 详情页还提示"打印稿里的修改不会保存，如需修改订单请用「作废后重开」或退货"（`src/app/sale-orders/[id]/print/print-editor.tsx:695`）——与代码一致。

## 5. 估价行与补单（回答点名问题 4）

### 5.1 schema 表示

### 5.2 开单侧（重要：字段没落库）
- 表单开关在每行最前（`new-sale-form.tsx:1784, 1820-1838`），打开后：用库存置灰（1944）、需进货显示"待补"（1979）、进价禁用（1989）。

- 后果（代码推断，DB 内容未核实）：估价行落库为 `estimated=false`，`/pending-estimates` 查不到（page.tsx:36 `where { estimated: true, estimatedResolvedAt: null }`），详情页不显示"估价待补"角标（`[id]/page.tsx:149-151,204-209`），`fillEstimatedAction` 会返回"这一行不是估价行"（pending-estimates/actions.ts:63）。**补单闭环在开单侧断开**。该字段在 `239fdf2`（估价待补开单侧）引入时就未写入——`git log -S` 显示该文件只有这一个提交涉及 estimated，故不是后续被删掉的。

### 5.3 `fillEstimatedAction` 逐步拆解（pending-estimates/actions.ts:42-155）
1. **权限**：`requireAdmin().catch(() => null)`，非 admin → `{error:"仅管理员可补单"}`（43-44）。页面侧 `canFill = role === "admin"`，`sales` 连页面都进不去（page.tsx:30-33）。
2. **校验**：zod（14-24，`unitPrice` 必须 >0）；`item` 不存在 → "找不到这一行"（62）；`!item.estimated` → "这一行不是估价行"（63）；`item.estimatedResolvedAt` → "这一行已经补过了"（64）；`item.saleOrder.status !== "confirmed"` → "原售卖单已作废，无需补单"（65）；`supplier` 必须存在（68）。
3. **事务内顺序**（75-128）：
   - a. 取当日 PO 最大序号（77-85，与手工开单同一套 `PO+yyyyMMdd+4位`，`buildOrderNo` order-no.ts:25-27）；
   - b. `purchaseOrder.create`：**`status="pending"`（待收货，不动库存）**、`sourceType="auto"`、`sourceSaleOrderId = 原售卖单`、`remark="估价补单（原单 SOxxx）"`、`operatorId = admin.id`、`totalAmount = round2(qty × unitPrice)`，内嵌一行 item（`unitId=商品单位`、`quantity=qty`、`unitPrice`、`amount`、`restockQty=qty`）（87-111）；
   - c. **回写哪一行**：`saleOrderItem.update { costAmount, estimatedResolvedAt: new Date(), estimatedPurchaseOrderId: po.id }`（114-117）；
   - d. **顺带补正商品档案**（119-125）：`productName` 与当前名不同则改 `name`；`supplier.name` 与商品 `manufacturer` 不同则改 `manufacturer`——**这一步没有单独的 product 审计**（见 §6）。
4. **事务外**：审计 `entityType="sale_order_item"`、`action="update"`，`before={estimated:true, costAmount}`、`after={补单进货单: orderNo, supplierId, unitPrice, costAmount, 商品改名}`（130-143）；`revalidatePath` `/pending-estimates`、`/purchase-orders`、`/sale-orders/[id]`（144-146）。
5. **库存变化**：本 action **不改库存**；库存要再到进货单点"确认入库"（page.tsx:78-81 的说明与 purchase actions.ts:195-233 一致）。
6. 返回：`{ok:"已生成进货单 POxxx（待收货），成本 ¥x 已写回本行"}`。
7. 幂等/并发：`P2002` 重试 3 次（149）；`estimatedResolvedAt` 的"已补"判定在事务外读取（64），并发两次调用可各生成一张补单（唯一约束只在 orderNo 上，同一 `itemId` 无唯一约束）。

### 5.4 估价行的"入口"依赖主数据写路径
表单里"加一行估价商品（临时名）"是两步：先 `createQuickProductAction({name, manufacturer, unitId, ...})` 建商品（products/actions.ts:214-235，仅 admin），再把新商品挂成 `estimated: true` 的行（new-sale-form.tsx:343-377），单位还能就地新建（`createQuickUnitAction`，new-sale-form.tsx:380-395）。CLI 的 `estimate add-row` 必须复刻这两步。
