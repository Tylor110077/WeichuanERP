# 第 3 轨：退货与收付款写路径（调查结论）

> 只读调查，全部结论带 file:line。仓库根 `/Users/tylor/Code/WeichuanERP`。
> 对应 `docs/agent-cli-plan.md` 第 3 节第 5 条（退货如何冲减）与第 9 节第 3 条（收付款记账口径与单据关联）。

---

## 0. 摘要

1. **退货不改历史单据**：售卖退货与进货退货都**只新增单据 + 新增库存流水**，从不回写原单行、不重算原单成本快照（`sale-returns/actions.ts:161-172`、`purchase-returns/actions.ts:155-165`）。
2. **售卖退货入库用「原单成本快照均价」**：`costSnapshotPrice = saleOrderItem.costAmount / saleOrderItem.quantity`，流水 `bizType=sale_return_in`、数量为正（`sale-returns/actions.ts:105,142,147-158`）；退货行的 `costAmount` 落库（`SaleReturnItem.costAmount`，schema:535）。
3. **进货退货出库用「当前移动加权均价」**：`applyStockChange(before, -qty, before.avgCost)`，流水 `bizType=purchase_return_out`（`purchase-returns/actions.ts:136,141-152`）；退货价（默认＝原进价）只用于金额与应付冲减，`PurchaseReturnItem` **无 costAmount 字段**（schema:473-489）。
4. **应付/应收不靠付款表求和**：余额 = `单据总额 − received_amount/paid_amount（冗余列） − Σ 未作废退货单 total_amount`，付款登记时用 `increment` 同步冗余列（`receivables-payables/actions.ts:99-109`）。SQL 口径见 `receivables-payables/page.tsx:90-120` 与 `dashboard/page.tsx:39-57`。
5. **一笔付款只挂在「一张单」上**（`Payment.orderType + orderId`，schema:543-544），**不支持一笔核销多单、不支持预收/预付**；`PaymentOrderType` 里的 `sale_return`/`purchase_return` 全仓库无人写入（无退款流程）。
6. **收付款只能作废（红冲），不能改**：`voidPaymentAction` 把 `status=voided` 并 `decrement` 回单据冗余列（`receivables-payables/actions.ts:147-164`）；无 update/delete 路径。
7. **审计覆盖本轨道 100%**：6 个写 action（退货 create/void ×2、收付款 create/void）全部 `writeAudit`；但审计写在事务**之外**（`sale-returns/actions.ts:177` vs 事务 111-176）。
8. **发现一个真实 bug**：进货退货单号序号生成查错了表（查 `purchaseOrder` 而非 `purchaseReturn`），导致**当天第二张进货退货单必然失败**（`purchase-returns/actions.ts:107-116` + 181-186 的 P2002 重试）。
9. **超退只靠「读—判断—写」，无唯一约束/行锁**：可退余量在事务外计算（`sale-returns/actions.ts:74-98`、`purchase-returns/actions.ts:72-94`），并发两次提交可超退。
10. **口径不一致**：应收应付/单据列表/单据详情/应收应付报表**冲减**退货；而工作台「今日销售额」、进销存汇总、销售排行、操作员业绩**完全不冲减**退货（`reports.ts:107-109`、`dashboard/page.tsx:22-26`）。

## 1. 退货：数据模型与冲减口径

### 1.1 模型（prisma/schema.prisma）

| 模型 | 行号 | 关键字段 |
|---|---|---|
| `PurchaseReturn` | 448-471 | `orderNo`(unique) / `purchaseOrderId`→原进货单 / `supplierId` / `totalAmount`（注释即「应付冲减」）/ `remark` / `operatorId` / `status`(ReturnOrderStatus=confirmed\|voided) / `voidedBy/voidedAt/voidReason` |
| `PurchaseReturnItem` | 473-489 | `purchaseReturnId` / `purchaseOrderItemId`（**行级关联原单分录**，无 unique）/ `productId` / `quantity`(12,3) / `unitId` / `unitPrice`(退货价) / `amount`；**无 costAmount** |
| `SaleReturn` | 491-514 | `orderNo`(unique) / `saleOrderId` / `customerId` / `totalAmount`（「应收冲减」）/ `remark` / `operatorId` / `status` / void 三件套 |
| `SaleReturnItem` | 516-537 | 同上 + `costAmount`（「按原单成本快照回补库存成本」，schema:535） |
| `ReturnOrderStatus` | 36-39 | `confirmed` / `voided`（**默认 confirmed**，schema:461/504） |

约束：只有 `order_no` 唯一（`prisma/migrations/20260902135505_init/migration.sql:239,274`）。
`purchaseOrderItemId` / `saleOrderItemId` **没有唯一索引、没有 CHECK、没有触发器** —— 超退在 DB 层无兜底。

### 1.2 售卖退货：冲减口径（`src/app/(main)/sale-returns/actions.ts`）

- **库存**：**增加**（退货入库）。`applyStockChange(before, +quantity, costSnapshotPrice)` → 写 `Product.stockQty/stockAmount/avgCost`（`:142-146`），并插入一条**正向**库存流水 `changeQty=+quantity`、`unitCost=costSnapshotPrice`、`bizType="sale_return_in"`、`bizOrderNo=退货单号`（`:147-158`）。
- **成本价来源**：**原单成本快照的均价**，不是当前加权成本：
  `costSnapshotPrice: Number(row.costAmount) / Number(row.quantity)`（`:105`，注释 `:90`「按原单成本快照回补」，`:141`）。
  → 若原单该行是「估价待补」（`costAmount=0`），退货入库成本价即为 **0**（`sale-orders/[id]/page.tsx:149-154` 说明估价行成本为 0）。
- **是否重算成本快照**：**否**。原 `SaleOrderItem.costAmount` 不被修改；退货行的成本另存到 `SaleReturnItem.costAmount = round2(quantity × costSnapshotPrice)`（`:170`）。**不重算移动加权**以外的任何东西，也不改 `stockQtyUsed`。
- **金额**：`totalAmount = Σ round2(quantity × 退货单价)`，退货单价由表单传（页面默认＝原售价，`sale-returns/new/page.tsx:78`），最后 `update` 回单头（`:174`）。
- **remark**：action 从不写入（`:123-131` 的 create data 无 remark）→ **退货单备注永远为 NULL**，表单也没有备注输入框（`return-form.tsx` 全文无 remark）。
- **事务**：单头 create + 每行商品 update + 流水 + 行 create + 单头 update 全在 `prisma.$transaction`（`:111-176`）。

### 1.3 进货退货：冲减口径（`src/app/(main)/purchase-returns/actions.ts`）

- **库存**：**减少**（退货出库）。`applyStockChange(before, -quantity, before.avgCost)`（`:136`）→ 流水 `changeQty=-quantity`、`unitCost=当前avgCost`、`bizType="purchase_return_out"`（`:141-152`）。**按当前移动加权均价出库，不按原进价**。
- **前置库存校验**：事务**外**先读 `Product.stockQty`，不足则报错「请先补货」（`:90-94`）。事务内不复查（并发下 `applyStockChange` 会走负数防御分支，schema/`stock-cost.ts:30-34` 允许负库存）。
- **退货价**：`unitPrice` 由表单传（默认＝原进货单价，`purchase-returns/new/page.tsx:78`），只用于 `PurchaseReturnItem.amount` 与单头 `totalAmount`。
- **与应付的联动**：**不是**改 `PurchaseOrder.paidAmount`，而是**动态冲减**——应付余额的 SQL 里 `LEFT JOIN (SELECT purchase_order_id, SUM(total_amount) ... WHERE status='confirmed')`（`receivables-payables/page.tsx:114-116`）。所以**退货单一落库，供应商欠款立刻变小**，无需任何额外写操作。
- **作废退货单**：`voidPurchaseReturnAction` 把货**加回**库存（`applyStockChange(before, +quantity, before.avgCost)`，`:216`）、写 `void_reverse` 流水（`:221-232`）、`status=voided`（`:234-237`）→ 应付自动恢复（因为 SQL 只统计 confirmed）。

### 1.4 售卖退货作废（`sale-returns/actions.ts:198-263`）

- 逐行**减库存**：先校验 `before.qty >= item.quantity`，否则报「库存不足…无法撤销退货」（`:223-225`）；再 `applyStockChange(before, -quantity, before.avgCost)`（`:226`）→ `void_reverse` 流水（`:231-242`）。
- **注意口径不对称**：退货入库用的是**原单快照成本**，作废退货出库用的是**当前均价**（`:226`）→ 作废后 `Product.avgCost` 可能与退货前不同（金额被当前均价「洗过一遍」）。
- 应收恢复同样是动态的（`:197` 注释「概览口径动态计算」）。

### 1.5 与「作废原单」的交互（重要口径缺口）

- `voidSaleOrderAction`（`sale-orders/actions.ts:514-625`）**不检查是否存在退货单或收款**（该文件全文无 `returns`/`return` 引用），它把**原单全部数量**按当前均价回补库存（`:536-559`）。
  → 若该单已退货 5/10，再作废原单，会把另外 10 件也补回 → **库存多出 5 件**；退货单仍是 `confirmed`，退货行 `costAmount` 仍挂在那里。
- `voidPurchaseOrderAction` 对 `received` 单会先校验「库存 ≥ 本单数量」，不足则直接提示「请改用【进货退货】」（`purchase-orders/actions.ts:294-306`）——这一条**部分**挡住了「已退货又作废」。
- 反向：已作废的原单**不能**退货（`sale-returns/actions.ts:69`、`purchase-returns/actions.ts:66`），也不能收付款（`receivables-payables/actions.ts:53,63`）。

### 2.3 `createPurchaseReturnAction` — `purchase-returns/actions.ts:43-188`

### 2.4 `voidPurchaseReturnAction` — `purchase-returns/actions.ts:191-253`

- guard：未登录/`sales` 禁（`:197`）；`reason` 必填（`:200-201`）；已作废幂等（`:205`）。
- 副作用（事务 `:208-238`）：逐行**加**库存（`:216`）+ `void_reverse` 流水（`:221-232`）；`status=voided` 三件套。**无库存上限校验**（作废退货是加库存，不需要）。
- 审计 `:239-246`，返回 `{ok:"已作废，库存已加回"}`。

### 2.5 行级/页面辅助（非 action）

- `parseReturnRows`（`src/lib/return-rows.ts:43-59`）：「空行/未填/填 0」→ 整行跳过（连退货价都不校验）；负数与非法文本**不跳过**，交给 zod 报错。测试固化于 `tests/return-rows.test.ts:22-105`（8 个用例，含「不填就是不退」「负数不是跳过」「非数字不当 0」）。

## 3. 收付款：数据模型与单据关联

### 3.1 模型（`prisma/schema.prisma:539-564`）

```
Payment {
  id, orderNo (unique, PAY/POF + yyyyMMdd + 4 位)
  direction  PaymentDirection  // receipt 收款 / payment 付款
  orderType  PaymentOrderType  // sale | purchase | sale_return | purchase_return
  orderId    Int               // 关联单据 id（按 orderType 区分表）
  amount Decimal(14,2), method PaymentMethod, remark, operatorId
  status PaymentStatus = confirmed | voided
  voidedBy/voidedAt/voidReason
  @@index([orderType, orderId])
}
```

- **关联方式 = 多态外键**（`orderType + orderId`），**没有 Prisma relation、没有 DB 外键**；`orderId` 指向 `sale_orders.id` 或 `purchase_orders.id`（`:543-544`）。索引 `@@index([orderType, orderId])`（`:561`）。
- **一笔付款只能挂一张单**：`orderId` 是单值（`:544`），zod 也是单值（`receivables-payables/actions.ts:17`）→ **不支持一笔核销多张单**。
- **没有客户/供应商外键**：对方是通过 `orderType+orderId` join 回单据得到的（`payments/page.tsx:103-120`、`supplier-statement/page.tsx:79-93`）。
- **不支持预收/预付**：没有任何无单据的收款路径（`orderId` 必填 positive）。
- **不支持退款**：`PaymentOrderType` 声明了 `sale_return`/`purchase_return`（`:56-61`），但全仓库**没有一处写入**（grep 结果：只有 `"sale"` 与 `"purchase"`，见 `receivables-payables/actions.ts:16,47,99,153`、`payments/page.tsx:76-77,216`、`supplier-statement/page.tsx:81`）。
- 枚举：`PaymentDirection`(51-54)、`PaymentOrderType`(56-61)、`PaymentMethod`(63-69)、`PaymentStatus`(41-44)。中文标签集中在 `src/lib/payment-labels.ts:5-21`。

### 3.2 `createPaymentAction` — `receivables-payables/actions.ts:29-132`

| 项 | 内容 |
|---|---|
| guard | `await requireLogin()`（**未登录是抛异常**，`guards.ts:28-32`，不是返回 error）；`role==="sales"` → 「业务员无收付款权限」（`:31`）→ 只有 admin/boss |
| zod | `direction: enum(receipt,payment)`；`orderType: enum(sale,purchase)`；`orderId` coerce int positive（「请选择单据」）；`amount` `requiredNumber({min:0}).refine(v>0)`；`method: enum(cash,bank,wechat,alipay,other)`；`remark: trim max200`（`:14-27`） |
| 未结金额 | sale：`totalAmount − receivedAmount − Σ confirmed returns.totalAmount`（`:55`）；purchase：`totalAmount − paidAmount − Σ confirmed returns.totalAmount`（`:65`） |
| 判定 | 单据存在（`:52,62`）；`status==="voided"` 拒（`:53,63`）；`amount > outstanding` → 「超出未收付金额…」（`:68-70`） |
| 副作用（事务 `:75-111`） | ① 生成 `PAY…`/`POF…` 单号（按 direction 选前缀，`:72`）；② `payments` 插 1 行；③ **同步冗余**：sale → `sale_orders.received_amount increment`，purchase → `purchase_orders.paid_amount increment`（`:99-109`） |
| 无单据状态校验 | **不限 `pending`/`received`**：待收货的进货单也能先付款（`:58-66` 只拒 voided） |
| 审计 | `entityType:"payment"`，`after` 含 orderNo/direction/orderType/orderId/amount/method（`:112-118`） |
| 返回形状 | `{ok:"收款/付款登记成功（PAY…，关联 SO…）"}`，**不 redirect**（`:122-124`）；失败 `{error}`。P2002 重试 3 次（`:73,126-131`） |
| 松耦合风险 | **action 不校验 direction 与 orderType 的配对**：`direction:"receipt"` + `orderType:"purchase"` 会成功落库（走 purchase 分支、加 `paid_amount`、单号却是 `PAY`）。网页表单永远传对（`payment-block.tsx:35,48,115-117`），CLI 若不自己约束就会造脏数据 |

### 3.3 `voidPaymentAction` — `receivables-payables/actions.ts:135-177`

- guard：`requireLogin()` + `sales` 禁（`:136-137`）。`reason` 必填（`:141`）。
- 幂等：已 `voided` → 「记录已作废」（`:145`）。
- 副作用（事务 `:147-164`）：`payments.status=voided` 三件套 + 对应单据冗余列 `decrement amount`。**没有库存副作用**。
- 审计 `:165-172`；返回 `{ok:"已作废，收付金额已冲回"}`。
- **没有「修改一笔付款」的能力**：全仓库 `payment.update` 只有这一处（void），`payment.delete` 不存在 → 记错金额只能「作废 + 重登」。

### 3.4 入口与死代码

- 登记入口**只在单据详情页**：`sale-orders/[id]/page.tsx:161-176`（`PaymentBlock direction="receipt"`）与 `purchase-orders/[id]/page.tsx:144-159`（`direction="payment"`）；组件为 `src/components/payment-block.tsx:58-212`（收款/付款共用，权限文案 `canPay` 由父页给，`:110`）。
- `/receivables-payables` **没有登记表单**，只给「详情 / 登记」链接（`unpaid-order-table.tsx:161-165`、`receivables-payables/page.tsx:18` 注释）。
- `src/app/(main)/receivables-payables/void-payment-button.tsx` 定义了 `VoidPaymentButton`，但**全仓库无任何引用**（grep `VoidPaymentButton` 只命中自身）→ 死代码。

## 4. 应收应付余额的确切计算口径（关键）

**口径 = 单据表冗余列 + 未作废退货单求和；付款表（payments）只用于展示与「按对象列示」，不参与余额计算。** 三处实现必须一致，逐条列出。

### 4.1 【权威】SQL 聚合（分组与合计都用它）

- 应收：`src/app/(main)/receivables-payables/page.tsx:90-105`
  ```sql
  SUM(GREATEST(so.total_amount - so.received_amount - COALESCE(sr.total,0), 0))
  FROM sale_orders so
  LEFT JOIN (SELECT sale_order_id, SUM(total_amount) AS total
             FROM sale_returns WHERE status='confirmed' GROUP BY sale_order_id) sr
  WHERE so.status='confirmed' AND created_at 在区间
  ```
- 应付：同文件 `:106-120`，`po.status IN ('pending','received')`，join `purchase_returns`。
- **单笔未结清**：`total_amount − received_amount/paid_amount − Σ confirmed 退货`（`page.tsx:127-132`；行数据 `:151-171`）。
- ⚠️ 表格只取最近 200 张（`:67,84` `take:200`）后再内存过滤（`:127`），**合计不受此限**（`:88-89` 注释、`:386-390` 截断提示）。

### 4.2 工作台总额（同一口径，全时间、不带日期筛选）

- `src/app/(main)/dashboard/page.tsx:39-56`：两段 `$queryRaw`，条件分别为 `so.status='confirmed'` 与 `po.status IN ('pending','received')`，**没有 `GREATEST`**（可能为负），并且**不做日期过滤**（全量）。
- `:62-63` 取 `total`；`:101-110` 展示为「应收总额/应付总额」。

### 4.3 单据详情页/列表页（同一口径，逐单）

- 售卖单详情：`sale-orders/[id]/page.tsx:82-90`（`outstanding = total − received − Σ confirmed returns.totalAmount`）。
- 进货单详情：`purchase-orders/[id]/page.tsx:72-86`（同式，用 `paidAmount`）。
- 售卖单列表：`sale-orders/page.tsx:135-145`（`needsReceipt = total − received − returned > 0`）；表格内 `sale-orders/order-table.tsx:108`。
- 进货单列表：`purchase-orders/page.tsx:136-143`；`purchase-orders/order-table.tsx:107`。

### 4.4 报表与对账

- 应收明细报表 `lib/reports.ts:199-209`：`unreceived = max(0, total − receivedAmount − returned)`；应付明细 `:154-164` 同式。列里都有「退货冲减」。
- 厂家对账 `supplier-statement/page.tsx:95-106`：`unpaid = max(0, totalAmount − Σ confirmed payments.amount − returned)`。
  **注意这里的 paid 是从 payments 表按单据求和**（`:79-96`），不是 `paidAmount` 冗余列 —— 与 4.1/4.2/4.3 是**两套取数方式**，只在「冗余列始终与付款表一致」的前提下才等价（登记/作废都同时维护，见 `receivables-payables/actions.ts:99-109,153-163`，目前一致；若将来直接改库就会分叉）。
- **出口**：`/reports/export?tab=receivables|payables`（`src/app/reports/export/route.ts:8-48`，sales 角色 403 `:11`）导出同一份 `buildReport` 数据。

### 4.5 【口径缺口】不冲减退货的地方（CLI 对数时最易踩）

| 位置 | 代码 | 现象 |
|---|---|---|
| 工作台今日销售额 | `dashboard/page.tsx:22-26` | `saleOrder.aggregate(_sum.totalAmount)`，不减退货 |
| 工作台今日利润 | `dashboard/page.tsx:27-33` | 成本快照求和，不减退货 |
| 进销存汇总 | `reports.ts:98-109` | `saleAmount` = 全部 confirmed 售卖单总额，注释里都没提退货 |
| 单品销售排行 | `reports.ts:222-236` | `saleOrderItem.groupBy(_sum.quantity/amount/costAmount)`，退货行**不影响**销量/销售额/成本 |
| 操作员业绩 | `reports.ts:273-293` | 按售卖单聚合，不减退货 |
| 售卖单详情「本单毛利」 | `sale-orders/[id]/page.tsx:91` | `profit = total − ΣcostAmount`，退货后毛利不变（虚高） |
| 单据「金额」本身 | 原单 `totalAmount` 永不变 | 退货不修改历史单据（不变量 3.1） |

→ 结论：**「销售额/毛利」类指标 = 不冲减；「应收应付/未收未付」类指标 = 冲减退货**。CLI 的对数验收必须按指标分开认定，否则一定对不上。

### 4.6 付款表在哪些地方被求和（展示口径）

- `/payments` 头部合计：`prisma.payment.groupBy({by:["direction"], _sum:{amount}})` + 默认 `status=confirmed` 过滤（`payments/page.tsx:90-100,122-124`）。
- 单据详情的「已收/已付」合计：**用 payments 数组在内存求和**（`payment-block.tsx:86-88`），与 `receivedAmount` 冗余列并列显示（`:89` 用 `outstanding` prop）——两者理论上应相等。
- 供应商对账 `supplier-statement/page.tsx:96`（见 4.4）。

## 5. 审计覆盖情况

本轨道（退货 + 收付款）**6 个写 action，6 个写审计，无遗漏**：

| action | file:line | action 值 | entityType | before/after |
|---|---|---|---|---|
| `createSaleReturnAction` | `sale-returns/actions.ts:177-183` | create | sale_return | 仅 after（orderNo/saleOrderId/totalAmount） |
| `voidSaleReturnAction` | `sale-returns/actions.ts:249-256` | void | sale_return | before+after（含 voidReason） |
| `createPurchaseReturnAction` | `purchase-returns/actions.ts:170-176` | create | purchase_return | 仅 after |
| `voidPurchaseReturnAction` | `purchase-returns/actions.ts:239-246` | void | purchase_return | before+after |
| `createPaymentAction` | `receivables-payables/actions.ts:112-118` | create | payment | 仅 after（金额/方向/单据） |
| `voidPaymentAction` | `receivables-payables/actions.ts:165-172` | void | payment | before+after |

机制与限制（`src/lib/audit.ts:25-50`）：
- `action` 是**封闭联合**（`"login"|"logout"|"create"|"update"|"delete"|"receive"|"void"|"reset_password"`，`:15`）→ **没有 `refund`/`reverse` 之类动作**；红冲只能记成 `void`。
- 审计写在**业务事务之外**（如 `sale-returns/actions.ts:176` 事务结束 → `:177` 才 audit），且失败只打日志（`audit.ts:46-49`）→ **可能出现「业务成功但审计缺失」**。CLI 若要求「写操作必有审计」，需要另外保证（现有网页也同样不保证）。
- `before` 只记单号/状态这类摘要，**不记行级明细**（退货的每行数量/成本不在审计里，只在 `sale_return_items`）。
- 本轨道相关表 `stock_movements`、`sale_return_items`、`purchase_return_items` 是业务账，由所属 action 一次写入，**不单独写审计**（设计上如此）。
- 相邻写操作抽查：星标开关有审计（`sale-orders/actions.ts:648-657`）。**申报范围**：本节只对退货 + 收付款三条路径下了"全覆盖"结论；全项目其他模块的审计覆盖度属第 6 轨。

## 6. 退货/收付款中「只能点页面、没有服务端 action」的部分

1. **没有「退货单详情页」**：路由清单（plan 第 2 节）里只有 `/sale-returns`、`/purchase-returns` 列表（`sale-returns/page.tsx`、`purchase-returns/page.tsx`）。行明细只在**原单详情**里展示（`sale-orders/[id]/page.tsx:282-336`、`purchase-orders/[id]/page.tsx` 同构）。→ CLI 若要「按退货单号查明细」，**必须自己写查询**，没有现成页面/端点可复用。
2. **两个退货单列表页都没有任何筛选**（只支持 `?page=`，`sale-returns/page.tsx:19,24-28`）→ CLI 的 `query returns --from/--to/--customer` 无页面口径可抄。
3. **可选择原单的退货入口在服务端就不存在**：`/sale-returns/new?orderId=` 必须带 `orderId`，否则只渲染一句「请从售卖单详情页发起退货」（`sale-returns/new/page.tsx:37-43`；`purchase-returns/new/page.tsx:37-43`）。→ 「退货」这件事本身**依赖一个先存在的单据 id**，CLI 需要两步（query 原单 → create return）。
4. **退货行不可增删、行集合由服务端按原单生成**（`return-form.tsx:64-77`）→ CLI 传的行必须属于该原单（服务端会校验 `退货行与原单不匹配`，`sale-returns/actions.ts:95`）。
5. **退货单备注（`remark`）没有任何写入入口**：action 不写、表单没有（见 1.2）→ CLI 也写不进去，除非改服务层。
6. **收付款没有独立登记页**（只能从单据详情页）；没有「按客户/供应商一次性结多张单」的批量核销；没有预收/预付；没有退款给客户/供应商。`PaymentOrderType` 已留 `sale_return`/`purchase_return` 枚举位但无人写入（见 3.1）。
7. **收付款无「改」只有「作废」**（3.3）。
8. **登记收付款页面的金额默认值来自服务端计算的 outstanding**（`payment-block.tsx:126`），CLI 拿不到这个默认值时必须自己按 4.1 的公式算一遍。

## 7. 对 `docs/agent-cli-plan.md` 的具体修订建议

### 7.1 第 3 节第 5 条「退货需冲减（⚠️待核实）」→ 可改 ✅

建议改写为：
> 5. **退货需冲减（✅已核实）**：售卖退货**新增**一条 `stock_movements(bizType=sale_return_in)` 正向流水，并按**原单成本快照均价**（`saleOrderItem.costAmount/quantity`）回补 `Product.stock_qty/stock_amount/avg_cost`；进货退货按**当前移动加权均价**出库，写 `purchase_return_out` 负向流水。退货**不改原单任何字段**、**不重算其它单据成本**。应收应付余额由 `total − 已收付 − Σ未作废退货单` 动态算出（无退货→付款的写回滚）。证据：`sale-returns/actions.ts:105,142,147-158`、`purchase-returns/actions.ts:136,141-152`、`receivables-payables/page.tsx:90-120`。

并新增一条不变量：
> 7. **退货不冲减「销售额/毛利」口径**：工作台今日销售额、进销存汇总、销售排行、操作员业绩、单据毛利**都不减退货**；只有应收应付/未收未付类指标减退货。CLI 对数时按指标分开认定（`reports.ts:107-109`、`dashboard/page.tsx:22-26`）。

### 7.2 第 9 节第 3 条「收付款记账口径与单据关联方式（⚠️待核实）」→ 可改 ✅

建议改写为：
> 3. **收付款记账口径（✅已核实）**：`payments` 表用**多态关联** `orderType(sale|purchase)+orderId`（**无 DB 外键、无客户/供应商列**），**一笔只核销一张单**；**无预收预付、无跨单核销、无退款**（`PaymentOrderType.sale_return/purchase_return` 是**未被写入的枚举位**）。余额不靠付款表求和，而靠单据冗余列 `received_amount/paid_amount`（登记 `increment`、作废 `decrement`，`receivables-payables/actions.ts:99-109,147-164`）；唯有「厂家对账」是从 payments 表按单求和（`supplier-statement/page.tsx:96`），两套取数目前一致。**只能作废不能修改**（无 update/delete 付款的路径）。

### 7.3 计划里需要修正/补强的地方

1. **5.6「Agent 单先不动库存」与退货叠加需要额外规定**：现有 `voidSaleOrderAction` **不检查退货/收款**，作废一张已部分退货的售卖单会把**全部数量**补回库存（`sale-orders/actions.ts:536-559`，无 returns 校验）。审核流若允许「作废 Agent 单」，必须先补这条校验，否则库存会错。
2. **Phase 2.5 要求「审核前不产生库存/成本副作用」时，退货也必须纳入**：退货是**仅次于开单**的库存写操作（且售卖退货入库用快照成本），若 Agent 的退货单立即可见库存，会绕过审核把关。建议审核流覆盖 `sale_return`/`purchase_return` 与 `payment` 三类。
3. **Phase 3 顺序建议调整**：计划把「收付款」排在「开单」之前（`plan 第 8 节 Phase 3`）。但收付款的 `outstanding` 校验**依赖售卖/进货单的创建逻辑**（且依赖退货冲减口径），而它自身不产生库存副作用、风险更低——保持「先收付款」是合理的；但**退货**应排在「作废/改单」**之前**，因为作废原单与退货的交互（7.3.1）必须先有正确语义。
4. **第 10 节风险表**新增一行：`退货与原单作废/并发退货` → 对策：① 服务层在 `void 原单` 前检查是否存在 confirmed 退货/收付款；② 退货余量校验移入事务并对原单行加锁（`SELECT … FOR UPDATE`）或新增唯一/幂等键，现有实现是事务外读判断（`sale-returns/actions.ts:74-98`）。
5. **第 7 节命令面**里 `wc-cli order estimate fill` 之外的写命令应补 `--line` 语义：退货命令**必须显式给 `unitPrice`**（zod 必填，`sale-returns/actions.ts:26-31`），且 `--qty 0/不填` = 该行不退（`return-rows.ts:43-59`）。
6. **CLI 侧必须自己校验 `direction` × `orderType` 配对**（action 不校验，见 3.2 末行）。

### 7.4 必须报给主智能体的两个缺陷（会影响 CLI 正确性，与计划书原文无关）

1. **进货退货单号序号查错表（真实 bug）**：`purchase-returns/actions.ts:107-116` 用 `tx.purchaseOrder.findMany({ where: { orderNo: { startsWith: "PRF<日期>-" } } })` 求当日最大序号 —— 查的是 `purchase_orders`（前缀永远是 `PO`），**永远匹配不到**，`maxSeq` 恒为 0，单号恒为 `PRF<日期>-0001`。当天第二张进货退货单 → `order_no` 唯一键冲突 P2002 → 重试 3 次仍冲突（`:104,181`）→ 返回「单据号生成失败，请重试」。**售卖退货无此问题**（`sale-returns/actions.ts:112` 查的是 `saleReturn`，正确）。
2. **`dangerouslySetInnerHTML` 式的口径分叉点**：`supplier-statement/page.tsx:96` 从 payments 求和，其余全部用冗余列；CLI 对数时必须指定用哪一套（建议统一用冗余列，即 4.1）。
